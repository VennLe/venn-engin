# 帧节奏：为什么"移动 + 转视角"看起来一顿一顿

> 2026-10-23 · 用户报障："游戏运行后，角色在移动时尤其是鼠标移动转换视角时，
> 明显感觉角色动作在卡顿，步伐也变得僵硬了起来。"
> 验收：`tools/verify_frame_pacing.py`（12 条，约 60 秒，含对照组）
> 相关：`engine/core/RunMode.h`、`engine/rhi/Swapchain.cpp`、`engine/core/Time.h`
> 探针：`MYVK_LOG_DT=1`（逐帧 `FRAME-DT` 锚点，含 CPU 分段）+ `tools/_probe_frame_dt.py`
>
> **2026-11-06 补记：同一个症状还有第二章** —— 锁了 FIFO 之后仍可能落进
> "一帧 8.6 ms、一帧 24.9 ms"的交替节拍，根因是交换链图像数。见 §6。

---

## 0 · 一句话结论

**动画播放器和角色位移都是干净的，脏的是"时基"。**
呈现模式原来是 MAILBOX（不锁帧），主循环在 60 Hz 的屏上跑到 **470~490 fps**，
每帧步长抖动 **31%**。渲染帧与显示刷新不是整数倍关系 → 合成器每次取的
"最新一帧"距上次刷新多久完全看运气 → 匀速运动（转视角时整个视野都在动）
推进得不均匀 = 肉眼看到的"一顿一顿"，走路的步频也跟着忽快忽慢。

修法只有一行策略：**默认 FIFO（锁垂直同步）**。副作用是帧率从 480 掉到 60 ——
顺带省掉 87% 的 GPU 空转。

---

## 1 · 先证明"不是动画的错"

`MYVK_LOG_DT=1` 会在每帧末尾打一行，把三件事放在一起（缺一不可）：

```
FRAME-DT f=<帧号> dt=<步长> play=<0|1> cap=<0|1> pos=(x,y,z) animT=<播放头>
```

* `dt` —— 这一帧的真实步长（抖不抖、有没有尖刺）
* `pos` —— 玩家本帧的落点（位移在空间上是否连续）
* `animT` —— 骨骼动画的播放头（姿势相位是否按 dt 线性推进）

修复**前**，按住 W 并持续左右甩鼠标（`tools/_probe_frame_dt.py`）实测：

| 量 | 值 | 判读 |
|---|---|---|
| dt | 2.08 ms ± 0.63 ms（**31%**），峰 5.0 ms | 时基在抖 |
| 3D 速度 | 3.000 m/s，cv **0.7%** | 位移是干净的 |
| ΔanimT / dt | **1.0000** | 播放头严格按 dt 推进 |
| 动画状态切换 | idle → walk → idle，共 3 条 | 没有反复横跳 |

也就是说：**逐帧看每一帧都是对的**，问题只可能出在"这些帧什么时候被显示"
—— 那是呈现层，不是动画层。这一条先钉死，避免后面把力气花在播放器上。

---

## 2 · 根因：470 fps 喂 60 Hz 的屏

`Swapchain::create` 原来的策略是"有 MAILBOX 就用 MAILBOX"。MAILBOX 不限制
提交速率，而editor 的空场景（一个角色 + 一块地）在这个 GPU 上轻松跑到
480 fps：

* 渲染 8 帧，显示刷新 1 次（60 Hz）；
* 合成器取的是"最新一帧"，它距上一次刷新的年龄在 **0~2.1 ms** 之间随机；
* 于是每两次刷新之间，仿真时间前进 16.7 ms **±12%**；
* 匀速运动因此被判成"有时走得多、有时走得少"。转视角时最刺眼（整个画面
  都在动），走路时表现为步频忽快忽慢（"步伐僵硬"）。

这不是"帧率高所以更流畅"——**帧率与刷新率不是整数倍时，高帧率反而会制造
抖动**。要么锁到刷新率（FIFO），要么让帧率是它的整数倍，没有第三条路。

## 3 · 修法

### 3.1 呈现模式默认 FIFO（`engine/core/RunMode.h` + `rhi/Swapchain.cpp`）

```cpp
// RunMode.h
inline bool vsyncEnabled() {
    if (const char* s = std::getenv("MYVK_VSYNC")) return s[0] != '0';
    return !automationRun();          // 自动化不锁，互动锁
}
```

* `MYVK_VSYNC=1` / `=0` 显式指定（量 GPU 峰值 / 延迟时用 0）。
* 不设时：**自动化关、互动开**。判据见 `core::automationRun()`（`MYVK_LOG_RECTS`
  之类，任何一条命中就算脚本），因为脚本要的是"跑满帧数"，不是画面。
* 交换链创建处打一行锚点，验收脚本可以断言：
  `Swapchain present mode = FIFO (vsync=1)`。

### 3.2 单帧步长上限 0.1 s（`core/Time.h`）

一次真正的长停顿（着色器热重载、拖窗口、系统卡一下）之后墙钟 dt 可能是
0.2~1 s。不夹住的话这一帧里玩家会按 `速度 × dt` 瞬移半米、动画播放头一次
跨过小半圈、重力一步把角色推进地里。夹住之后最多推进 1/10 秒 —— 慢一点，
但**连续**。对"卡顿"的主观观感来说，长停顿本身的伤害小于停顿之后那一记瞬移。

⚠ 不影响确定性验证：`MYVK_FIXED_DT` 走的是另一条分支。

## 4 · 修复后的实测

同一台机器、同一个场景、同样的操作（W + 甩鼠标）：

| 量 | 修复前 | 修复后 |
|---|---|---|
| 帧率 | 470~490 fps | **60.1 fps** |
| dt | 2.08 ms ± 0.63 ms（**31%**） | 16.64 ms ± 0.82 ms（**4.9%**） |
| 尖刺（dt > 2×均值） | 6% 的帧 | **0** |
| 速度 cv | 0.7% | 0.08% |
| ΔanimT / dt | 1.0000 | 1.0000 |

`tools/verify_frame_pacing.py` 把上面几条都写成断言，并且**带对照组**：
`MYVK_VSYNC=0` 时必须比锁帧组快 ≥ 1.5× 且抖动 > 10%（证明开关是活的、而且
"不锁就会抖"这件事本身是可复现的，不是拍脑袋）。

> ⚠ 这里原来要求 `> 200 fps`（绝对帧率），2026-11-06 改成相对值，
> 理由见 §6.6。

## 5 · 还没做的

* **帧率上限选项**（60 / 120 / 无限制）目前只有环境变量，没有 UI。真需要
  分级的话，它应该落在渲染设置页，而不是再加一个 `MYVK_*`。
* 如果某台机器**撑不住 60 fps**，FIFO 会退到 30 fps（而不是像 MAILBOX 那样
  在 45~60 之间抖）。届时该做的是降 DRS / 关特性，不是取消锁帧。
* 相机仍然**刚性**跟着角色（第三人称 `focus = pos + (0,0,1.2)`）。时基干净
  之后这已经不是问题；但将来若在陡峭地形上看到"整个人连镜头一起上下颠"，
  该动的是相机的跟随滤波，不是帧节奏。

## 6 · 补记（2026-11-06）：锁了 FIFO 还会顿 —— 交换链图像数

### 6.1 症状：均值对，逐帧不对

锁帧之后 `verify_frame_pacing` 仍有 4 条红，但读数很怪：

```
A2 帧被锁在刷新率上        dt=16.75 ms → 59.7 fps      ← 均值完全正确
A3 稳态不塌陷              p90=25.3 ms 中位=9.6 ms 比值=2.64   ← 红
A4 尖刺 < 10%              55/129 帧，中位间隔 2 帧           ← 红
A5 静止 vs 移动停顿一致    静止 50 个 vs 移动 55 个           ← 红
```

**均值 60 fps，而中位数只有 9.6 ms** —— 这不是"变慢"，是**双峰**。

### 6.2 定位：把 CPU 分段接进 `FRAME-DT`

只靠 `dt` 看不出"这 24.9 ms 花在哪"。把 `CpuProfiler` 的上一帧读数追加进
同一行（现在常驻，见 §6.5）：

```
FRAME-DT … dt=24.6 cpu rend=21.80 rw=15.99 rec=5.00 pres=0.05 logic=0.83
FRAME-DT … dt= 8.9 cpu rend= 6.09 rw= 0.05 rec=5.34 pres=0.04 logic=0.81
```

判读：

* 长帧的 16 ms 全在 `rw`（`vkWaitForFences`），`rec`（录命令）**没变** ——
  所以不是"渲染变重了"；
* `pres` 恒 0.04 —— `vkQueuePresentKHR` **从来不阻塞**；
* 于是阻塞被推到了**下一帧的 fence wait**，形成极限环：

```
dt:      8.6   24.9    8.6   24.9   …   均值 16.7（名义 60 fps）
等 fence: 0.05  16.0    0.05  16.0
```

每两帧一个"快-慢"。平均帧率骗过所有看均值的判据，但肉眼就是**一顿一顿**。

### 6.3 根因：交换链给了 3 张图像

`Swapchain::create` 原来是 `minImageCount + 1`（这台机器 = 3 张）。3 张图像
允许 **2 个 present 排队**，于是主循环能跑到显示器前面一帧：CPU 连续跑两次
不阻塞，然后被一张刚释放的图像憋住 16 ms。

⚠ **这一条是双稳态**：同一份代码、同一台机器，有时锁得干干净净（全程
16.6 ms），有时落进交替。这正是上一轮排查"基线绿、改动红"的真相 ——
不是改动引起的，是硬币的两面。**判据不可复现时，先怀疑被测系统有多个稳定态。**

### 6.4 修法：按呈现模式取图像数

```cpp
const bool synced = (presentMode == VK_PRESENT_MODE_FIFO_KHR ||
                     presentMode == VK_PRESENT_MODE_FIFO_RELAXED_KHR);
uint32_t imageCount = synced ? minImages : (minImages + 1);
```

* **锁帧时取 `minImageCount`（2）**：present 队列只能压一帧，CPU 被 vblank
  咬住，`dt` 全程 16.5~16.9，`rw` 稳定在 ~8 ms（等一个 vblank）。
* **不锁帧时仍取 `min + 1`**：多余图像存在的意义就是让 CPU 不排队等显示器，
  MAILBOX 要靠 3 张才跑得满。一刀切成 2 会压掉不锁帧的吞吐。

实测（同一场景、同样操作）：

| 量 | 修复前 | 修复后 |
|---|---|---|
| dt 形状 | 8.6 / 24.9 严格交替 | **16.7 ± 0.3 全程均匀** |
| A3 p90/中位 | 2.64 | **1.04** |
| A4 尖刺 | 55/129 帧 | **0/127 帧** |
| A5 静止 / 移动停顿 | 50 / 55 | **0 / 0** |

代价：锁帧时少一张图像 → CPU/GPU 重叠少一帧。本机实测 GPU 侧工作约 6 ms
（`rend 13.9 − rw 7.9`），远在一帧预算之内，没有掉帧。

### 6.5 顺带：`FRAME-DT` 常驻 CPU 分段

`cpu rend/rw/rec/pres/logic` 五个数现在固定跟在 `FRAME-DT` 后面。理由就是
§6.2 —— 没有它们，"24.9 ms 的帧"会被归错因（这轮先怀疑过日志 I/O，又怀疑
过动画采样，都不是）。读数是**上一帧**的（`beginFrame()` 推进历史后才可见），
归因时按相邻帧配对看。

### 6.6 C1 的阈值从绝对改成相对

`MYVK_VSYNC=0` 原来是硬要求 `> 200 fps`。这条在本机永远红：编辑器每帧要画完
整个 ImGui 面板 + 视口，实测 **103 fps（9.7 ms/帧）**，而在 G 组的口径里
机器**是**给 MAILBOX 的 —— 于是判据落进"拿到 MAILBOX 却没解锁 = 真回归"
那一支。可 9.7 ms 是**工作量**，不是**锁**。

解锁成功与否的可观测不是"跑到多少帧"，而是"比锁帧快多少"：

```
C1 不锁时确实更快（≥ 锁帧组的 1.5×）  102 fps（1.70× 锁帧组 60 fps）
```

换台更快的机器或更空的场景，绝对帧率会自己涨，判据不用改。
（C2"不锁时抖动更大"仍然保留：27.3%，它是"开关确实是活的"的证据。）
