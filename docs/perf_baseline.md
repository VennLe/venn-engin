# 性能基线（P1）

> **这份文档回答一个问题：引擎现在多快，贵在哪。**
> 在这之前，项目里所有性能数字都是 **Debug** 的（`build/`，`/RTC1` + 全断言 +
> 不内联）。拿它判断"要不要优化、优化有没有用"是没有意义的。所以先立一份
> **RelWithDebInfo** 基线，后面 P2~P10 改完都跟这张表比。
>
> 采集工具：`tools/bench_baseline.py`（2026-11-01 新增）
> 机器：**Intel Iris Xe**（集显，本机）· 垂直同步默认 · `MYVK_VALIDATION=0`

---

## 1 · 怎么跑

```bat
make perf-build                          :: → build-rel/bin/（与回归用的 build/ 分开）
python tools/bench_baseline.py --mode game --frames 900   :: 运行时负载（Game.exe）
python tools/bench_baseline.py --mode editor --frames 300 :: 编辑器视口空闲
```

⚠ **为什么必须另开 `build-rel/`**：`build/` 是**回归用的 Debug**，一切
`verify_*.py` 都指它。把 `build/` 换成 RelWithDebInfo 会同时改掉两件事 ——
"断言在不在"和"帧率是多少" —— 回归与基线互相污染。`build-*/` 已在 `.gitignore` 里。

⚠ **量法五条**（改了就不可比）：

1. **丢预热帧**（默认前 14）：起手几帧被 `maxFrameTime` 钳到 100 ms；
2. **中位数，不用均值**：本机 DWM 每 ~15 帧偷一次 55~73 ms，均值被那几下决定；
3. **GPU 时间取 `GPU-TIMING` 日志**（引擎自己打的时戳和），不是 `1/fps`
   —— 后者含呈现排队；
4. **`MYVK_RUNTIME_MAXFPS=0`**：运行时 `assets/game.json` 里 `maxFps=60`，
   开着上限量出来全是 16.6 ms，什么也测不出来（第一次跑就撞上了）；
5. **`--frames 900`**（不是 300）：`GPU-TIMING` 每 **30 帧**一条，300 帧只有
   10 个样本，中位数没有意义。

## 2 · 基线表（2026-11-01，`build-rel`，Game.exe = 真负载）

```bat
python tools/bench_baseline.py --mode game --frames 900
```

| 场景 | 分辨率 | 样本 | GPU 中位 (ms) | GPU max (ms) | 墙钟 fps |
|---|---|---|---|---|---|
| `anime_demo.json` | 1280x720 | 31 | 12.1 | 14.5 | 67 |
| `anime_demo.json` | 1600x900 | 31 | 16.4 | 18.9 | 51 |
| `anime_demo.json` | 1920x1080 | 31 | 24.3 | 30.8 | 39 |
| `sandbox.json` | 1280x720 | 31 | 10.7 | 12.6 | 75 |
| `sandbox.json` | 1600x900 | 31 | 14.8 | 17.8 | 56 |
| `sandbox.json` | 1920x1080 | 31 | 19.7 | 24.1 | 42 |

`anime_demo` = 单角色 + 二次元着色链；`sandbox` = 空场景 + 地形。
墙钟 fps 含加载与退出，只能当量级；**趋势看 GPU 中位**。

### 2.1 分段（贵在哪一段）

| 场景 | 分辨率 | forward | depth | shadows | post | local_sh | cluster |
|---|---|---|---|---|---|---|---|
| `anime_demo` | 1280x720 | 5.20 | 2.61 | 2.04 | 1.34 | 0.78 | 0.04 |
| `anime_demo` | 1600x900 | 7.75 | 3.77 | 2.04 | 1.96 | 0.77 | 0.06 |
| `anime_demo` | 1920x1080 | **12.57** | 5.17 | 2.05 | 2.71 | 0.78 | 0.07 |
| `sandbox` | 1280x720 | 4.67 | 2.01 | 1.77 | 1.34 | 0.79 | 0.04 |
| `sandbox` | 1600x900 | 6.98 | 3.10 | 1.96 | 1.76 | 0.79 | 0.06 |
| `sandbox` | 1920x1080 | 9.81 | 4.40 | 2.72 | 1.76 | 0.79 | 0.07 |

**读法**：

- **`forward` 是唯一的大头**（1080p 占帧时间 50%），并且**随分辨率线性涨**
  （5.2 → 12.6 = ×2.4，正好是像素数比 ×2.25）→ 它是**填充率**，不是几何/提交。
  想快只能降 shading 成本或降分辨率（DRS / 半分辨率后处理），**改 CPU 一点用没有**。
- **`depth` 也随分辨率线性涨**（2.6 → 5.2 = ×2.0），说明 DepthPrePass 现在是
  **带宽**而不是三角形数限制 → 和 memory 里那条"P2 rest 分解 / P3 buffer 预留
  都改 CPU"是两件事，别拿它们来期待这项。
- **`shadows` 几乎不随分辨率动**（2.04 / 2.05 / 2.05）→ 它跟的是**光源数与级联
  贴图尺寸**，不是屏幕像素。这条决定了"降分辨率救不了阴影"。
- **`post` 随分辨率涨**（1.34 → 2.71），`local_sh` / `cluster` 常量级（0.78 / 0.06），
  后者说明分簇本身几乎免费 —— 真要省就去省分簇之后的光照。

## 3 · Debug vs RelWithDebInfo：一个反直觉的结论

同配置（`Game.exe`，`anime_demo`，1920x1080，`--frames 600`）：

| 构建 | GPU 中位 (ms) | 墙钟 fps |
|---|---|---|
| `build/`（Debug，`/RTC1` + 全断言） | 26.2 | 36 |
| `build-rel/`（RelWithDebInfo） | 24.3 | 39 |

**只差 8%。** 编辑器侧也一样（1600x900：Debug 11.0 vs Rel 11.8，互有胜负）。

结论（这条比数字本身重要）：

1. **GPU 时间与 CPU 构建类型无关**是预期之内的；但 **墙钟也几乎不变**，说明
   这两份场景**当前不是 CPU 受限** —— 42% 的帧时间里 CPU 在等 GPU（或等呈现）。
2. 所以 **"把 Debug 换成 Release 就能快一倍"是错的**，反过来说，
   **以前拿 Debug 数字做的"性能退步"判断也不可信**：它们可能只是 GPU 抖动。
3. P2~P10 里凡是**只动 CPU** 的项（P2 rest 预计算、P3 buffer 预留），在这两份
   场景上**不会**体现在帧率上；要量它们得看 `FRAME-DT` 与 CPU 侧提交时间，
   或者把场景换成"多角色 + 多光源"把 CPU 压上去。

## 4 · 怎么用它判断"有没有变慢"

1. 同一台机器、同一个脚本、同一份场景，**同一次开机内**前后跑；
2. 只比 **GPU 中位**（和 §2.1 的分段大头 `forward`）；
3. 掉了超过 **10%** 才算变慢 —— 本机同配置重复跑的自然波动约 3~6%，
   跨会话能到 60%（`verify_frame_pacing` 10-31 重标定时量到过）。

⚠ **不要**把 `bench_baseline.py` 塞进回归：帧率随机器状态浮动，进回归就是随机红。
它是**采集器**；那条"别卡顿"的闸门是 `verify_frame_pacing`（用 p90 与
"静止 vs 移动"对照，不用绝对帧率）。

## 5 · 已知局限（下次补之前别拿这张表下错结论）

- **没有"角色数"这一维**：`anime_demo` 只有 1 个角色，`sandbox` 是空场景。
  群像场景（同屏 10+ 角色，二次元常态）要等 **B8 蒙皮 LOD** 的夹具，
  在那之前**别拿单角色数字去估群像**。
- **分辨率只改窗口大小**，不改 `renderScale`（DRS 关着）。要量 DRS 得单独开。
- **没有加载时间**：这张表只有稳态帧时间。着色器变体编译、`.vmesh` 解析、
  纹理上传都不在里面 —— 而它们才是"第一次进去卡三秒"的真凶。
- **只有本机集显**：换独显/换机器这张表直接作废，必须重测。
