# Venn 引擎「二次元 3D 游戏」定位差距审计

> 审计日期：2026-10-25  
> 审计范围：`engine/` 81,221 行 + `editor/` 50,841 行 + `runtime/` 5,580 行 + `assetio/` + `assets/shaders/`  
> 结论基于逐文件通读与全仓检索，每条都带证据位置。

---

## 0 · 一句话结论

**引擎的渲染基础设施是"现代通用 3D 引擎"水准，甚至超出当前需求；但它是一台通用写实引擎 —— 而"二次元"不是一组材质参数，是一整套非物理的着色体系与表演体系。**

当前实事：

> ⚠ **下表是 2026-10-25 审计当时的快照，保留原样是为了留住"当时判断错在哪"。**
> 其中三行已经不成立：NPR 卡通着色（§7 落地基础版）、头发次级物理
> （§9 落地弹簧骨）、描边（§11 落地后处理边缘检测）。看现状请跳 §7~§11，
> 不要拿这张表当当前状态。

| 维度                                              | 现状                                                               |
| ----------------------------------------------- | ---------------------------------------------------------------- |
| NPR 卡通着色代码                                      | **0 行**（`toon`/`cel`/`ramp` 在 `engine/` 与 `assets/shaders/` 零命中） |
| 描边                                              | **0 行**（`VK_CULL_MODE_FRONT_BIT` 全仓 0 命中，stencil 全 `DONT_CARE`）  |
| 面部专用处理（SDF face shadow）                         | **0 行**（全仓 SDF 唯一实现是 UI 字体图集）                                    |
| Morph Target / Blend Shape（表情）                  | **0 行**，且资产格式、IR、加载器、顶点布局、着色器、渲染器 **七处全断**                       |
| 头发/衣物次级物理                                       | **0 行**                                                          |
| 动画状态机 / 层 / 遮罩 / 事件 / Root Motion / IK / LookAt | **0 行**（只有硬编码四态 if-else）                                         |
| 过场时间轴 / 对话 / 字幕                                 | **0 行**                                                          |

当前默认角色 Alicia 的"卡通感"来自**贴图里烘死的渐变**（`docs/alicia_import.md:44` 原话："卡通渲染贴图（toon 材质已经烘在贴图里，PBR 下直接能看）"）。这意味着一换光照、一换视角、一加动态光，卡通感立刻崩 —— 因为它根本不是着色器算出来的。

**这个引擎现在能做的：** 一个渲染质量不错的写实风格第三人称 Demo。  
**这个引擎现在不能做的：** 任何一部二次元游戏里的任何一个角色特写镜头。

## 1 · 三个根因级缺陷（不是"缺功能"，是"架构挡路"）

下面三条必须先改，否则后面每一条 NPR 需求都会撞墙。它们共同的特征是：**改造成本随时间指数增长，越早改越便宜。**

### A. 着色器变体是全组合笛卡尔积 —— NPR 加不进去

**证据：**

- 关键字只有 6 位：`engine/render/ShaderKeywords.h:56-75`（`kKeywordCount = 6`，bit0~bit5 已用满）
- CMake 用 `foreach(MASK RANGE 0..1<<N)` **无条件全展开**：`CMakeLists.txt:383-413`
- 实测产物：`build/bin/shaders/` 里 **128 个 pbr 变体**（64 组合 × `pbr.frag` + `pbr.bindless.frag`）+ 62 个其他 = **190 个 .spv，11 MB**

**为什么这是致命的：**

二次元渲染至少需要新增这些**互斥的着色模型**与开关：

| 需求                     | 需要的维度                                    |
| ---------------------- | ---------------------------------------- |
| Toon 着色模型              | 与 Default/Skin **互斥**的第三档 `ShadingModel` |
| 描边 pass                | 独立管线（正面剔除 + 法线外扩），不该进主变体表                |
| 面部 SDF 阴影              | 开关（只有角色头部需要）                             |
| 头发各向异性高光               | 与 Toon **互斥**的第四档                        |
| 眼睛专用（MatCap/视差）        | 与 Toon **互斥**的第五档                        |
| 高光遮罩 / ramp 贴图         | 开关                                       |
| 描边遮罩                   | 开关                                       |
| 第二 UV（面部 SDF/lightmap） | 开关                                       |
| 形态键                    | 开关                                       |

**按当前机制 = 6 + 9 = 15 bit = 32,768 组合 × 2 个着色器 = 65,536 个 .spv。**

即使全部有效组合只有几百个，`foreach` 也会老老实实编 6.5 万个（单个 68~78 KB，合计约 **5 GB**，编译时间从分钟级变小时级）。**这条路走不通。**

**正确形态（业界做法）：**

1. **按着色模型拆文件**，而不是在一个 `pbr.frag` 里堆 `#if`。  
   `toon.frag` / `toon_hair.frag` / `toon_eye.frag` / `toon_face.frag` / `pbr.frag`，共享 `common.glsl` 的光照结构、阴影、IBL、雾。  
   每个文件只保留**自己需要的少数开关**（如 `toon.frag` 只需 RAMP / OUTLINE_MASK / ALPHA 三位 = 8 组合）。
2. **变体表从"全组合"改为"显式白名单"**，由材质实际用到的组合惰性编译或构建期枚举，而不是 `1 << N` 全开。
3. **Permutation Domain**：把关键字分成互斥组（`ShadingModel` / `AlphaMode` / `Features`），组合数是**各组之和**而不是**乘积**。UE5 的 `FMaterialShaderPermutationParameters` 就是这套。

**验收判据（可自动化）：** `ls build/bin/shaders/*.spv | wc -l` 必须 < 300，且新增一个着色模型只增加 ≤ 8 个 .spv。

**✅ 已完成（2026-10-25 晚）—— 见 §7。** 实测：`pbr.frag` 族 **128 → 60 份**，  
全仓 .spv **190 → 182**，体积 **11 MB → 9.8 MB**；`Toon` 作为第三档着色模型  
已经跑通（`bit6`），按新机制再加 `hair/eye/face` 三个模型从 1024 份降到 96 份  
（差 10.7 倍）。上面那条验收判据已经满足。

---

### B. 材质是"单层 PBR 参数包"，承载不了二次元的多层脸

**证据（`engine/assets/Material.h` 全字段已逐个核对）：**

| 缺什么                                    | 为什么二次元必须有                                                                                          |
| -------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `sortPriority` / `renderQueue` / layer | 全字段无（grep 0 命中）。二次元的脸 = 脸皮 + 眼球 + 虹膜 + 睫毛 + 眉毛 + 腮红 + 口内，**靠固定绘制顺序叠加**，不靠深度。这是 MToon/URP Toon 的第一课 |
| 第二套 UV                                 | 顶点只有一套 `glm::vec2 uv`（`engine/assets/Mesh.h:25`，6 个属性已用满 location 0~5），面部 SDF 阴影贴图必须独立 UV          |
| ramp 贴图槽                               | 7 个贴图槽里没有（`Material.h:103-148`：albedo/normal/orm/roughness/metallic/emissive/height）               |
| 描边颜色 / 宽度                              | 结构体无相关字段                                                                                           |
| 高光遮罩（spec mask）                        | 只能借 `roughnessMap` 间接控制                                                                            |
| MatCap 槽                               | 无                                                                                                  |
| 发光强度独立倍率                               | `emissive` 是 vec3，无 `emissiveStrength`（glTF 有此扩展，未接）                                               |
| 着色模型只有两档                               | `enum class ShadingModel { Default, Skin }`（`Material.h:90`）                                       |

**更麻烦的一处**：`.vmesh` 格式**不存 `alphaMode`**，导入材质一律硬写 `opaque`（`engine/assets/MaterialImport.cpp:481-486`）。项目自己的文档已经记录了这个后果：

> `docs/alicia_import.md:367-368`："`.vmesh` 没有 alphaMode、导入的材质一律 Opaque，于是**眼睛被脸皮整片挡住**"  
> `docs/alicia_import.md:374-375`："正确修法是给 .vmesh 加 alphaMode / 描画顺序……不在这一刀的范围里"

也就是说：**当前引擎连"给角色一张正常的脸"这件事都做不到**，只能靠把眼睛做成独立实体手动调深度。这是二次元角色的第一道门槛。

---

### C. 角色管线是"一个 Model = 一套骨架 + 一段 clip"，没有表演层

**证据：**

- 一个实体只有一份 `SkinnedMeshComponent`（单 `model` + 单 `jointMatrices`），一个 `Model` 只有一个 `std::shared_ptr<Skeleton>`（`engine/assets/Model.h:41-48`、`engine/ecs/Components.h:118-141`）
- 顶点固定 4 骨、80 字节、6 属性（`engine/assets/Mesh.h:22-42`），**没有形态键通道**
- `Skeleton` 无 `findJoint` / `jointByName`（只有 `findClip`，`Skeleton.h:76-80`）→ **无法做挂点**
- `AnimatorSystem` 只做"采样 + 双 clip crossfade"，**无骨骼后处理阶段**（`AnimatorSystem.cpp:180-224`）

**后果：** 加不了表情、挂不了武器/发型、做不了头发弹簧骨、做不了看向。这些不是"锦上添花"，是二次元角色的日常。一个不能换发型、不能做表情的角色，做不出任何剧情演出。

**2026-10-25 部分落地（见 §9）：** `AnimatorSystem` 在 `samplePose` 与
`poseToJoints` 之间开了一个 `applyPerformance()` 阶段，L4 弹簧骨（头发/裙摆）
与 L2 LookAt（单骨看向）已经能跑。**仍是"一段 clip"**：状态机、分层遮罩、
表情三层都还没有，`animator` 组件上那七个占位字段只是从"看起来能用"
变成了"显式标灰"。`Skeleton` 上**仍然没有** `findJoint` —— 两个新模块都是
自己做一遍 O(n) 名字扫描，等第三个消费者出现时再抽出公共函数（现在抽
等于为两个调用点设计 API）。

## 6 · 一个需要明确的产品决策

引擎当前在**渲染质量**上的投入（TAA/SSGI/SSR/体积雾/Hi-Z/POM/面积光）已经**远超**一款二次元游戏的画面需求，而 **NPR/表演层**是一片空白。这不是技术判断错误，是**目标漂移**：过去几轮的优化目标实际上是"做一个高质量通用渲染器"。

如果定位真的是"专门开发二次元游戏"，那么接下来 6 个月的投入重心应该从"渲染真实度"整体平移到"角色表现力 + 演出工具链"，并且**接受 NPR 会主动放弃物理正确性**（Toon 的阴影色不是算出来的，是美术指定的；脸上不能有 PBR 的菲涅尔边缘光；角色不该被环境色污染）。

**这两件事在着色器里是无法共存的** —— 同一个材质要么走 PBR 分支要么走 Toon 分支。这就是为什么 P0-1（变体拆分）必须排在第一位：它不只是性能优化，它是"两种世界观能否在同一引擎里共存"的架构前提。

## 7 · 本轮实际落地（2026-10-25）：P0-1 变体白名单 + A1 赛璐璐

### 7.1 机制：位宽 ≠ 组合数

旧机制把两件事绑死了：`kKeywordCount`（位宽）既决定掩码空间，又决定
`foreach(MASK RANGE 0 .. 1<<N)` 编多少份。于是"多一个关键字"= 组合数**翻倍**。
新机制把两者拆开：

| 概念 | 谁决定 | 值 |
|---|---|---|
| 位空间（掩码能表示哪些开关） | `ShaderKeywords.h` 的 `kKeywordCount` | 7（bit0~bit6） |
| **实际编哪些组合** | `CMakeLists.txt` 的分组白名单 | 60 份 |

白名单是**按着色模型分组**写的（`SHADING_MODELS` / `GROUP_alpha` /
`FEATURES_<model>` / `SHADER_MODELS_<file>`），组合数是

```
Σ_模型 (alpha 取值数 × 2^该模型自己的特性数)
= pbr(3×8) + skin(3×8) + toon(3×4) = 24 + 24 + 12 = 60
```

不是 `2^7 = 128`。关键在于 `FEATURES_toon` **只有 2 项**（不要 POM）——
每个模型只为自己真正需要的开关付钱。

编译期还有一道 `static_assert(kKeywordCount == VENN_KEYWORD_COUNT)`：C++
侧和 CMake 侧的位宽只要差 1，configure 当场失败，而不是等到运行时
掩码越界去读别的变体。

### 7.2 实测数字

| 指标 | 改造前 | 改造后 |
|---|---|---|
| `pbr.frag` 族变体 | 128 | **60** |
| 全仓 `.spv` | 190 | **182** |
| `.spv` 总体积 | 11 MB | **9.8 MB** |
| Toon 族掩码 | —— | 64,65,66,67,68,69,70,71,72,73,76,77（12 份） |
| 未来加 hair/eye/face 三模型 | 2^10 = 1024 份 | **96 份**（差 10.7×） |

**零行为变更的证据**（`tools/verify_shader_variants.py`）：
`MYVK_SHADER_FORCE_MASK=0` 与 `=4`（NORMAL_MAP）逐像素比对，**最大差 1 LSB、
均值 0.1293、>18 的像素数为 0** —— 是"等价"，不是"看起来差不多"。

白名单外的组合（例如 `ALPHA_BLEND | ALPHA_MASK` 这种语义上互斥的掩码）
在 configure 阶段就会被 `file(REMOVE)` 清掉，避免运行时静默读到**过期字节码**
（这是改造过程中真实踩到的坑：`add_custom_command` 只生成不删除，
旧的 144 份 pbr 变体留着，编辑器读到的仍是上一版着色器）。

### 7.3 A1：`ShadingModel::Toon`（bit6）

用来证明"新机制真的能装 NPR"。三条改动全在 `pbr.frag` 的
`toonDirect()` 里：

1. **半兰伯特 + 两档量化**：`smoothstep(0.47, 0.53, N·L*0.5+0.5)`。
2. **暗部 = 基色 × 冷色调**（`0.45,0.49,0.62`），不是"乘个小数变暗"。
3. **阈值化硬高光**（`pow(...,48)` 再过 `smoothstep(0.88,0.93)`）。

实施过程中踩到两个**只有像素证据才能发现**的错：

- **背光面被阴影项清零**。`shadowFactor()` 在 `N·L <= 0` 时直接返回 0
  （写实渲染里这是对的），而赛璐璐的暗部是一笔**颜料**。整项乘 `shadow`
  → `mix(dark, lit, band) * 0 == 0` → 球的下半部三通道全 0，与写实 PBR
  的暗部**完全一样**，"冷色阴影"在像素上等于不存在。
  修法：`mix(dark, lit * shadow, band)` —— 阴影只衰减**受光档**。
- **交界处没有台阶**。修完上一条后又出现反向问题：`lit` 在 `ndl≈0` 处
  是 `0.55·albedo`，暗部色 R 通道是 `0.52·albedo` —— 两者几乎相等，
  明暗交界线消失，整颗球看着像"均匀受光 + 稍微发蓝"。把亮档抬到
  `0.80~1.00`、暗档压到 `0.45~0.62` 才有 1.78× 的可见台阶。

另外 IBL 给的中性天光（约 +0.14 线性值）会把暗部冷色冲淡（实测 B/R 只有
1.07，线性理论值 1.38），所以 Toon 变体里**环境光也跟着亮暗分档**压一次
（`ambient *= mix(vec3(0.66,0.72,0.90), vec3(1.0), band)`）。写实路径不动。

**验收**（`tools/verify_toon_shading.py`，已登记进 `run_regression.py`）：

```
第 1 组  变体路由：default→k0 / skin→k16 / toon→k64，且不存在 skin+toon 共存
第 2 组  亮度标准差：default 18.4 / skin 18.2 / toon 25.8（+41%）
第 3 组  暗部：default R=0.0（死黑）/ toon R=151.5、B/R=1.108
```

### 7.4 顺带发现（已记为 P1-13）

球体是最坏的"掠射角自遮挡"场景。做 Toon 之前，`Default` 的明暗是连续
渐变，阴影图 PCF 的台阶被藏在渐变里看不见；一变成二值交界，交界线外侧
立刻露出约 8 px 宽的台阶状锯齿。**NPR 会让阴影图的分辨率/偏置缺陷无处可藏**，
这不是 Toon 的 bug，是它把已有缺陷放大了。

| **A** | 同像素叠加：SDF 阴影 / ramp / 腮红贴花 / 眼睛 matcap | 不参与（在着色器里做完） | 通道 ✅（§12）；SDF 算法待做 |
| **B** | 跨网格叠放：眉 / 睫 / 眼 / 发 vs 脸皮 | 参与，且**语义优先于距离** | ✅ 本轮 |
| **C** | 部件是 Opaque 还是 Blend | 间接参与（决定写不写深度） | ✅ 本轮 |

混在一起做的后果很具体：只加 `renderQueue` 不加 A 类槽位，SDF 阴影还是无处存；
只加 A 类槽位不加排序，眼睛还是被脸皮挡死。

### 8.2 三条 GPU 通道已经全部占满（这是方案不能绕开的硬约束）

| 通道 | 现状 | 还能加吗 |
|---|---|---|
| `PushConstants` | **恰好 128 字节**（`RenderTypes.h:257`），Vulkan 保证的下限 | ❌ 唯一空着的 4 字节是 `emissive.w`，已被 bindless 页号占用 |
| 纹理 set | `kTextureSetCount = 7`，set0 + 7 = **8** = `maxBoundDescriptorSets` 的规范下限 | ❌ 非 bindless 路径加不了第 8 张 |
| `GpuMaterialPage` | ~~32 字节~~ → **96 字节**（6×16B），12 个语义槽用了 11 个 | ✅ **已扩**（§12，2026-10-25） |

结论：**A 类只能走 bindless 页表扩容**。非 bindless 路径在结构上已经封死。
这是"事先查过通道"的价值 —— 否则会先设计一套漂亮的参数结构，写到一半发现没地方放。

> **2026-10-25 追记**：第三行的 ✅ 已经兑现，见 §12。前两行的 ❌ 没变，
> 而且这一轮的 rampMode 三态就是被它们逼出来的 —— 因为 push 里连一个
> `float` 都塞不进去，"有没有挂 ramp"这个开关只能塞进页表的一个 float 分量。

### 8.3 B 类：三键排序 + 覆盖带

```cpp
// Material.h
std::int32_t renderQueue = 2000;   // 主键：属于哪个"带"
std::int32_t sortOrder   = 0;      // 次键：同带内微调
static constexpr std::int32_t kOverlayQueueStart = 3000;
bool isOverlay() const { return renderQueue >= kOverlayQueueStart; }
```

排序键 `(renderQueue, sortOrder, -viewDepthSq)` + `std::stable_sort`。
**默认 2000/0 让三键退化成单键** —— 玻璃/烟雾/既有场景一分不变。

覆盖带（`>= 3000`）的管线状态：`depthTest = false`（= `VK_FALSE`，片元全通过、
且完全不读深度缓冲）+ `depthWrite = false`。

为什么必须放弃深度裁决：**二次元的眼睛是凹在眼窝里的**，深度值比脸皮大；
眉毛被刘海盖住，物理上前者一定在后。用 `LEQUAL` 永远不会出现，用"关掉深度测试"
才会出现。这不是偷懒，是这个行业的通行做法。

参考带序（美术起点，**不是引擎规则**）：

```
1900 天空   2000 身体/衣服   2400 脸皮   2900 后发
3000 前发   3100 眼白+虹膜   3200 睫毛   3300 眉毛   3400 腮红/贴花
```

注意**头发(3000) 必须小于眼睛(3100)** —— 二次元的眼睛要压在刘海上。
"按部件类别自动分类"行不通就是这个反例：头发既要在脸之后、又要在眼睛之前，
任何类别枚举都表达不了。所以顺序只能由美术手填，引擎只保证"升序绘制 + 稳定"。

### 8.4 `VENN_OVERLAY` 是个**纯状态位**，不增一份 `.spv`

它不改变任何一行片元代码，只改 `depthTest` / `depthWrite`。所以：

- 进 `SHADER_KEYWORDS`（位宽 7 → 8，`kKeywordCount = 8`）
- **不进任何 `FEATURES_<model>`** → 白名单不变 → 组合数仍是 60
- `VariantPipelines` 里 `m_spvMask = kKeywordAll & ~kKeywordStateOnly`，
  拼文件名时用 `key & m_spvMask` → 缓存键里有 bit7（不同深度状态要不同管线），
  文件名里没有（字节码相同）

这是 P0-1 那次改造"位宽 ≠ 组合数"的**第二个应用场景**（第一个是白名单）。
60 份变体覆盖 120 条管线，零 .spv 增量。

### 8.5 P0-3：alphaMode 进资产

真相比审计时写的更彻底：`assetio::SourceMaterial` 里**连这个字段都不存在**。
所以 FBX 解析器无从写入、`.vmesh` 无从存储、运行时一律 Opaque。

修法：

1. `SourceMaterial` 加 `AlphaMode{Opaque,Mask,Blend}` + `alphaCutoff`
2. `.vmesh` 材质段 `v1 → v2`，**末尾追加**两个字段；读端 `if (matVersion >= 2)`
   → 版本 1 的旧资产读成 Opaque，**不需要重烤**，行为与改造前一致
3. FBX 两条导入路径用同一套判据推 `Blend`：`pbr.opacity` 挂了贴图 /
   `features.opacity.enabled && value < 1` / `fbx.transparency_factor < 1`

⚠ 只推得出 `Blend`，推不出 `Mask`。FBX 没有"alpha test"这个概念，镂空是靠
贴图 alpha 做的；该走 Blend（边缘软、必须排序）还是 Mask（不混合、能写深度、
边缘硬）是**美术意图**，不该由导入器替人决定 —— 默认给 Blend，要 Mask 在
Inspector 改。

⚠ 这条**不修**"眼睛被脸皮挡住"。眼睛是不透明的，它出不来是因为脸皮先写了
深度。那条的正解是 B 类覆盖带。这里修的是另一件事：半透明睫毛/发片/树叶
被强制成不透明。

### 8.6 验收：`tools/verify_render_queue.py`（已登记进 `run_regression.py`）

用两颗球构造一个"物理上一定被挡住、语义上一目了然"的局面：近球（红）直径 8
在 t=34，远球（绿）直径 8 在 t=48，同心 → 远球投影完全落在近球轮廓内。

| 组 | 近球 rq | 远球 rq / order | 绿色占比 | 结论 |
|---|---|---|---|---|
| 1 | 2000 | 2000 / 0 | **0.000** | 默认行为不变，近球在上 |
| 2 | 2000 | 3100 / 0 | **0.994** | 覆盖带的远球穿透近球 |
| 3 | 3000 | 3100 / 0 | **0.994** | 顺序只看数值，不看距离 |
| 4 | 3100 / 5 | 3100 / 0 | 0.000 | 反向 sortOrder 后近球回到上面 |
| 4b | 3100 / 0 | 3100 / 5 | 0.994 | sortOrder 大的在上面 |

第 1 组和第 2 组的唯一差别是 `renderQueue`，其它字节完全相同 ——
这是"renderQueue 真的在控制绘制顺序"最干净的证据。0.000 vs 0.994 之间
不存在"看起来差不多"的灰区。

零回归：`verify_shader_variants` 全 PASS（含 `FORCE_MASK=0 vs 4` 的 LSB 对照）、
`verify_alpha_mask` 5 组全 PASS、`.spv` 仍是 182 个。

### 8.7 踩坑

- **把远球沿 +Z 往后挪是错的**。机位是斜的（下俯 16°），沿 Z 后退会让球
  **偏离视线**（实测偏 10.7 世界单位，球径只有 8），只露出边缘一条 →
  绿色占比 0.111。既不像 PASS 也不像 FAIL，看着像"覆盖带只生效一半"。
  正解是沿**视线方向**取坐标，或者干脆把 pitch 设为 0。
- **采样区不能用视口中心**。实测近球心比视口中心**偏上 52 px**（球心 y=360、
  视口中心 y=412）。用视口中心切 0.25 倍的块，下半截越界压到红环上 →
  同样是 0.614 那种"半对半错"的假象。改成从第 1 组的红球轮廓反推球心。
  教训与 verify_toon_shading 那次一致：**判据没错的时候，先怀疑几何**。
- **`MYVK_SHADER_FORCE_MASK` 不能影响绘制顺序**。队列分类一开始读
  `it.keywords`（= `effectiveKeywords`），而那个函数会被强制掩码整个替换 →
  一旦场景里有 overlay 材质，`verify_shader_variants` 的像素对照比的就
  不是同一个绘制顺序了。改成直接读 `mat->isOverlay()`。
- **overlay 项必须 `skipDepthPrepass`**。覆盖带的意义是不被深度裁决；
  让预通道把它的深度写进去，后面的透明物体会拿它去做 early-Z，
  睫毛/眉毛会被当成实体几何把身后的东西剔掉。

### 8.8 已知局限

覆盖带用 `depthTest = false` → overlay 项无条件画在已画内容之上，**包括它
物理上真该被挡住的地方**（侧脸时脸颊凸起挡住眼球边缘）。更精细的做法是保留
`LEQUAL` + 给这些顶点一个深度偏置（`depthBias`），那需要 `PipelineDesc` 再加
一个字段。先接受，等真在某个资产上看到问题再做。

## 9 · 本轮实际落地（2026-10-25）：C 类"表演层"第一刀 —— L4 弹簧骨 + L2 LookAt

### 9.1 先把"表演层"拆开：它不是一层，是五层正交的东西

原审计里 §1.C 写的是"一个 Model = 一套骨架 + 一段 clip，没有表演层"。
这句话对，但它把五件互不依赖的事捆成了一个词。拆开之后才看得出先做哪件：

| 层    | 内容                       | 输入                        | 典型实现                          |
| ---- | ------------------------ | ------------------------- | ----------------------------- |
| L0   | 驾驶层（状态机）                 | 输入意图 / 速度 / 落地            | 状态图 + 转移条件 + 混合时间             |
| L1   | 合成层（分层遮罩）                | 多段 clip + 骨骼遮罩            | upper/lower body 分开采样再合并      |
| L2   | 修正层（LookAt / IK）          | 目标点 / 地面 / 手部目标          | 骨骼后处理：改朝向、改终点                 |
| L3   | 表情层（BlendShape）           | 表情权重                      | 顶点形态键（要动顶点格式）                 |
| L4   | 次级运动层（弹簧骨）               | 父骨运动 + 重力 + 风             | Verlet 质点链 + 距离约束             |

关键观察：**这五层的流水线插入点是同一处** ——
`采样 → 混合 → 遮罩 → IK → 根运动提取 → 局部转世界 → 乘 invBind → 上传`
（`docs/character_pipeline_roadmap.md` §3.2 写死的那条）。
所以先落一层不等于以后要返工，插入点是稳定的。

### 9.2 为什么先做 L4 + L2，而不是 L3 表情

按"收益 × 成本"排，不是按层号排：

| 层 | 收益 | 成本 | 判断 |
| -- | ---- | ---- | ---- |
| L4 弹簧骨 | 高（角色立刻"活"） | **极低**：零资产改动、纯 CPU、不进顶点格式 | ✅ 先做 |
| L2 LookAt | 中高（眼神有交流感） | 低：单骨后处理，同样零资产改动 | ✅ 先做 |
| L0 状态机 | 高（能做玩法） | 中：要设计数据格式 + 编辑器 UI | 下一步 |
| L1 遮罩 | 中 | 中：要按骨骼子树维护遮罩掩码 | 之后 |
| L3 表情 | **最高**（二次元的脸就是表情） | **最高**：动顶点格式（P0-5），资产管线全链要改 | 必须和 P0-5 一次改对 |

L4 的成本之所以是"极低"，只有一条理由：**它靠骨骼名前缀识别链**，
`.vmesh` 不升版本、模型不用重烤、美术不用改命名规范（不合规时在组件上手填前缀）。
L3 之所以必须往后放：它和 P0-5（顶点格式已用满 6 属性）是同一件事，
做早了要改两遍。

### 9.3 弹簧骨：判据比算法难

算法本身是教科书内容（Verlet + `iterations=3` 的距离约束 + 指数回弹）。
真正决定"能不能用"的是**怎么从 128 根骨里找出该飘的那 27 根**：

- 自己匹配前缀 **且** 父骨也匹配 → 参与模拟
- 自己匹配、父骨不匹配 → attach（固定端，受动画驱动，物理不碰）

这条判据让"缝在 head 上的第一根头发骨"自动成为固定端，不需要在资产里额外
标注锚点。`hair1_L`（父骨是 `head`）→ attach；`hair2_L..hair4_L` → 模拟。

实测：`alicia.vmesh` 128 根骨里识别出 **27 根**（头发 4 链 × 左右 + 裙摆），
日志锚点 `ANIM-SPRING-RIG bones=27 joints=128 prefixes=[<default>]`。

`SpringRig` 按 `(Skeleton*, prefixes)` 缓存，**必须是 `std::map` 不能是
`unordered_map`** —— 返回的是引用，rehash 会让它悬垂。

### 9.4 LookAt：必须在父骨空间算

如果直接在骨架空间把 head 的朝向指向目标，转身时头会"拧在原地"（世界朝向
不变但身体转了）。正确做法是把目标点变换到**父骨空间**再算局部旋转。

另外 `shortestArc()` 要处理反向 180°（`cross` 退化 → NaN），且 `angleDeg()`
要用 `|q.w|` 而不是 `q.w`（`q` 与 `-q` 是同一个旋转，符号取决于构造路径）。

### 9.5 顺带修掉的"假开关"

审计里最刺眼的其实不是"缺什么"，而是**`animator` 组件上那七个字段没有
运行时消费者**：`controllerPath` / `stateIndex` / `floatParams` / `triggerParams` /
`rootMotion` 进了序列化、Inspector 有控件，全仓 grep 找不到读它的地方。
用户点得到、存得下、跑起来什么都不发生 —— 这比"没有这个功能"更伤信任。

本轮处理：`ImGui::BeginDisabled()` 标灰 + 一句提示
（"Greyed out = the field exists but nothing reads it…"）。
**没删**，因为删了以后加状态机要重新设计一遍字段和存档兼容；
**没留成可用态**，因为那是骗人。

### 9.6 验收

`tools/verify_anim_runtime.py`：**42 项全 PASS**，其中 15 项本轮新增
（`spring_*` 8 项、`lookat_*` 6 项、`spring_integration_first_frame`）。
已登记进 `run_regression.py` 的 `TRIGGERS`，并把
`engine/scene/SceneSerializer.*` 加进依赖 —— 序列化段落写错的表现是
"存盘再开头发不飘了"，而动画自检看不到。

真实资产端到端（一次性探测，**未进回归**）：`alicia.vmesh` 在运行时
`SCENE-SPRINGBONE` → `ANIM-PERF spring=1` 持续输出；A/B/C 三图对比

| 组 | 设置 | 与 baseline 的像素差（人物区域） |
| -- | ---- | ------------------------------ |
| ① | 无弹簧骨 | — |
| ② | 弹簧骨，无风 | `mean=7.17`，`>24` 占 6.2% |

### 9.7 踩坑

- **默认前缀不能带分隔符**。第一版写的是 `hair_` / `hair.` / `skirt_` / `tail`，
  在真实资产上**一个都没匹配到** —— alicia 的头发骨叫 `hair1_L`，下划线在
  数字后面。改成裸 `hair` / `skirt`。也**不放 `tail`**：人体骨架里 `tail`
  通常指尾椎（tailbone），会把脊柱弄软。
- **编辑器非 Play 态传的是 `dt = 0`**，弹簧骨永远不动。日志症状极具迷惑性：
  `ANIM-TICK f=1 … dt=0.00000` 且 **只有 f=1 一条**（编辑器加载完只跑一帧就
  停在那儿等交互）。修法是 `physDt = (dt > 0) ? dt : m_wallDt`，
  `m_wallDt` 来自 `steady_clock` 并 `clamp(0, 0.05)`：Play / 自检走 `dt`
  （确定性优先），编辑器非 Play 走真实帧间隔。
- **手写场景 JSON 的 `skinned` 块不会建出子网格渲染实体**。它只建
  `SkinnedMeshComponent`（骨骼、clip、`ok=1` 全对），但角色的 20 个子网格
  是 `instantiateModel` 建的。症状是视口一片空白，而
  `CULL-STATS renderables=1 tris=2` —— 那"1 个"是地面。**判据看
  `renderables` 和 `tris`，不要看有没有报错**（一个错都没有）。
  要看角色必须走 `ModelInstance` 那条路：运行时 `createPlayer`、
  编辑器拖入、或 `MYVK_EDITOR_IMPORT`。
- **运行时跑不出表演层，是因为 `Game.exe` 是旧的**。改了 `engine/animation/`
  只重编 `VennEditor` 会得到一个错误结论："运行时没有表演层"。
  `msvc-build.cmd build <target>` **只吃第一个 target**，三个要分开跑。
- **只有 skinned 实体的场景会踩 BVH 越界**（`std::vector<scene::Bvh::Node>`
  的 `operator[]`）。加一块静态地面就绕开了。对照组（关掉弹簧骨）同样崩，
  证明与本轮无关 —— 但它值得单独记一笔。

### 9.8 已知局限 / 下一步

- **没有碰撞体**。头发会穿过肩膀和胸口。下一步最该做的是给 `SpringRig`
  挂几个球（肩、胸、头的包围球），在距离约束之后再做一次"点推出去"。
- **只有一条链的朝向修正，没有扭转修正**。`shortestArc` 只纠正指向、
  保留绕骨轴 roll，所以发束自身不会扭转。
- **`applyPerformance` 是逐实体单线程 CPU**。27 根骨 × 3 次迭代在 alicia 上
  可忽略，但同时 20 个角色时该考虑合并成一次批处理或搬到 compute。
- 顺序上接下来是 **L0 状态机**（`Locomotion` 里已经有 idle/walk/run/jump 的
  雏形，缺的是"把 `animator` 那七个占位字段接上"），再往后是 L1 遮罩，
  最后 L3 表情和 P0-5 一起做。

## 10 · 本轮实际落地（2026-10-25，第二刀）：L0 状态机 —— 把"假开关"接成真的

### 10.1 为什么 L0 排在 L2/L4 之后而不是之前

§9 的收益×成本表把 L0 排在"下一步"，理由不是它不重要（它最重要 ——
不做状态机，做十个动作也串不成玩法），而是**它复用现成结构，成本本来
就低**，先做哪一刀取决于"能立刻消除多少不信任"。

§9 做完 L4+L2 之后，`animator` 组件上还剩七个字段全是占位。这一刀把
其中**五个**接上了：

| 字段 | 之前 | 现在 |
| --- | --- | --- |
| `controllerPath` | 序列化 + Inspector 控件，**全仓无读取者** | `AnimatorSystem::tick` 加载并每帧推进 |
| `stateIndex` | 只在 Inspector 里 `TextDisabled` 显示 | 状态机真正读写（`-1` = 未初始化） |
| `stateTime` | 同上，恒 0 | 每帧 `+= dt`，`hasExitTime` 靠它判 |
| `floatParams` | 三张空表，没有任何条件读它们 | 转移条件的数值输入（`Speed`） |
| `boolParams` | 同上 | 转移条件的布尔输入（`Grounded`） |
| `triggerParams` | 同上 | 一次性事件，被采纳后**立即清零**（`Jump`） |
| `rootMotion` | 占位 | **仍是占位**（A4），Inspector 继续标灰 |

### 10.2 接线位置：为什么在"取 clip 指针"之前

```
① 补 defaultClip
② 状态机推进          ← 这里
③ 取 clip 指针 / 推进 time / 镜像
④ 采样 → 表演层 → 关节矩阵
```

放第 ③ 步之后的话，状态机这一帧改了 `clipName`、而采样还在用旧的那段 ——
症状是"切状态慢了整整一帧"，只在 `ANIM-FADE` 的 `begin from=` 上看得出来。

### 10.3 三条硬语义（少一条就从"能用"变成"看着像 bug"）

1. **trigger 被采纳后立即清零。** 不清的话 `Any → Jump` 在回到 Idle 的
   下一帧又成立 → 角色无限起跳。这是状态机最经典的一个 bug，也是本轮
   唯一专门写了"再跑 5 帧不许重入"断言的。
2. **每帧最多采纳一条转移。** 允许一帧连转时，多个条件同时成立会跨过
   中间的过渡时长，肉眼是"直接弹到终态"。
3. **`dt == 0` 不推进 `stateTime`，但必须完成初始化。** 编辑器非 Play 态
   传的就是 `dt = 0`。只做"不推进"而不做"初始化"的话，打开场景看到的是
   `defaultClip` 定住的姿势，而 Inspector 显示 `state=Idle`
   （症状：视口是 Walk、面板说 Idle）。

### 10.4 与 `Locomotion` 的分工：谁写 `clipName`

两条路径**互斥**，由 `controllerPath` 是否为空决定：

- 空 → `Locomotion`（硬编码四态，P4 的行为，**逐位不变**）
- 非空 → 状态机接管，`RuntimeApp::tickPlayerAnimation` 与编辑器 Play 都
  **直接 return / 走 else 分支**，不再调 `updateLocomotion`

⚠ 两者同时写 `sk.clipName` 的话每帧互相覆盖，症状是"角色在两个动作之间
高频抖动"，而两边的日志都正常 —— 所以这条互斥是硬约束，不是优化。

⚠ 编辑器那段**不能用 `continue`** 跳过 `updateLocomotion`：后面紧跟着相机
更新，`continue` 会把相机一起跳过（画面卡住但动画正常，比抖动更难查）。

### 10.5 参数名是"约定"，不是"映射表"

引擎侧写死三个名字：`Speed`(float) / `Grounded`(bool) / `Jump`(trigger)。
控制器资产按这三个名字声明参数就能被喂到。

为什么不做映射表：多一层映射的结果是**每个工程的每份控制器都要额外配
一遍**"我的 Speed 叫 V"；而真正的差异（走跑分界在哪、起跳要不要看贴地）
本来就在控制器的转移条件里 —— 那才是该写的地方。控制器没声明这三个参数
时，喂进去的条目不会被任何条件读到，是死数据（无害，但 Inspector 的参数
黑板会显示出来，便于发现"名字拼错了"）。

### 10.6 顺带解决的三件事

- **`physics::stepCharacter` 的 `jumped` 从"只有自检读"变成运行时也有消费者**
  （`PlayerController::justJumped()`）。这里有个坑：**不能**用
  `!onGround` 代替"起跳"——走下台阶也是 `onGround` 变 false，那会把踏空
  当成起跳，动画会无缘无故播跳跃。
- **`switchClip` 从 `Locomotion.cpp` 的匿名 namespace 抽到
  `animation/ClipSwitch.*`**。状态机是第二个消费者，而这段逻辑错一处只
  表现为"过渡看起来怪"（不报错、不崩、日志正常）。两个消费者各抄一份的话，
  调手感时必然只改到一份，症状是"走路顺、按 K 起跳怪"。
- **`assets/animators` 进 `CMakeLists.txt` 的"每次都拷"档**。不加的话
  控制器只存在于源码树里，`build/bin` 里没有 → 运行时打
  `ANIM-CTL-BAD ... 打不开文件`。这条报错**指名道姓写出绝对路径**，
  正是因为设计时预期"配错路径是常态"。

- **`"from": "Any"` 被当成状态名去找**，找不到 → 整个控制器判无效 →

  看起来像用户配错，实际是解析器不认识自己的 schema。第一次跑自检时
  8 条断言一起红，就是这一条。
- **状态机初始化会 `switchClip(..., restart=true)` 把 `an.time` 归零**。
  写"相位连续"的断言时先手动设 `an.time = 0.5`，那一帧就被清掉了
  （`actual=0`）。正确顺序是先跑一帧让它初始化，再设播放头。
- **`stepAnimController` 不推进播放头**，推进是 `AnimatorSystem::tick` 的活。
  断言里期望 `1.001`（含 dt）是错的，应当是 `1.000`。分工写在两个文件里，
  写测试时最容易混。
- **日志锚点前缀重复**：`stepAnimController` 的 tag 传 `"ANIM"`，格式串里
  又写了 `%s-ANIM-STATE` → `ANIM-ANIM-STATE`。格式串改成 `%s-STATE`，
  于是 tag 语义与 `Locomotion` 的 `GAME` / `EDIT` 一致（谁在驱动）。
- **`assets/animators` 没进 CMake 的复制清单**，`build/bin` 里没有控制器，
  运行时直接报打不开。这类"新资产目录"每次都要动 `CMakeLists.txt`，
  漏了的表现是"编辑器（源码树 cwd）能跑、Game.exe 不行"。

### 10.9 已知局限 / 下一步

- **没有分层与遮罩**（P2-2）。上半身挥手 + 下半身走路仍然做不了。
  数据格式上要先定 `BoneMask`（骨骼名列表 / 前缀通配），再定层顺序。
- **没有动画事件**（P2-3）。脚步声、命中帧、特效帧都还挂不上。事件的正确
  位置是**控制器资产里按 clip 名索引**（不是 `AnimationClip` 里 —— clip 是
  共享资产，改它会污染所有用它的角色；而同一个 Walk，胖瘦角色的脚步帧
  本来就不同）。
- **没有 root motion**（`rootMotion` 仍是唯一标灰的字段）。它与
  `CharacterController` 有一个必须写死的契约：`FromClip` 模式下控制器
  必须把水平速度清零，否则"动画走 1 米 + 代码走 1 米 = 2 米"。
- **没有 Animator 面板**（A7）。现在只能手写 `*.anim.json` + Inspector 里
  填路径。可视化的状态机图要等 schema 彻底定稿再做 —— 否则等于把 schema
  焊死在 UI 里。
- **`Any` 转移的优先级只由数组顺序决定**，没有显式的 priority 字段。
  schema 里曾经想加（示例 JSON 里一度写了 `"priority": 10`），但解析器
  不读它 —— 那比没有更糟（写了以为生效）。所以删掉了，统一按数组顺序。

## 11 · 本轮实际落地（2026-10-25，第三刀）：P1-2 描边 —— 不加一遍几何的做法

### 11.1 为什么不用 inverted hull

roadmap 和 §5 里给的正解一直是 **inverted hull**（正面剔除 + 沿"平滑法线"
外扩 + 视距补偿宽度）。这一刀**没有**走那条路，理由是三条成本，不是审美：

| 代价 | inverted hull | 后处理边缘检测（本轮） |
| ---- | ------------- | ---------------------- |
| 几何 | **再画一遍**所有要描边的物体 | 0（复用已有的深度预通道） |
| 顶点数据 | 需要**平滑法线**（平均过的第二套法线）→ normal 已占 location 1，只能动顶点格式或加第二张图 | 0 |
| 逐物体开关 | 材质/顶点色写掩码，天然支持 | 需要一个"要不要描"的输入（还没有，见 §11.9） |
| 线宽 | 天然均匀（沿法线外扩固定的世界距离） | 天然是像素宽度，远处会变细 |

关键的取舍是第二条：**顶点格式已经被用满**（position / normal / uv /
joints / weights / color 六个 location），P0-5（BlendShape）本来就要动它。
为了描边先动一次、为表情再动一次 = 改两遍。而 P0-5 那次必须一次改对。

反过来，后处理路线的**全部**成本只有：预通道多写一个颜色附件 + post 里
9 次纹理采样。而它顺带把"深度 + 法线"这两张图交到了后处理手里 ——
以后的 SSAO / DOF / 线宽视距补偿 / 色调分离全都吃这一份。

### 11.2 为什么挂在深度预通道，而不是新开一个几何 pass

深度预通道本来就把**不透明几何完整画过一遍**（early-Z 的前提）。
新开一个 pass 意味着顶点 + 光栅化成本翻倍；挂在这里只多一个 4 通道的
`R16G16B16A16_SFLOAT` 写（8 B/sample，与 HDR 同量级）。

改动因此只落在三处：`HdrTarget` 的预通道 renderpass 多两个附件
（多采样 + resolve）、`depth_only.frag` 多一个输出、`Renderer` 的
clearValueCount 从 1 变 2。

⚠ **`depth_only.frag` 没有独立的 vert —— 它复用 `pbr.vert`**，而
`pbr.vert` 早就输出了 `vNormal`（世界空间法线，location 1）。所以片元
里那一行 `normalize(vNormal)` 是**白拿**的，不需要给预通道单独写一套
蒙皮/变换代码。这也是"预通道的顶点变换必须与前向逐位一致"那条纪律的
附带红利。

### 11.3 为什么 a 通道存"米"，不存 NDC 深度

描边的深度判据必须是**相对**差：

```
dRel = |d0 - d1| / min(d0, d1)
```

绝对差（`|d0-d1| > 0.01`）的症状是教科书级的：镜头前的角色描边粗成
一团（1 像素跨 2 cm，到处超阈值），50 米外的人物完全没有描边（1 像素
跨 1 m，但 NDC 深度差极小）。相对差把尺度约掉了。

而相对差要成立，`d` 必须是**线性距离**。NDC 深度是 `1/z` 分布，即使做
除法也救不回来。所以 a 通道写的是：

```glsl
viewDist = 1.0 / gl_FragCoord.w;   // == -viewSpaceZ，单位是米
```

一个除法拿到线性距离，不需要 near/far，不需要读 UBO。

⚠ **正交投影下 `gl_FragCoord.w` 恒为 1** → a 退化成常数 1.0，深度判据
失效，只剩法线判据。这是有意接受的：正交只出现在编辑器的前视/顶视图，
而描边是给游戏视口用的。写在 `depth_only.frag` 的文件头里，别让下一个人
以为那里写错了。

### 11.4 天空的 a = 0 是哨兵，不是"距离 0 的物体"

预通道的几何附件被清成 `(0,0,0,0)`。于是"这个像素没有几何"的唯一判据
就是 `a == 0`。判据写错（把 0 当成"贴在镜头上的物体"）的症状极具迷惑性：

- 不报错、不崩、日志干净；
- 整片天空被描成一圈黑边（因为 `|d - 0| / max(min(d,0),1e-3)` 爆炸）。

所以 `geoEdge()` 的第一件事是分三种情况：

```glsl
if (!vc && !vn) return 0.0;   // 两边都是天空 → 没有边
if (vc != vn)   return 1.0;   // 物体 vs 天空 → 这就是轮廓，必须描
// 两边都有几何 → 比深度和法线
```

**第二条不能省。** 少了它，站在天空前的角色就没有外轮廓 —— 而"角色与
背景交界处那条线"恰恰是二次元描边最主要的一条。验收里 `sky_has_no_outline`
（天空新增暗像素必须**恰好为 0**）守的是第一条。

### 11.5 必须用最近邻采样器

`PostProcess` 的 `m_sampler` 是线性过滤。几何缓冲另建了一个
`m_geoNearestSampler`（NEAREST/NEAREST），原因：

线性过滤会在物体边缘把"前景 2 m / 背景 8 m"插成 5 m。于是同一条轮廓
在 uv 上左右各出现半像素的中间值 → **一条边被检出两条线**，而且宽度
随物体远近变化。法线同理（插出来的法线谁也不像）。

两者格式相同（都是 G16R16F），只是 sampler 不同 —— 一个 setLayout
（单 sampler2D 形状）就能挂两种采样方式。

### 11.6 位置：tonemap / LUT / 暗角之**后**

`post.frag` 里合成顺序是：

```
HDR + bloom → 曝光 → tonemap → LUT → 暗角 → **描边** → 输出
```

- 必须在 tonemap **之后**：线颜色是显示域值。放在前面的话，线会被曝光
  乘、被 tonemap 压缩 —— 症状是"换个灯光线就变灰"，线的黑度不再可控。
- 必须在暗角**之后**：描边是风格化元素，不该被镜头暗角衰减。
- 必须在 LUT **之后**：线的颜色就是最终颜色，不参与调色。

这三条不是品味，是"线是**叠加的图案**还是**被照亮的材质**"这个定位问题
的直接后果。

### 11.8 踩坑

- **阈值 0.02 太低。** 相对深度差在**掠射角的大平面**上并不接近 0 ——
  看地面时相邻像素的距离差与距离成正比，相对差是个常数。0.02 会把远处
  地面的一堆像素判成边缘，画面上是一层"星点"。改成 0.05，并把
  `smoothstep` 的上界从 2x 放宽到 3x（宽过渡带把它压成很淡的一层，
  而不是刺眼的散点）。
- **`pc.ups.xy` 过去只在 DRS 开启时才填**（`renderScale == 1` 时是 0）。
  描边要用同一个纹素尺寸算采样步长，而描边与 DRS 是两件独立的事 ——
  照原样用会得到 `tx = 0`，8 邻域全采自己，**一条线都没有**。
  改成无条件填 xy（`z` 仍是开关）。这不改变基线：`upsampleScene` 在
  `z <= 0.5` 时第一行就 return，根本不读 xy。
- **`vkCmdBindDescriptorSets` 不接受 NULL 句柄。** 没有几何输入时不能
  "跳过绑定"，只能绑一个合法集。兜底用 HDR 那张（两者格式相同
  `R16G16B16A16_SFLOAT`，不会触发格式不匹配；描边关闭时着色器不采样它）。
- **`check_regression_map.py` 的 `want` 判据是"恰好相等"，不是"包含"。**
  给 `verify_outline` 登记 `engine/render/RenderTarget.*` 之后，
  `RenderTarget.cpp → 预览与地形并存` 那条 fixture 立刻红（实际集合多了
  一个）。要么改判据、要么补 fixture —— 选了补 fixture 并写清为什么
  （几何缓冲的视图就是在这个文件里跟着 recreate 传下去的）。
- **`MYVK_RUNTIME_PLAYER_MODEL` 在 Player 实体自带 `mesh` 时不生效**
  （`runtime_test/player_scene.json` 的 Player 是胶囊体 primitive）。
  第一次跑以为是模型没加载，其实是环境变量被场景覆盖了。对这个用例反而
  更好：胶囊体是**平滑曲面**，正好验证"平滑面内部不该被描出线"。

### 11.9 已知局限 / 下一步

- **没有逐物体开关，也没有"断线遮罩"。** 二次元描边在鼻翼、内眼角、
  嘴唇交界这些地方是要**断开**的，用顶点色或 UV2 通道存遮罩。那需要
  顶点格式多一个属性 —— 和 P0-5（BlendShape）是同一笔手术，一起做。
- **线宽是渲染像素，不随距离补偿。** 远处物体的线会更细（图上远处那个
  青立方体就很细）。要不要补偿是画风问题：GUST/Arc 系多半要，
  GGXX 那种纯 2D 感的不一定。做的话在 `geoEdge` 里按 `a` 缩放 `tx`。
- **不处理透明物体。** 预通道只画不透明几何（`recordOpaqueDepthGeometry`），
  所以 AlphaBlend 的头发/披风没有描边；Mask 材质**整体跳过**预通道
  （R4-1 的既有决定），也没有。要让它们有线，得先有"透明物体的深度"。
- **双面材质（DOUBLE_SIDED）的背面法线不翻转**（预通道是 SingleSpv，
  只有 cullMode 随掩码变）。看到裙摆内侧时法线朝里 → 内侧会有一圈假描边。
  等真遇到再按掩码编变体，别现在猜。
- 顺序上接下来是 **④⑤ 顶点格式 + 材质页**（UInt morphBase + 96B 页），
  然后 **③ IK**。这两件都不该再往后拖：表情和逐物体描边遮罩都在等它。

## 12 · 第四刀：材质页 32 B → 96 B（A 类槽位，2026-10-25）

第四刀先做了 §8.2 里的 **⑤ 材质页**，把 **④ 顶点格式**留到下一刀。
理由写在 12.1 —— 两者**并不耦合**，先做哪个不该由"顺口"决定。

### 12.1 为什么这一刀只做材质页，不碰顶点格式

审计文档原来的排法是"④⑤ 一起做，因为顶点格式变动要重烤全部资产"。
实际动手前核了一遍 `assetio/MeshFormat.h`，发现那个理由**只对 ④ 成立**：

```
文件头 version  = 容器版本（区块表布局）
区块头 version  = 该区块自身的布局版本
```

材质住在独立的 `MAT` 区块里，有自己的 `matVersion`（当前 v2）。
**升它不影响 MESH 区块**，也就不触发重烤 —— §8.2 那条"每次顶点变动都要
重烤"对材质页不适用。反过来，④ 是真的要重烤（顶点 stride / 属性表变了）。

于是两件事的性价比完全不同：

| | ④ 顶点格式 + MORPH 区块 | ⑤ 材质页 96 B |
|---|---|---|
| 资产 | 要重烤全部 `.vmesh` | 不用 |
| 导入器 | FBX/glTF 的 morph target 解析 | 无（导入链没有 ramp 概念） |
| CPU | Mesh 存 delta + AnimatorSystem 驱动权重 | Material 四个指针 + 六个标量 |
| 解锁 | 表情 / morph 动画 | ramp 明暗带 / matcap / detail |
| 规模 | 一整条数据链 | 一个结构体 |

所以这一刀把 ⑤ 单独做完（**端到端可验证**），④ 留成独立的一刀。
这也顺带修正了审计文档 §0 那条排序原则的说法：耦合的是"资产重烤"，
不是"文件格式"。

### 12.2 96 B 的字段分配，以及为什么不能加 set 也不能加 push

三条 GPU 通道在 32 B 时代就已经全满（§8.2 的账），所以四个语义槽只能进页表。
96 B = 6 个 `uvec4`，每一块都从 16 的倍数开始（std430 的 `vec4` 对齐）：

| 偏移 | 字段 | 内容 |
|---|---|---|
| 0 | `tex0` | albedo / normal / orm / roughness |
| 16 | `tex1` | metallic / emissive / height / **ramp** |
| 32 | `tex2` | **matcap / sdfShadow / detail** / 预留 |
| 48 | `params` | **rampMode / matcapStrength / sdfStrength / detailStrength** |
| 64 | `params2` | **detailTiling / matcapRotate** / 预留 |
| 80 | `spare` | 整块预留（下一刀：morph 权重基址 / 分层遮罩） |

前 32 B **语义与字节都一个字没动** —— 这是"关 = 基线"能成立的前提：
非 bindless 路径、老资产、既有的逐像素对照，全都依赖这段布局没变。

`params` 那一块值得单独说：**push 常量满了之后，这是全引擎唯一能放
逐材质浮点的地方**。ramp 档数、四个强度都是美术要连续调的量，不能进
关键字变体（那会让变体数按参数值爆炸）。这条"通道账"是审计文档 §8.2
事先算过的，这一刀只是去兑现它。

### 12.3 ramp 的语义：乘法调制，不是替换（这是本轮最大的一个坑）

第一版写的是 `band = ramp 采样值`（**替换**程序化两档量化）。全白 ramp
的实测结果是**整个背光半球变成纯黑**。

原因不在采样，在 `toonDirect` 的结构：`band` 同时是"走哪一档"的开关——

```glsl
const vec3 lit  = albedo * (0.80 + 0.20 * ndl);
const vec3 dark = albedo * vec3(0.45, 0.49, 0.62);   // 冷色调阴影
return mix(dark, lit * shadow, band) + spec;
```

`band ≡ 1` 意味着"处处走亮档"，而亮档是 `lit * shadow`；背光面
`shadowFactor` 返回 0（N·L ≤ 0），于是拿到 `lit × 0 = 0`。
A1 花力气建立的"**阴影是有颜色的颜料，不是没有光**"当场被抹掉。

改成乘法调制：

```glsl
return band * texture(rampMap, vec2(u, 0.5)).r;
```

- 白 ramp = `band × 1.0` → **逐位等于** `band`（验收断言 `max diff == 0`）
- 黑 ramp = `band × 0` → 恒 0 → 整个球落在暗部色上（验收断言 `std` 塌掉）
- band 决定"越没越过交界"，ramp 决定"越过之后多亮"，两者独立

**代价要诚实记下来**：乘法只能压暗受光档，**扩不宽受光区**。想让贴图自己
定义"哪一档是暗部色"，得把暗部色的定义也交给贴图（一张色带图或三通道
ramp）—— 那是下一刀。

### 12.4 关闭判据为什么是 `params.x = -1`，而不是"看贴图空不空"

页表里空槽绑的是内置白图，着色器**无法从下标反推**"这张是不是缺省白"。
所以 CPU 侧统一给三态：

| `params.x` | 含义 |
|---|---|
| `-1` | 没挂 rampMap → 走程序化量化（逐像素等于引入这个槽之前） |
| `0` | 挂了，纯渐变（按 NdotL 直接采样） |
| `>0` | 挂了，量化成 N 档（采样点落在色带中心） |

只靠"白图 ×1"是不够的：那样没挂 ramp 的材质（绝大多数）仍要付一次
纹理采样。`-1` 让它们连采样都不做。

### 12.5 三处实现都必须"缺省 = 恒等"

四个槽的缺省一律**纯白**，且用法一律写成恒等形式：

| 槽 | 用法 | 缺省为什么是恒等 |
|---|---|---|
| ramp | `band *= ramp.r` | 白 = ×1 |
| matcap | `color += matcap.rgb * strength` | strength 缺省 0 → +0 |
| detail | `albedo *= mix(vec3(1), dtex, strength)` | 白 + strength 1 → ×1 |
| sdfShadow | 只通到乘法调制（算法待做） | 白 = 处处受光 |

`detail` 那一行刻意用 `mix(vec3(1), ...)` 而不是直接乘：强度旋钮 0 应该
表示"贴花完全不显示"，而**乘法归零会让画面变黑**。mix 到 1 才是淡出。

### 12.6 验收（`tools/verify_material_page.py`，12 项全 PASS）

八轮 Editor.exe 截图，**只换材质、不换机位**（几何与相机严格不变，
所以跨运行的差异只可能来自材质）。判据分两类，恒等类用 `max diff == 0`

## 13 · 第五刀：顶点格式 80 → 112 B（uv2 / morphBase / tangent，2026-10-25）

第四刀（§12）做的是材质页，第五刀做的是 §8.2 P0-5 的另一半：**顶点格式**。

### 13.1 为什么这一刀只做"格式"，不做 morph 数据链

先看这件事的成本结构。§12.1 已经论证过"材质页能单独做"，因为材质住在独立的
`MAT` 区块里、有自己的版本号，升它不触发重烤。顶点**没有**这个待遇：

```
MESH 区块头：version(4) count(4) stride(4) idx16(4)
读端：if (stride != kVertexSize) → 直接拒，报"请重烤"
```

`stride` 一变，全部 `.vmesh` 立刻不可读 —— 这个强约束是**故意的**（错位读比
报错危险得多），代价就是"顶点格式必须一次改对、一次烤完"。

但"格式"和"morph 通道"是两件事，可以分两刀：

| | 这一刀（④-a，格式） | 下一刀（④-b，morph 通道） |
|---|---|---|
| 顶点 stride | 80 → 112 | 不动 |
| `.vmesh` | MESH 区块 v1 → v2，全部重烤 | 加 `MORPH` 区块（可跳过，不重烤） |
| 导入器 | uv2 / tangent 真取值 | blend shape 解析 |
| GPU | 无（没人读新通道） | SSBO + 权重 + 着色器形变 |
| 解锁 | 什么都没解锁 | 表情 / morph 动画 |

分开做的依据是 `morphBase` 的**哨兵**：`0xFFFFFFFF` = "这个顶点不参与任何
目标"，所以"通道存在但全是空的"是一个**合法且自洽**的状态。uv2 / tangent
同理（缺省 0 = 没有）。于是 ④-a 不需要任何消费者也能落地，而 ④-b 不需要
再动格式。反过来（先做 morph 再做格式）等于格式改两次、资产烤两次。

这一刀**不产生任何像素变化**，这是设计使然，不是没做完 —— 见 §13.6。

### 13.2 112 B 的字段分配

老六个属性**偏移一个都没动**（这是整刀最重要的约束，`verify_vertex_format`
的 E 组就是在证明它），新的三个通道全部追加在 80 之后：

| 偏移 | 字段 | 大小 | 内容 | "有没有"的判据 |
|---|---|---|---|---|
| 0 | `pos` | 12 | 位置 | — |
| 12 | `normal` | 12 | 法线 | — |
| 24 | `uv` | 8 | 主 UV | — |
| 32 | `joints` | 16 | 骨骼内下标 ×4 | 权重和 > 0 |
| 48 | `weights` | 16 | 蒙皮权重 ×4 | 同上 |
| 64 | `color` | 16 | 顶点色（Mesh Paint） | 全 1 = 不染色 |
| 80 | `uv2` | 8 | 第二套 UV（面部 SDF / lightmap） | 由**材质**决定用不用 |
| 88 | `morphBase` | 4 | morph 稀疏流下标 | `0xFFFFFFFF` = 不参与 |
| 92 | `reserved0` | 4 | 必须是 0 | — |
| 96 | `tangent` | 16 | xyz = 切线，w = 手性 ±1 | `w == 0` = 没有 |

112 = 16 × 7，且 `tangent` 落在 96（16 的倍数）—— 这不是审美问题：glm 的
`vec4` 在不少平台上按 16 对齐，`vec4` 落在非 16 倍数的偏移上会把结构体
撑出隐式填充，而隐式填充**无法 static_assert**，只能靠运气。

`reserved0` 是**显式命名**的 4 字节，不是留着好看：
- 隐式填充字节的内容是未定义的，而 `AssetSelfTest` 的 `rt_vertex_subset`
  用 `memcmp` 逐字节比顶点 —— 隐式填充会让它在"数据完全相同"时随机红。
- 它也把"以后加一个 u32"的成本从"再改一次 stride、再烤一遍"降到零。

### 13.3 morphBase 为什么是"下标"，为什么哨兵不能用 0

标准做法有两种：

- **密集**：`delta 下标 = v × targetCount + t`。不需要 `morphBase` 字段，
  但每个顶点都要为**所有** target 留槽位。
- **稀疏**：只给真正会动的顶点分配槽位，`morphBase` 指向该顶点那段连续
  的 delta。

算一笔账：50 个 shape key（VRChat 系角色的常态，口型 + 眨眼 + 眉毛 +
身体） × 3 万顶点 × 12 B（vec3 位置偏移）≈ **18 MB / 每子网格**，还是
**不含**法线偏移的数字。稀疏排布只给真正动的顶点分配，一层表情通常只动
脸部的几千个顶点，差一到两个数量级。

ufbx 本身也是稀疏的（`ufbx_blend_shape.offset_vertices[]` 是"哪些逻辑顶点
有偏移"的下标表），所以稠密化反而是额外工作。

**哨兵必须是 `0xFFFFFFFF`，不能用 0**：`morphBase` 是流数组的下标，0 是
一个合法值（第 0 个 target 的第 0 个 delta）。用 0 表示"没有"，症状是
"某几个顶点莫名其妙跟着表情动" —— 而且要等到 ④-b 真跑起来才暴露。

配套的坑：`std::vector<Vertex>(n)` 走的是**值初始化**，没有 NSDMI 的成员
会被清零。所以 `morphBase` / `reserved0` 都带了默认成员初始化器
（`assetio/Vertex.h` 与 `engine/assets/Mesh.h` 各一份）。漏掉它的后果
不是编译错，是"所有顶点都指向流的第 0 项"。

### 13.4 为什么不开"顶点级标志位"，三个通道各用自己的哨兵

直觉方案是加一个 `uint flags`，`bit0 = 有 uv2`、`bit1 = 有切线`。
没这么做，理由是三条：

1. **每个通道已经有天然哨兵**：切线的手性只有 ±1，`w = 0` 是干净的空位；
   morph 的下标是 u32，`0xFFFFFFFF` 是干净的空位；uv2 是"用不用"的问题，
   由**材质**决定（同一个网格里"一半顶点有 UV2"不是合法状态）。
2. **逐顶点标志会引入一个非法状态**：`flags.bit1 = 1` 但 `tangent = 0`。
   哨兵方案根本没有这个状态。
3. **它要多一次取指**，换来的只是"省一个哨兵值"。

顺带记一条：§11.9 里"描边断线遮罩需要 UV2 通道"这个说法**可以收回**了 ——
`color` 通道（location 5）从 P0-3 起就已经在顶点上，用它的 alpha 存遮罩
就够，不需要新字段。

### 13.5 属性表只喂 0..5：VUID-Input-07904

顶点 stride 里有 32 个字节"没有着色器声明"，这在 Vulkan 里是**合法**的
（属性描述只管"哪几个 location 从哪儿取"，stride 里剩下的字节没人管）。
但反过来不成立：

```
管线声明了 location 6，而顶点着色器没消费 → VUID-...-Input-07904
管线没声明 location 6，而着色器读了它 → 读到 0（未定义行为，不报错）
```

`pbr.vert` 目前只声明 `location 0..5`，所以 `attributeDescriptions()`
**保持返回 6 条**（不是 9 条），阴影/贴花继续传 5。将来开一个新通道，
必须**同时**改两处：`attributeDescriptions(9)` + 顶点着色器里声明。只改
一边,前者是校验层报错、后者是静默读 0 —— 后者更难查。

三个通道各自的消费者（写在 `Mesh.h` 的注释里，实现时按这张表接）：

| 通道 | 消费者 | 所在刀 |
|---|---|---|
| `uv2` | 面部 SDF 阴影（采样头部的 unwrap 贴图） | ⑥ |
| `morphBase` | morph delta 流（SSBO，按 target 权重累加位置/法线） | ④-b |
| `tangent` | 各向异性头发高光（需要真 TBN，导数版不能用） | 头发刀 |

### 13.6 验收：为什么这一刀没有截图判据

老规矩是新功能做"改前 / 改后"两轮截图、要求 `max diff == 0`。这一次
**用不上**，而且不是偷懒：

1. 三个新通道**没有任何着色器读**（§13.5）。
2. 老六个属性的字节在重烤前后**逐个相同**（E 组，164594 个顶点）。
3. → 渲染出来的每一帧必然一样。一张"必然一样"的图不能证明任何事。

所以判据全部钉在**字节**上。这不比截图弱 —— 格式手术最危险的失败模式

### 13.7 踩坑记录

- **焊接键漏字段 = 静默数据丢失，不是"多留几个顶点"。** `vertexKey` /
  `vertexEqual` 不把 `uv2` / `tangent` 加进去，两个 uv2 不同的顶点会被判成
  同一个，UV2 只剩其中一份 —— 几何完全正确，只有面部阴影纹理是歪的。
- **`uv_sets[0]` 就是 `mesh.vertex_uv`。** ufbx 头里明写了 "The first set
  contains the same data as vertex_uv"，取 0 当"第二套"得到的是一张复制品。
- **`uv2` 的 V 翻转方向必须与 `uv` 一致。** FBX 原点在左下、引擎在左上，
  `uv` 做了 `1 - y`，`uv2` 漏掉就是两套 UV 上下镜像 —— 只有近似对称的脸
  才看不出来。
- **零长度切线比"没有切线"更有害。** 存在判据是 `w != 0`，放一个零向量
  过去会让着色器拿 `normalize(0)` 建 TBN，整片法线贴图变 NaN 黑斑。
  导入器里显式 `if (len2 > 1e-12)` 才写。
- **`readVec4` 会无条件读第 4 个 float。** glTF 的 `TANGENT` 在少数导出器里
  是 VEC3，用 `readVec4` 会越界读一个 float（落在下一个元素上时"能用"，
  落在末尾时崩）。改成 `readVec3` + `compS >= 4` 才读 w。
- **LOD 不能把切线带下去。** 把手性相反的两条切线平均出来是一个**错**的
  切线，比没有更难查。所以 `Lod.cpp` 显式留空（`Vertex v;` 的默认构造就是
  空），`morphBase` 同理 —— LOD 顶点是重新聚类出来的，和原顶点的 delta
  没有对应关系。两条都记在 §13.8。
- **验收脚本里 `.vmesh` 的 mtime 必须钉死。** 加载器判"缓存是否过期"比的是
  mtime；`shutil.copy2` 保留原时间戳，仓库里谁比谁新是历史偶然。不显式
  `os.utime(vmesh > fbx)`，D 组就会静默退化成"测的是 FBX 解析路径"，而统计
  数字照样对得上（两边数据一样）——**判据还在，被测对象换了**。
- **E1 第一版是假 PASS。** 备份文件名拼错 → 循环一次都没进 → `mismatched`
  为空 → 判 PASS，详情写着"0 个顶点已验证"。**一个能零证据通过的断言比
  没有更危险**：它让人以为这块被看着了。改成 `not mismatched and verified > 0`。
- **`assetio/MeshFormat.cpp` 变成两个 owner。** 它同时是格式总主（偏移/区块
  表，`verify_vmesh`）和顶点布局（stride/版本，本刀）。加完触发面后
  `check_regression_map.py` 立刻红在 `assetio/MeshFormat.cpp → verify_vmesh`
  这条 fixture 上 —— 与 §11 里 `RenderTarget.*` 那次是同一类，补 fixture
  而不是改判据。
- **`engine/assets/Mesh.h` 是横切，不该写进 TRIGGERS。** 写上去不影响行为
  （它在 `GLOBAL_GLOBS` 里），但会让读代码的人以为"改它只影响这条用例"。
  `check_regression_map.py` 的 E 组把这类"冗余 glob"单独列出来。

**顺带修掉的一个老问题（与顶点格式无关，但被这一刀撞出来）：**

`verify_vmesh` 的 D1 一直是红的（`pass=43 fail=2`），报
`anim_err_at_keys rot=179.591263`。查下来**不是抽帧器的问题**，是
`AssetSelfTest.cpp` 的 `pairClips` 按**名字**配对 clip：

```
FbxImport.cpp:527   clip.name = clip.name.substr(bar + 1);   // "Ns|Idle" → "Idle"
```

`anime_girl.fbx` 里有两段 clip 剥完前缀都叫 `Idle`（诊断打出来
`sameName=2`），于是第二段的 `before` 去和第一段的 `after` 相比 ——
误差是一个**恒定**的 179.59°，看着就像"抽帧把首帧删错了"。

排除过程也一并记下来，因为这个顺序下次还能用：先看 `dt0`（重复时间戳？
0.0333，不是）→ 再看同 `(joint,path)` 通道数 `dup`（多通道错配？1，不是）
→ 最后才数同名 clip（2，就是它）。改成**按下标配对**（`reduceClip` 原地改、
不删不重排 clip），真值立刻回到 `rot=0.0969`，45/45 PASS。

⚠ 但**资产侧的重复 clip 名还在**（两段 `Idle`）—— 按名字选 clip 的地方
（编辑器片段列表、脚本 API）本身是歧义的，记进 §13.8。

### 13.8 已知局限 / 下一步

- **三个通道都没有消费者。** 这是这一刀的定义，不是欠账（§13.1）。但反过
  来说：**`tangent` 的"有值"路径从未被真实数据验证过** —— 6 个资产全都
  不带切线（Blender 默认不导出），所以 B3 只能断言"全或无"、正例是空的。
  等第一个带切线的 FBX 进来时才能验。
- **不生成切线。** 缺就缺。生成要按三角形累加再做 Gram-Schmidt，而现在
  没有任何着色器读它 —— 凭空生成一份没人验证的数据，只会让头发那一刀在
  排查时多一个可疑变量。
- **LOD 不携带切线，也不携带 morph。** 见 §13.7 的说明。要知道代价：
  一个带表情的脸如果开了 LOD，拉远之后表情会**冻在基础形状**上。二次元的
  脸一般不参与 LOD，但这条要先写下来。
- **`anime_girl.fbx` 有两段同名 `Idle` clip。** 从 §13.7 那条一起发现的。
  影响：按名字选片段的入口是歧义的。修法有两条（导入期去重命名 / 全局改用
  下标），都会改动产品数据，要单独一刀 + 重烤。
- **`morphBase` 的稀疏流布局**（§14 已定）：`morphBase` + `morphCount` 两个
  字段（后者复用了原来叫 `reserved0` 的那 4 字节），vertex-major、同顶点内
  按 target 升序。**但权重还没地方放** —— push 常量 128 B 满仓，见 §14.6。
- **④-b2（GPU 形变通道）仍是下一刀。** 之后 ③ IK，然后 ⑥ 表情 /
  面部 SDF（UV1 已就位，缺的是算法）。

## 14 · 第六刀：morph 数据链（MORPH 区块 / delta 流 / 焊接重映射，2026-10-25）

第五刀（§13）把顶点格式一次改对，三个新通道全是空的；这一刀把
`morphBase` 填上**真数据**，并让 `.vmesh` 里真的存在一条 delta 流。

### 14.1 为什么这一刀仍然不接 GPU

§13.1 把 ④ 拆成「格式」和「morph 数据链」两半，依据是 `morphBase` 的哨兵
让"通道存在但全是空"成为合法状态。这一刀做完，`morphBase` 有真值了，
但**着色器仍然不读它**。理由不是"还没做完"，是一个具体的技术障碍：

```
PushConstants 现状（128 B，Vulkan 保证的下限，一个字节都不剩）
  model(64) baseColorFactor(16) pbr(16) emissive(16) skin(16)
                                                        ↑
  skin.x = jointBase   skin.y = POM 视差深度
  skin.z = 蒙皮标志    skin.w = alphaCutoff（符号兼 dither 开关）
```

morph 权重是**每实例**的数据（每个角色当前的表情进度），必须有一条
per-instance 的通道。可选的四条路都不通：

| 通道 | 为什么不行 |
|---|---|
| push 常量 | 128 B 满仓，`skin` 四个分量各有主 |
| 顶点属性 | 权重是 per-instance，不是 per-vertex |
| 材质页（96 B） | 页是 per-material，权重是 per-instance |
| 纹理 set | 7 个已在 `maxBoundDescriptorSets` 的下限上（§12.1） |

唯一可行的是**新的 SSBO**（per-instance 权重数组），而它需要一个
per-instance 的基址 —— 那又回到 push 没有空位。所以这是一个**要单独设计**
的问题（候选：把 `pbr.w` 的 ao 挪进材质页 spare、给 MDI 记录用 `aux.y`、
或者干脆把 jointMatrix 与权重块放进同一个分配器共用槽号），不该和
"数据链落地"混在一刀里。§14.6 把候选写清楚了。

**所以这一刀的定义是**：让 morph 数据从 FBX 一路走到运行期的
`assets::Mesh`，并且**每一环都有断言**。GPU 那一段单独一刀。

### 14.2 MORPH 区块格式（v1，可选区块）

`.vmesh` 的第六个区块 id = 6。**没有 morph 的资产不写它** —— 6 个资产里
只有 1 个有，写空区块会让每个读端每次多跳过一段，也会让"有没有 morph"
的判断退化成两个条件。

```
MORPH 区块:
  u32 version = 1
  u32 subMeshCount            // 必须等于 MESH 区块的 subMeshCount
  per submesh:
    u32 targetCount
    u32 deltaCount
    u32 nameStrIdx[targetCount]        // STR 区块下标
    SourceMorphDelta deltas[deltaCount]  // 32 B each，见下
```

`SourceMorphDelta` 的 32 字节是**刻意与 GPU 布局对齐**的：

| 偏移 | 字段 | GPU 侧 |
|---|---|---|
| 0 | `position` (vec3) | 直接读 |
| 12 | `target` (u32) | 直接读 |
| 16 | `normal` (vec3) | 直接读 |
| 28 | `vertex` (u32) | **填充位**（着色器不读） |

`vertex` 在 GPU 上是浪费的 4 字节，在文件里是**校验的关键**：它让加载路径
能断言"流的顺序 == 顶点顺序"。少了这道校验，一次"顶点重排了但流没跟着
重排"会让整张脸按错误的顶点形变 —— 而几何、法线、UV 全都正常，肉眼只能
看到"脸歪了"。为了这 4 字节换一个能定位的错误，值。

### 14.3 三个有强制顺序的步骤

morph 数据是**按下标**存的，而焊接会换下标。所以整条链的顺序是写死的：

```
① prepareMorphIdentity   （焊接前）
      把"这个顶点参与哪些 target、偏移是多少"编码进 morphBase/morphCount，
      让焊接把它们当顶点身份的一部分。
② weldVertices(+remap) → remapMorphTargets  （焊接后立刻）
      按 old→new 映射改 delta 表的顶点下标，去重、按新下标升序。
③ buildMorphStream       （所有换下标的操作都做完之后）
      按顶点序展平成 delta 流，写真的 morphBase/morphCount。
```

**① 为什么必须在前**：`weldVertices` 只看 `Vertex` 的字段。如果 morph 归属
不在字段里，一个"在 target_3 里往前鼓 2mm"的顶点会和一个"不在任何 target
里"的完全相同的顶点焊在一起 —— 形变静默丢失，而且只在做表情时才看得出。

**② 为什么必须紧跟焊接**：`remap` 只在那一刻有效。中间插任何换下标的
操作（比如将来的顶点重排）都会让 remap 失效。

**③ 为什么必须最后**：它写的是"最终顶点下标空间"上的 base。

`optimizeForCache` 不在这个约束里：它**只改索引顺序，不动顶点数组**
（`VertexOps.cpp` 的实现）。所以 morph 完全不受它影响 —— 这一条要写下来，
因为将来有人把 Forsyth 换成"重排顶点"的版本时，这里会静默错。

### 14.4 焊接阶段 morphBase 存的是哈希，不是下标

①②之间那个状态值得单独说：`morphBase` 此时存的是**归属哈希**
（64 位 FNV 低 32 位，编码 target 下标 + 量化后的 pos/normal 偏移），
`morphCount` 是参与 target 数。`vertexKey` / `vertexEqual` 都把它算进去。

为什么不用"另一个字段"：没有另一个字段（112 B 已经满了）。
为什么不用下标：下标是**每顶点唯一**的，焊什么都不会合并 —— 顶点数会虚高，
而且"同一份 FBX 烤两次"的一致性会依赖导入顺序。

哈希碰撞的概率是 2^-32，再叠一道 `morphCount` 必须相等的判断。这个风险
是显式接受的：一次碰撞的症状是"某块几何静默失去形变"，而它需要
2^32 分之一的巧合 + 恰好两个顶点其余属性完全相同。

⚠ **这个临时值不能在任何别处读。** `buildMorphStream` 会把它覆盖掉。
`prepareMorphIdentity` 的函数注释里写了这句。

### 14.5 `reserved0` → `morphCount`：一次预期的复用

§13 里第 92 字节的 u32 叫 `reserved0`，注释是"必须是 0，预留"。这一刀
把它改名成 `morphCount`。

这不是语义漂移，而是**当初留它的目的**：`tangent` 必须落在 96（16 的倍数），
所以 88/92 那两个 u32 里，88 给了 `morphBase`、92 只能是"以后再要一个 u32"。
现在那个"以后"到了。

所以：**顶点 stride 仍然是 112，一个字节都没加**，MESH 区块版本仍然是 2。
老 v2 资产里这两个字段是（哨兵, 0），新读端解释成"没有 morph"—— 与真实
情况一致，不需要重烤没有 morph 的资产。

读端新增两条硬校验（都在 `readMeshFile` 里，每次加载都跑）：

```
MESH 有非哨兵 morphBase，但 MORPH 区块缺失  → 报错（不是静默当成没有）
morphBase == 哨兵 ⇔ morphCount == 0         → 否则报错
```

### 14.6 数据规模：alicia 的实测账

```
alicia.fbx   blend_deformer 4 个（eye / face / other / other02）
             channel 共 60 个（3 + 49 + 7 + 1），全部 keyframes=1
             逻辑顶点 2750（278 + 1894 + 552 + 26）
             焊接后渲染顶点 21310

烤制结果     88 targets / 18132 deltas / 566.6 KB
             文件 2.58 MB → 3.13 MB（+22%）
```

88 而不是 60，是因为**target 下标是子网格内局部**的：一个 mesh 按材质分成
几个子网格时，每个桶都带上自己那套非空 target。60 + 28 = 88。

为什么不做"跨子网格统一的 target 表"：alicia 的 4 个 blend_deformer 本来就是
各自 mesh 的，`eye` 的 `target_0` 和 `face` 的 `target_0` 没有任何关系。
强行统一名字只会造出一张大部分是空的表，而且会让驱动端以为"驱动 target_3
会影响整只模型"。

**代价**（记进 §14.8）：跨子网格驱动一个表情要按子网格分别查。

#### 内容层面的证据（`tools/_probe_morph_stats.py`）

字节自洽能证明**结构**对，但证明不了**内容不是一堆 0** —— 一个全 0 的
delta 流同样能通过 verify_morph 的全部 25 项。所以另有一个探针直解 MORPH
区块，把内容画出来：

```
18132 条 delta 的位移长度
  min  1.04e-05 m       max  6.70e-02 m       mean 7.12e-03 m
  zeros = 0            ← 没有任何一条是空的
每个 (子网格,target) 的 delta 条数：最多 926，88 对里没有空的
受影响顶点在正面投影上**集中在头部**，少量在躯干
```

最后一条是最有用的：**动的是脸**。如果位置偏移漏了坐标轴变换（§14.7 那条
`geometry_to_world`），红点会整体偏出去；如果 delta 的 target 串了（两侧
子网格的下标混用），会看到"手在跟着眨眼动"。一张三格图比三十条断言更快
看出这类错。

### 14.7 踩坑记录

- **`ufbx_get_blend_shape_offset_index` 不能每顶点调一次。** 它内部是线性
  扫描，21310 顶点 × 700 偏移 × 60 target ≈ 9 亿次比较，烤一个资产要等
  半分钟。改成"每 target 建一次反查表、扫一遍顶点"（目标倒置），
  降到 128 万次。
- **`offset_vertices[]` 可能越界。** ufbx 头里明写了 "may be out-of-bounds
  for a given mesh"（同一个 shape 被多个 mesh 共享时偏移表是按并集建的）。
  不检查就是一次越界读，且在 Windows 上大概率"看起来能用"。
- **morph 的位置偏移必须过 `geometry_to_world` 的线性部分。** 蒙皮网格的
  顶点在 `walk` 里被烘到静止世界空间，偏移漏掉同一个变换的症状是"角色
  一捏表情就往斜上方飞"，而且**只在有缩放的节点下明显** —— 平移到原点的
  节点看不出问题。
- **法线偏移不能归一化。** 它是增量不是方向。归一化会把"轻微鼓包"（0.01）
  放大成"整体膨胀"（1.0）。
- **`vertexEqual` 里 `morphCount` 也必须比。** 与 `vertexKey` 一一对应是
  铁律（§13.7 那条的延伸）：哈希说"同"而实际"不同"时，差异会被直接抹掉。
- **`rt_new_channels` 会红。** 它拿写盘**前**的顶点整字节 `memcmp`，而
  `morphBase` 在写盘时才从哨兵变成真下标 —— 那是预期变化，不是丢数据。
  改成比较时把这两个字段抹平（其余 104 字节仍逐字节比）。
- **验收脚本 C 组第一版三项全红，而 C++ 读端是绿的。** 原因：MESH 目录里的
  `ofsV` 是**相对区块起点**的偏移，Python 直接拿它当绝对偏移用，读到了
  别的区块的字节。这恰好证明了"两条独立实现互校"的价值 —— 如果只信 C++
  一边，这个 bug 会一直在脚本里（而脚本是判据）。
- **`--info` 加一行不会撞现有正则。** `verify_vmesh` 的 B2 正则锚在
  `submeshes=... index16=` 那一行，新加的 `morph targets=...` 是独立行。
  但下一个往同一行追加字段的人要注意 —— 那条注释（`assetc/main.cpp:190`）
  就是为此写的。

### 14.8 已知局限 / 下一步

## 15 · 第七刀：GPU 形变 + 四条欠账清算（2026-10-25）

第六刀（§14）把 morph 的**数据**烤进了 `.vmesh`，但着色器一个字节都没读，
所以那一刀的正确性只能靠离线断言守。这一刀把数据接上 GPU，并且顺手清掉
§14.8 记的四条欠账。

### 15.1 为什么四条欠账必须同一刀

四条欠账看起来彼此无关（名字、in-between、offset_weights、LOD），其实全都
落在**同一条数据链的同一个中间层**：

```
ufbx blend_deformer → blend_channel → blend_keyframe → (target 下标, targetWeight)
                    → 每子网格的 delta 流 → MORPH 区块 → MorphRig → GPU SSBO
```

- 「名字无语义」→ 需要一个 `channel → 名字` 的表，而这张表的位置在
  **channel 层**，正是 in-between 也要改的那一层。
- 「in-between 不支持」→ 要求 channel 记 `(targetWeight, target)` **点列**，
  而点列里的 target 是**子网格内局部下标**，与「按名字驱动」共用同一张
  重映射表。
- 「offset_weights 被忽略」→ 改的是 delta 的**产生**方式，改完必须重烤，
  重烤就要过 MORPH 区块版本号（v1 → v2），而版本号一变，channel 表刚好
  可以一起加进去。
- 「LOD 不带 morph」→ 判据是 `Mesh::hasMorph()`，而 `hasMorph()` 的真假
  取决于 v2 读端能不能正确读出 channel 表。

一句话：**这四条里任何一条单独做，都要把 MORPH 区块改两次版本号。**
所以合成一刀，区块只升到 v2。

### 15.2 通道方案：三块 SSBO，不是"再挤一点 push"

§14.8 当时评估过三套「塞进现有通道」的方案。全部作废，原因很简单 ——
**PushConstants 已经满了**：

```
128 B = model(64) + baseColor(16) + pbr(16) + emissive(16) + skin(16)
```

`skin` 那段是第五刀（§13）给蒙皮加的，加完之后 `pbr.w` 已经是最后一个
可挪的标量，而 morph 需要的是**三样东西**：

| 需要 | 按什么变 | 大小 |
|---|---|---|
| delta 流基址 | 按 **Mesh** 变（每个子网格一段） | u32 |
| 权重块基址 | 按 **实例** 变（每角色一套 49 个权重） | u32 |
| target 数 | 按 Mesh + 实例变（`0` = 整条链跳过） | u32 |

一个 `pbr.w` 装不下一组三元组，而 `aux.y/z/w` 只有三个槽、且 MDI 与基线
路径各需要一条独立通路。最终：

```
binding 25  MorphDeltas   StorageBuffer   Vertex   MorphDelta[]   (32 B/条)
binding 26  MorphWeights  StorageBuffer   Vertex   float[]
binding 27  MorphSlots    StorageBuffer   Vertex   uvec4[]        (16 B/实例)
```

`set 0 binding 0..24` 本来已经占满，`kGlobalSetBindings` 从 25 抬到 **28**。
三块都是 `VK_SHADER_STAGE_VERTEX_BIT` —— 片元阶段用不到形变后的法线，
用不到的东西不给它可见性。

`MorphSlots[i]` 的 `uvec4` 布局：

```
.x = delta 流基址（全局，单位=条）
.y = 权重块基址（全局，单位=float）
.z = target 数      (0 → 该实例不形变，整段循环跳过)
.w = 保留
```

### 15.3 着色器：形变必须发生在蒙皮之前

这是这一刀唯一一处"顺序错了就全错"的地方：

```glsl
vec3 morphPos = vec3(0.0), morphNrm = vec3(0.0);
if (inMorphCount > 0u) {
    const uvec4 mi = morphSlots[morphSlot];
    if (mi.z > 0u) {
        const uint base = mi.x + inMorphBase;   // inMorphBase = 本子网格在流里的起点
        const uint n = min(inMorphCount, 256u);
        for (uint i = 0u; i < n; ++i) {
            const MorphDelta d = morphDeltas[base + i];
            const float w = morphWeights[mi.y + d.target];
            morphPos += d.position * w;
            morphNrm += d.normal   * w;
        }
    }
}
```

两个理由：

1. **delta 与 `inPos` 同空间。** 烤制时 delta 已经过了 `geometry_to_world`
   的线性部分（§14.7 那条坑），所以它和 `inPos` 都在"静止世界"空间。
2. **`skinMat` 是「静止世界 → 当前姿势」**，所以形变后的顶点要**再**乘
   `skinMat`，而不是反过来：

```glsl
if (dot(inWeights, vec4(1.0)) > 0.0) {
    mat4 skinMat = ...;
    localPos = skinMat * vec4(inPos + morphPos, 1.0);
    localNrm = mat3(skinMat) * (inNormal + morphNrm);
}
```

写成 `skinMat * inPos + morphPos` 的症状是「角色摆 POSE 时表情偏移量变得
和姿势无关地乱飘」—— 静止姿势下完全看不出来，因为 `skinMat == I`。

法线偏移**不归一化**（§14.7 同一条坑）：它是增量不是方向。

循环上限 `min(inMorphCount, 256u)` 是防御性的：`inMorphCount` 来自顶点属性，
属性表错了就是任意大数，`for` 直接挂死。真实最大 926（§14.6），所以 256
这个上限**目前会截断** —— 但截断只可能发生在一个 target 影响某子网格里
超过 256 个顶点时，而 `kMaxLevels`/属性都是按真实数据配的。真要接更大的
资产，这里得跟着 `kMorphDeltaCap` 一起抬，`verify_morph_gpu` 的 G2 会红。

顶点属性 `location 7 = morphBase`、`location 8 = morphCount`（都是
`R32_UINT`）在第六刀就写好了。但顶点属性表**不是连续前缀**：

```
pbr.vert      读 0..5 + 7/8   （跳过 6 = uv2，9 = tangent）
shadow.vert   读 0..4 + 7/8   （不需要 uv / 切线）
```

所以 `Mesh.h` 里不是 `attributeDescriptions(count)`，而是
`attributesFor({0,1,2,3,4,5,7,8})` —— 传一个下标集合。原来那个"前 N 个"
的自由函数只留给 decal（它确实只用前缀）。

### 15.4 channel 与 target 解耦：in-between 落地

数据模型从「channel → 一个 target」改成「channel → `(targetWeight, target)`
点列」：

```cpp
struct MorphChannelKey {
    float targetWeight = 1.0f;
    std::uint32_t target = 0;      // kNoMorphTarget = 本子网格没有这个偏移
};
constexpr std::uint32_t kNoMorphTarget = 0xFFFFFFFFu;

struct MorphChannel {
    std::string name;
    std::vector<MorphChannelKey> keys;   // 按 targetWeight 升序
};
```

`kNoMorphTarget` 是**插值断点**，不是"整条丢掉"。这条区别很关键：一个
in-between 通道的三个 key 里，某个子网格可能只参与了其中两个；第三个位置
必须是"在这个 targetWeight 上，这个子网格没有偏移"，而不是"这个子网格不
参与这个通道" —— 后者会让它在 0 和 1 之间整个消失。

MORPH 区块 v1 → v2 就是在目标表后面追一张 channel 表：

```
[目标表]  count, 然后 count × (nameStr, deltaCount, delta[])...
[channel] channelCount, 然后 channelCount × (nameStr, keyCount, keyCount × (f32 weight, u32 target))
```

读端三条硬校验（缺一条就会在运行时变成静默错位）：channel 没有 key、
`target >= morphTargets.size()`、`targetWeight ∉ [0,1]`。

**版本陷阱**：容器区块表里的 `version` 字段是**固定常数 1**（写端 `Sec`
结构里根本没有 version 字段），真正有效的是**区块内部第一个 u32**。外部
工具（包括我第一版的 `verify_morph.py`）按区块表判断版本会读歪 —— 这条
写进了 `verify_morph.py` 的注释里，因为它骗了我一次。

### 15.5 名字：从「只保留」到「按名字驱动」

`MorphRig` 是这一刀新增的运行时层，把「88 个逐桶 channel」压成「49 个
唯一名字」：

```cpp
struct MorphRigChannel {
    std::string name;
    struct Point { std::uint32_t subMesh, target; float weight; };
    std::vector<Point> points;
    std::uint32_t drives = 0;      // 真正会动的 (子网格,target) 数
};

struct MorphRig {
    std::unordered_map<std::string, std::uint32_t> channelIndex;
    std::uint32_t targetCount = 0;
    void evaluate(const std::vector<float>& weights, ...) const;
};
```

- **88 → 49** 是因为同一批 target 名在多个子网格里重复出现（`target_0`
  在 `eye` 和 `face` 里都有，但下标无关）。合并键是**名字**，`points` 里
  记的是 `(subMesh, target)` 全限定坐标。
- 名字冲突（同一子网格里两个 channel 同名）在**烤制时**就加了 `#i` 后缀，
  所以运行期的名字表是无冲突的 —— 代价是名字可能长得像 `target_0#1`。
- 驱动接口：

```cpp
assets::setMorphWeight(model->morphRig, mp.weights, "target_7", 0.8f);
float w = assets::morphWeight(model->morphRig, mp.weights, "target_7");
```

返回 `bool` / 找不到返回 -1，调用方可以区分"名字不存在"和"值就是 0"。
控制台 `morph.set <channel> <weight> [name]`、`morph.list [name]`、
Inspector 滑条、场景序列化四条路都走这一个函数。

**诚实记录**：alicia.fbx 里的通道名**本来就是** `target_0` 这类（7.5 MB
二进制里搜 `Blink` / `blink` / `shape` 命中 0 次，`target_0` 命中 76 次）。
所以"名字无语义"这条欠账，引擎侧能做到的极限是：

| 能做到 | 做不到 |
|---|---|
| 名字如实保留（不按位置重排、不丢） | 凭空造出语义名 |
| 按名字驱动，不依赖下标 | 保证美术下次不叫 `target_0` |
| 重名不互相覆盖（`#i`） | 跨资产统一命名 |

"引擎只能按下标驱动"这个**症状**已经消失（现在按名字），但"资产里没有
语义名"这个**根因**在美术侧，不在引擎侧。要在引擎里补，只有一条路：给
`.vmeta` 加一张「名字 → 语义」的映射表（还没做，见 §15.12）。

### 15.6 offset_weights：预乘进 delta

ufbx 的求值式是

```
vertex += offset * weight * offset_weights[i]          // ufbx.c:32078
```

`offset_weights[i]` 是**逐偏移的常数**，与权重无关 —— 所以它可以**预乘进
delta**，`MorphDelta` 的 32 B 布局一个字节都不用改：

```cpp
const std::size_t owCount = shape->offset_weights.count;
const float ow = (di < owCount) ? float(shape->offset_weights.data[di]) : 1.0f;
rec.pos = glm::vec3(po.x, po.y, po.z) * ow;
if (hasNOff) rec.nrm = glm::vec3(no.x, no.y, no.z) * ow;
if (rec.pos == glm::vec3(0) && rec.nrm == glm::vec3(0)) continue;   // ow == 0 的直接丢
```

最后那行丢弃是必须的：`ow == 0` 的偏移预乘后是零向量，留着只会多读一次
SSBO。实测烤完**零 delta 条数 = 0**（`verify_morph.py` 的 G1），说明要么
alicia 里没有 `ow == 0` 的偏移，要么丢弃生效了 —— 两种情况下最终数据都干净。

§14.8 原话说「忽略它的后果是权重不是 1 的偏移被当成 1」。现在不会了。

### 15.7 LOD：拒绝错配，而不是补数据

原欠账是「LOD 不携带 morph」。直觉上的修法是"给 LOD 各级也烤一份 delta"，
这是错的：

- LOD 各级是 `ensureLod` **独立减面**出来的 Mesh，顶点集合与 LOD0 不同；
- delta 是**逐顶点**的，减面后要重新做一次最近邻投影，等于重烤一遍；
- 更要命的是 `Model::subMeshIndexOf(const Mesh*)` 找不到 LOD 各级的 Mesh，
  所以就算数据对了，槽位也对不上。

真正的症状是**静默失效**：几何 / 法线 / UV 全对，只有脸不动。比掉帧难查
一个数量级。所以改成明确拒绝：

```cpp
} else if (base->hasMorph()) {
    // 有 morph 的网格**不建 LOD 链**
    VK_LOG_INFO("LOD-SKIP-MORPH '%s'（网格带 morph 偏移，不做自动减面）", ...);
} else if (meshLooksSkinned(*base)) {
    ... 正常建 LOD ...
}
```

代价写清楚：**带表情的角色永远不会自动减面**。这是一个明确的取舍 ——
alicia 才 21310 顶点，远没到需要 LOD 的规模；等真有大资产要做 LOD，正确
做法是"在 DCC 里对每一级 LOD 各导一份带 shape key 的 mesh"，而不是运行时
减面再猜 delta。

### 15.8 槽位、预算、以及「永不重建」的硬理由

三块 SSBO 是**固定容量**，建一次，**永不重建**：

```
kMorphDeltaCap  = 24 MB / 32 B = 786432 条
kMorphWeightCap =  4 MB /  4 B = 1048576 个 float
kMorphSlotCap   = 8192 个实例
```

（alicia 实测用了 18132 条 / 88×49 权重 / 20 个槽位，占用率 2.3% / 0.4% /
0.2%，余量充足。）

为什么不扩容重建：**换 buffer 会让主视口有一帧读到空 buffer**。描述符集
在 `createFrames` 里一次写好（`writeGlobalSet`），重建意味着要重新写描述符
并保证所有在飞的帧都同步 —— 在主线程里做这件事，代价和风险都远超「预留
24 MB 显存」。

超限时的降级：`m_morphBudgetHit` 置位、`m_morphBudgetWarned` 只打**一次**
日志（每帧打会淹掉真正的错误），受影响实例的 `targets` 写 0 = 不形变。
半形变比不形变糟得多（会看到脸只动一半）。

槽位分配有三条路径，**每条都要正确**：

| 路径 | 槽位来源 | 写在哪 |
|---|---|---|
| MDI（bindless+间接） | `MdiInstance.aux.y` | `buildMdiFrameData` |
| 基线合批 | `gl_InstanceIndex` | 批构建时逐个写 `morphSlots[]` |
| 阴影 | 现场求值 + `m_instanceOffset++` | `ShadowPass` 的 `push.which.z` |

MDI 那条最容易错：`gl_InstanceIndex` 是**紧凑化之后**的下标（间接绘制会
跳过视锥外实例），索引不到全局槽空间。所以槽位必须由**目录**带过来：

```cpp
rec.aux = glm::ivec4(it.jointBase,
                     static_cast<int>(batch.firstInstance + (k - i)), 0, 0);
```

注意这里是**重算**（批基址 + 批内偏移），不依赖 `it.morphSlot` —— 早期
版本依赖它，一旦批次重排就串槽（症状：A 角色的表情动在 B 角色脸上）。

`targets == 0` 时必须**显式清零**，不能靠"反正没人读"。槽位是复用的，
上上帧残留的 `targets > 0` 会让一个已经超预算的实例突然开始用别人的 delta。

### 15.9 欠账清算

| §14.8 的欠账 | 状态 | 落点 | 怎么验的 |
|---|---|---|---|
| 着色器不读 morph | **已解决** | `pbr.vert` / `shadow.vert` + SSBO 25/26/27 | `verify_morph_gpu` G2（像素差 0.048%）|
| 名字无语义 | **引擎侧已解决**，根因在美术侧 | `MorphRig` + `setMorphWeight` + `morph.set` + 序列化按名字 | G4a/G4b/G4d + 场景往返 |
| in-between 不支持 | **已解决**（无样本） | channel → `(targetWeight,target)` 点列 | `verify_morph` F1~F5；alicia 实测 0 条 |
| offset_weights 被忽略 | **已解决** | 预乘进 delta | `verify_morph` G1（零 delta = 0 条）|
| LOD 不携带 morph | **已解决**（改为拒绝建链）| `AssetManager::ensureLod` + `LOD-SKIP-MORPH` | 日志实测触发 |

四条里唯一没有真实样本的是 in-between。这条必须写在显眼位置：**路径支持
≠ 路径验过**。alicia 的 60 个 channel 全部 `keyframes=1`，所以求值代码里
"级间插值"那一半在真实资产上**从没执行过**。

### 15.10 那个最大的 bug：把「材质桶」当成「in-between 关键帧」

这是这一刀唯一的**功能性** bug，也是最值得记的一条。

**症状**：`verify_morph_gpu` 的 G2（"滑条 1.0 与 0.0 的像素差"）一直是
**0.000%**。而 `verify_morph.py` 的 34 项**全绿**。

**原因**：v2 的 channel 表里，同一个名字在多个子网格上各有条目（§15.4 说的
"target 下标是子网格内局部"）。`MorphRig::build` 按名字把它们合并成一个
channel，`points` 里于是有多个 `(subMesh, target)` —— **它们的 `weight`
全是 1.0**。

第一版 `evaluate` 直接把这些点当成"关键帧链"来插值：

```cpp
// 错的那一版
const float w0 = points.front().weight, w1 = points.back().weight;
```

alicia 所有点 `weight == 1.0`，于是 `w <= points.front().weight` **恒成立**
（任何 `w ∈ [0,1]` 都 ≤ 1.0），走 `w0` 那支、只给 `points.front()` 赋值 ——
**一个滑条只驱动第一个材质桶**。眼睛动了，脸没动。

**发现路径**（值得记）：加 `MYVK_MORPH_DBG=1`，每 30 帧打一条 `MORPH-FRAME`
把每个槽位的 `targets` / 权重基址 / `w0` 都 dump 出来，看到

```
[0 d=0 w=0 n=7]w0=0.00  [2 d=... w=... ]w0=0.00  [3 d=... w=...]w0=1.00
```

只有 1 个桶到位。**如果没有这份 dump，"像素差 0%"这个现象可以有一百种解释。**

**修法**：先把点按 `targetWeight` 去重成"级"，再在级之间插值。

```cpp
// 1) 去重成级（同一 targetWeight 上的多个桶是同一级，不是相邻帧）
constexpr std::size_t kMaxLevels = 64;
float lv[kMaxLevels]; std::size_t nl = 0;
for (const Point& p : rc.points) {
    if (nl > 0 && p.weight <= lv[nl - 1] + 1.0e-6f) continue;
    if (nl == kMaxLevels) break;
    lv[nl++] = p.weight;
}
if (nl == 0) continue;

// 2) 定位区间：w 落在哪两级之间
float scW[2] = {-1.0f, -1.0f}; float scV[2] = {0.0f, 0.0f};
if (w <= lv[0]) {
    scW[0] = lv[0];
    scV[0] = (lv[0] > 1.0e-6f) ? std::min(w / lv[0], 1.0f) : 1.0f;  // w<首级 → 按比例
} else if (w >= lv[nl - 1]) {
    scW[0] = lv[nl - 1]; scV[0] = 1.0f;                              // 超出末级 → 饱和
} else {
    std::size_t j = 0; while (j + 1 < nl && lv[j + 1] < w) ++j;
    const float span = lv[j + 1] - lv[j];
    const float t = (span > 1.0e-6f) ? (w - lv[j]) / span : 1.0f;
    scW[0] = lv[j]; scV[0] = 1.0f - t;
    scW[1] = lv[j + 1]; scV[1] = t;
}

// 3) 逐点取它所在级的系数，同级的点全部拿到同一个系数
for (const Point& p : rc.points) {
    if (p.target == kNoMorphTarget) continue;
    float s = 0.0f;
    if (scW[0] >= 0.0f && std::abs(p.weight - scW[0]) <= 1.0e-6f) s = scV[0];
    else if (scW[1] >= 0.0f && std::abs(p.weight - scW[1]) <= 1.0e-6f) s = scV[1];
    if (s > 0.0f) add(p.subMesh, p.target, s);
}
```

关键在于第 3 步的**循环覆盖所有点**，而不是只取 `front/back`。修完 3 个
桶全部 `w0=1.00`，G2 从 0.000% → **0.048%**。

写入走带边界检查的 `add` lambda（越界写 = 堆破坏，且崩在几帧之后，看不出
是 morph 干的）。

**防回归**：新增判据 **G4d** —— 最后一帧 `MORPH-FRAME` 里 `w0=1.00` 的槽位
数 **≥ 2**。这条判据专门守这个 bug：它不检查"有没有形变"，而检查"是不是
**只有一块**在形变"。G2 从 0% 变成 0.048% 也能过"大于 0"的断言，但只有
G4d 能挡住"只动一只眼睛"这种半残状态。

### 15.11 验收：为什么数据层 34 项全绿还是漏了

这一刀最大的方法论收获：**数据层的断言与"看起来对不对"之间有一个断层。**

`verify_morph.py` 现在 34 项，覆盖：区块字节自洽、版本、三条硬校验、
88 对 delta 全部非空、位移长度分布、channel 表结构（F1~F5）、offset_weights
预乘（G1）、运行期 channel 数与磁盘唯一名字数一致（E5/E6）。它**全绿**，
而 GPU 上一块脸都不动。

原因不是断言写得差，是**断言的对象选错了**：

- 数据层能证明「delta 流里有 18132 条非零位移，且 target 下标不越界」；
- 它**不能**证明「求值函数把这 18132 条按正确的系数喂给了着色器」。

那个 bug 活在**求值层**，而求值层唯一的输出就是像素。所以：

`verify_morph_gpu.py`（15 项，四次启动只差控制台命令）：

| 判据 | 守什么 |
|---|---|
| G0 / G0b / G0c | 截到图 / 视口矩形 / **视口里有内容（≥5% 非背景）** |
| G1 | `base` 与 `zero` **逐像素相同**（关掉功能 = 回到基线）|
| G2 | `zero ≠ on`，差异 ≥ 0.02% |
| G3 | on 的包围盒变化 ≤ 55%（防"整个人飞出去"）|
| G4a / G4b | `morph.set` 成功 / 失败各一条 |
| G4c | `MODEL-INSTANCE ... mesh=20 skinned=1 morph=49` |
| **G4d** | **最后一帧 `w0=1.00` 的槽位数 ≥ 2** |
| G5 | `bad`（不存在的名字）与 `base` 逐像素相同 |
| G6 | 无崩溃 |

G0c 是被一个坑逼出来的：手写场景 JSON 里放 `skinned` 块，视口一片空白，
而 G1 显示"逐像素相同"、G5 也"通过"—— **空场景让逐像素断言平凡成立**。
`docs/anime_gap_audit.md` §9.7 记过这条（手写 `skinned` 只建
`SkinnedMeshComponent`，20 个子网格是 `instantiateModel` 建的），但我自己
又踩了一次。所以现在脚本走 `MYVK_EDITOR_IMPORT` 真实导入入口，并且**先
证明视口里有东西**，再比像素。

环境变量（四次启动只有 `MYVK_EDITOR_CONSOLE_CMD` 不同）：

```
MYVK_EDITOR_SCENE=scenes/_m15_cam.json      ← 只有相机 + 地面
MYVK_EDITOR_IMPORT=models/characters/alicia.fbx
MYVK_EDITOR_CONSOLE_CMD=morph.set target_7 1.0
MYVK_EDITOR_CONSOLE_CMD_FRAME=70
MYVK_EDITOR_NO_HUD=1
MYVK_LOG_RECTS=1
MYVK_MORPH_DBG=1
```

相机走**场景文件**的 `camera` 块（`applyCamera` 直接设值），不用
`MYVK_EDITOR_CAM` —— 后者走 `setTarget(eye + forward*distance)`，飞行模式
下 position 会被**再推一次** `distance`，角色变成几十像素一团。

## 16 · 第八刀：两骨 IK + 挂点 + `findJoint` 收敛（2026-10-25）

§15 之后角色已经"能动"，但只能**照着动画动**：脚落在动画里写好的地方，
手抓不到场景里的东西。这一刀把"目标点"接进来 —— 从**场景空间的一个
坐标**反推出关节该怎么转。

三件事合成一刀，理由和 §15 的四条欠账一样：它们共用**同一个中间层**。

| 件 | 落点 | 为什么必须在同一刀 |
|---|---|---|
| 两骨 IK | `animation/TwoBoneIK.*` | 要"找骨"——先得把名字匹配收敛掉 |
| 挂点 | `animation/BoneAttachment.*` | 要"读关节世界矩阵"——和 IK 反推的是同一组量 |
| `Skeleton::findJoint` | `assets/Skeleton.*` | 前两件都在找关节，而 `Animator` / `LookAt` 里各写了一遍 |

`findJoint` 不收敛的话，这一刀会**新增第三、第四份**名字匹配代码，而三份
之间的差异（要不要跳 `Head_end`、要不要不区分大小写）会变成"同一个名字在
IK 里找得到、在 LookAt 里找不到"这类没有报错的幽灵问题。

### 16.1 为什么是解析解，不是 FABRIK

两骨 IK 有一百种做法，其中绝大多数是**迭代**的（FABRIK / CCD）。这里选
余弦定理的闭式解，只有一个理由，但它足够硬：

> **这一刀必须能断言"同一输入逐位相同"。**

迭代解的不确定性不是"精度差一点"，而是"停机条件依赖上一步的结果"：
浮点下同一个 pose 两次求值几乎总会在最后一位分叉，尤其在 `acos` 边界附近
（腿快伸直时）。那样的实现能出画面，但你写不出 `ik_deterministic` 这条
断言 —— 而这条断言是"关掉功能逐像素回到基线"的地基。

两骨刚好有闭式解：

```
已知 A(root) B(mid) C(end) 与目标 T
L1 = |AB|, L2 = |BC|, d = clamp(|AT|, |L1−L2|, (L1+L2)·maxReachScale)

cosA = (L1² + d² − L2²) / (2·L1·d)     → angA = acos(cosA)
cosB = (L1² + L2² − d²) / (2·L1·L2)    → 弯曲角 = 180° − acos(cosB)
newB = A + (dirAT·cos(angA) + bendDir·sin(angA)) · L1
```

`dirAT ⟂ bendDir` 且两者都是单位向量 → `dirAT·cos + bendDir·sin` 也是
单位向量，`× L1` 恰好落在半径 L1 的球上。**不需要归一化，也不会越界。**

### 16.2 极向量必须从当帧动画反推

用户明确点了这一条，它不是"三种给法里的一种"，而是**默认**该走的那一种。

`bendDir` 决定"膝盖朝哪边弯"。给法有三种：

| 给法 | 来源 | 失效场景 |
|---|---|---|
| `PoleFromAnimation`（默认） | 把 `(mid − root)` 投影到 ⟂`root→target` 的平面上 | 动画里这条腿完全伸直 → 投影为零 |
| `PoleFromVector` | 配置的 `poleVector` 的垂直分量 | 配置与目标方向平行 → 投影为零 |
| 退化兜底 | `cross(dirAT, +X)`，不行再 `cross(dirAT, +Y)` | 两次都平行（几乎不可能） |

**为什么不能缓存成一个常量**：膝盖朝向随动画在变 —— 走路时朝前、蹲下时朝
前下方、踢腿时朝侧面。缓存一个常量的症状是"蹲下时膝盖朝着正前方，一站直
膝盖就转到侧面去了"，而且**不报任何错**。这类"只在某些姿势下错"的 bug
靠日志和数值断言都抓不到，只能靠"每帧重新反推"从根上避免。

投影公式本身就是这个意思：

```cpp
bend = ab − dot(ab, dirAT) · dirAT;   // ab = B − A，当帧算出来的
```

注意它是 `ab` 的**垂直分量**，不是 `ab` 本身 —— 平行分量（沿目标方向的
那部分）不参与"往哪边弯"，保留它只会让 `bendDir` 被拉向目标方向。

`ik_pole_follows_anim_a/b` 是这一条的断言：同一组 target、两种不同的
动画姿势（膝在左 / 膝在右），`bendAngleDeg` 相同但 `mid` 落在目标的**两侧**。
只断言弯曲角的话，缓存常量的实现也能通过。

### 16.3 自动解析：*最长子骨*，且显式配错就整条拒绝

`root` 不给名字时依次试 `thigh / upleg / upperleg / upperarm / uparm`
（**腿在前** —— 两骨 IK 的主战场是"脚贴地"，手部抓握大多数时候动画本身
就够了。宁可默认选中腿，也不要默认不生效）。

`mid` / `end` 不给名字时选**父骨是上一根、且 `restLocal` 平移最长**的那根：

```cpp
// restLocal 是"父骨相对量"，它的平移长度就是骨长 —— 不需要 FK
len = length(translationOf(joints[j].restLocal));
return bestLen > 1e-5f ? best : -1;   // 零长度辅助骨不算候选
```

`restLocal` 而不是 `invBind` 里凑：这是**静止姿势**的骨骼长度，与当前
动画姿势无关，所以链的解析结果**不随姿势变**（否则 `ik.list` 在不同帧会
给出不同的链，没法断言）。零长度的子骨（DCC 里常见的"同点辅助骨"）必须
排除，否则 `L1 = 0`，下面 `cosA` 的除零直接出 NaN，整条腿消失。

显式给了名字但**不成链**（mid 的父不是 root）→ **整条链拒绝**，报
`resolved=0`。不"就近凑一根"：凑出来的链会在下面用错父骨坐标系，症状是
"配了 IK 之后腿一直歪着"，而日志显示一切正常。

### 16.4 可达区间：`maxReachScale = 0.999` 不是 1.0

```
dmin = |L1 − L2| + 1e-4        ← 两骨"折叠到底"的距离
dmax = (L1 + L2) · maxReachScale
```

取 `1.0` 时，目标恰好等于臂长 → `cosA = 1.0000001` → `acos` 返回 NaN →
**整条链从视口里消失**（不是"偏一点"，是完全没了）。0.999 留了 0.1% 的
余量，视觉上看不出"差了 2 mm"，但把 NaN 从数学上排除掉了。

下界那一侧也有故事：目标比 `dmin` 还近时链**折不起来**，只能折到极限，
多余的距离变成"够过头"—— 这是几何事实，不是 bug。`ik_too_close_fold`
断的就是"目标贴脸时弯曲角 ≈ 180°"（真的折到底了）。

目标够不着时**如实报**：`actual = |target − end|` 走一次完整 FK 实测
（不是解析推 `|reachable − target|`），`ANIM-IK ... miss=1`。真实渲染里
这是最阴的一条 —— 角色看着没够到，日志说"够到了"，人就不查了。

### 16.5 求解流程：第二根骨的父骨旋转必须用**改完之后**的 root

```
pose --FK--> world(A,B,C)
     --余弦定理--> newB
     --shortestArc--> qA（root 的世界增量）
     --写回 root 局部-->  W'(root) = qA · W(root)
     --用 W'(root) 共轭 qB--> 写回 mid 局部
     --再 FK 一次--> 实测 end 误差
```

第二根骨那一步是整条链最容易写错的地方，所以写进了 `.cpp` 文件头：

> ⚠ 第二根骨的"父骨世界旋转"必须用**改完之后**的 root（`W'(root) = qA·W(root)`），
> 不是改之前的。用错的那一版看起来也能动，但 mid 的旋转被套在一个已经转过
> 的坐标系里，症状是"腿越弯，脚踝偏得越多"，而伸直时完全正常 —— 极难从
> 画面反推。

世界增量 → 局部增量用共轭：`R'_local = P⁻¹ · q · P · R_local`（P = 父骨
世界旋转）。`worldRotationOf` 用**第 0 列长度**归一化而不是
`quat_cast(mat3 / determinant)`：均匀缩放 s 的 3×3 行列式是 s³，除完得到
`R/s²`，既不正交也不归一，`quat_cast` 在非正交矩阵上给的是近似值。

`weight < 1` 时两根骨各 `slerp` 一半 —— 于是末端**不在**目标上，这是"半开
IK"的定义。要"半开且仍落在目标上"，正确做法是把**目标点**插值到当前末端
（软 IK），不是插值旋转。那是另一种语义，不进这一刀。

`weight = 0` 在函数第一行就 `return`，**一行 pose 都不碰**：`slerp(q, q, 0)`
在浮点下不是恒等，晚一行就有一次。这是"关掉逐像素回到基线"的唯一保证。

### 16.6 挂点：`jointMatrices[j]` 不是骨骼的世界矩阵

这是整刀最容易误解的一处。`jointMatrices` 里的东西是

```
jointMatrices[j] = invMeshNode · world(j) · invBind(j)
```

—— **"顶点该怎么动"的矩阵**，不是骨骼在哪。想拿到骨骼的世界矩阵要
把它反推回来：

```
subTransform · jointMatrices[j] · invBind(j)⁻¹ = YupToZup · world(j)
```

`subTransform`（`SubMesh::transform`）里含着 Y-up→Z-up 那一转，所以反推
出来的已经是引擎空间，可以**直接**接到宿主的 `worldMatrix` 上，不需要
再乘一次场景变换。

为什么可以随便取一个子网格的 `transform`：蒙皮路径本身要求所有子网格共享
同一个 `meshNodeWorld`（否则 `invMeshNode` 与 `meshNodeWorld` 约不掉，
蒙皮早就已经歪了）。所以这不是新假设，是沿用现有路径的前提。

写完的矩阵还要转成**局部**（`TransformComponent` 的语义）：有层级父时
先除掉父世界矩阵，没有时就是世界矩阵。写错这一处的症状是"挂点跟宿主走了
两步"（宿主自己是父的时候），或者"挂在别的物体下的挂点位置偏一个父位移"。

`|det(parentWorld)| > 1e-12` 才求逆：父的 0 缩放会让 `inverse` 出 NaN，
而 NaN 位置会让整个物体的包围盒变成 NaN → 它从视口里**消失**，日志里只有
剔除统计少了一个。

### 16.7 `Skeleton::findJoint`：两轮匹配，末端过滤只作用于第二轮

收敛成"一个函数 + 一组标志位"，而不是三个函数：

```cpp
enum JointMatchFlags : unsigned {
    kJointMatchExact           = 0u,
    kJointMatchCaseInsensitive = 1u << 0,
    kJointMatchSubstring       = 1u << 1,
    kJointMatchSkipEndTips     = 1u << 2,
};
constexpr unsigned kJointMatchDefault = kJointMatchCaseInsensitive |
                                        kJointMatchSubstring |
                                        kJointMatchSkipEndTips;
```

末端辅助骨的判据是**包含** `end / tip / nub`，不是"以 `_end` 结尾"：
Blender 写 `Head_end`，3ds Max Biped 写 `HeadNub`，Mixamo 写 `HeadTop_End`，
UE mannequin 写 `head_end`。三种写法，只有"名字里出现这三个词之一"是共通的。

**精确那一轮不过滤**，这是这一刀修掉的一个真 bug：

> 两轮都过滤 → 显式写 `Head_end` 的人永远拿到 -1。而且比"匹配错"更难查：
> 调用方会以为资产里没有这根骨。

空名字返回 `-1` 而不是 `0`：空名字的语义是"没指定"，"自动挑一根"是上层
的事（`LookAt` 用默认骨名，IK 用 `kAutoRootNames[]`）。

`findJointsWithPrefix` 顶掉 `SpringBone` 里那份前缀扫描（头发/裙摆要的是
**一组**骨，返回 `vector<int>`），前缀语义是"以它开头"，与 `findJoint` 的
"包含"不同 —— 头发 `hair` 不该匹配到 `ponytail_hairband` 之外的东西。

### 16.8 序列化：`poleMode` 存字符串，不存整数

`ik` / `attach` 两段都紧跟 `lookAt` 之后落盘。`poleMode` 存
`"animation"` / `"vector"`：存整数的话，以后往枚举中间插一档，老存档会
**静默**错位（`0` 还是 `0`，但含义变了）。这类 bug 只在读老工程时才发作，
而那时候已经没人记得枚举当初是什么顺序了。

`hasNonMeshContent` 补 `ik` / `attach`（**两处**：写出时与读入后各一次）。
顺带发现原来漏了 `springBone` / `lookAt` —— 同一个 bug 的四个实例，症状都是
"整个场景只有角色，于是在某些路径上被当成'空场景'处理"。

### 16.9 三层顺序：LookAt → IK → 弹簧骨

三者最终都落在 `Pose::rotation`（**局部**旋转），所以必须在 `poseToJoints`
之前跑。区别只在改几根骨：LookAt 一根、IK **两根**（root + mid，末端只被读）、
弹簧骨一条前缀链上 N 根。三者都不写平移 —— 骨长不变是 FK 的前提，也是
"脚落在目标上"能用余弦定理解的前提。

顺序的三条理由（都写在 `AnimatorSystem.h`）：动力学必须读最终姿势；接触
约束应该最接近最终姿势；前两层默认不重叠但**不假设**它们不重叠
（`rootBone` 完全可以配成 `neck`，那时顺序就有语义）。固定顺序的价值不是
"反正互不影响"，而是"同一帧两次求值逐位相同"这条可断言的性质。

### 16.10 验收

**数值（无窗口，`verify_anim_runtime`，从 64 → 100 条，这一刀加 36 条）**

| 组 | 条数 | 关键判据 |
|---|---|---|
| `find_joint_*` / `find_prefix_*` | 9 | 精确 / 包含 / 末端过滤 / **末端精确仍能命中** / 空名 -1 |
| `ik_*` | 22 | 链解析 6 · 求解 8 · 极向量 2 · 退化 3 · 集成 2 · **对照组** 1 |
| `attach_*` | 5 | 数量 / 跟随动画 / 真的移动 / 缺失计数 / 缺失时保持原变换 |

其中三条是"没有它等于没写"的：

- `ik_control_gt_10cm` —— **对照组**。不解算时末端离目标 > 10 cm。没有
  对照组，"能落到目标上"可以靠"目标本来就离得不远"蒙过去。
- `ik_deterministic` —— 同一输入两次逐位相同。这是选解析解的核心理由。
- `ik_weight_zero` —— `weight=0` 姿态**逐位**不变（不是"接近"）。

**像素（`verify_ik.py`，12 项，4 次启动只换 console 命令）**

| 判据 | 实测 |
|---|---|
| K0c 视口里真有内容 | content = 65.93%（空场景会让 K1 平凡通过） |
| K1 `weight=0` == 没开 IK | diff = **0.0000%**（逐像素） |
| K2 IK 改变了像素 | diff = 2.6532% |
| K2b 只动了局部 | 差异包围盒 = 12.56%（一条腿） |
| K3 脚落在目标上 | `actual=0.0000 miss=0 bone=LeftFoot` |
| K5 够不着如实报 | `actual=0.1245 miss=1 bend=5.1°` |
| K7 自动解析在真实资产上成立 | `LeftUpLeg>LeftLeg>LeftFoot` |

K7 是这一刀对**真实资产**的唯一证据：`ik.list` 在 alicia 上自动解析出
`LeftUpLeg > LeftLeg > LeftFoot` —— auto root 命中 `thigh`，`longestChild`
两次都选中了正确的那根（大腿→小腿、小腿→脚）。

挂点走**两条独立算法互校**：系统路径用 `jointMatrices · invBind⁻¹`，
断言路径用 `samplePose + poseToWorld` 纯 FK。只信一条的话，"把
`jointMatrix` 直接当骨骼矩阵用"也能自洽通过（那个实现里两个错误恰好抵消，
因为它算出来的东西和它自己比）。

### 16.11 踩坑记录

- **`diff_stats` 返回的是占比 0..1，不是百分数。** 这是这一刀最大的判据
  bug：我按百分数写了阈值，于是 K0c 严了 100 倍（真的把 66% 读成 0.66%
  判红），而 K2b 的 `bbox <= 45.0` 对上实测 `0.13` **恒真** —— 等于那条
  判据根本不存在。恒真的判据比红的判据更危险：它让你以为覆盖了。
  正确写法全部对齐 `verify_morph_gpu.py`（`>= 0.05` / `>= 0.0002` /
  `<= 0.45`）。
- **机位是判据的一部分。** 第一版用 3.4 m 全身机位，66° 屈膝只改 **83**
  个像素（0.0099%），刚好卡在噪声边界上。收到 1.9 m + 把目标抬到膝盖
  高度后腿宽 ~28 px，同样的动作改几百像素，信噪比从 1.2× 提到 10× 量级。
  "能过但其实很脆弱"的判据比红更糟。
- **`msvc-build.cmd build VennEditor` 第一次 exit=1。** 上一次会话遗留的
  `Editor.exe` 还被进程持有，产物写不进去。重跑 exit=0，`build_ik.log`
  里 0 个 error。**认日志，不认退出码。**
- **`find_joint_substring` 第一版红（actual=2 expected=3）。** 根因是
  "两轮都过滤末端骨"，见 §16.7。修法不是改期望值，而是补了一条
  `find_joint_endtip_exact` 把这个反例钉住。
- **`ANIM-IK` 在 400+ fps 下仍然刷屏。** 主锚点按 `frames % 60 == 1`
  节流是对的（一帧一行就够），但探针脚本里又套了一层 `seen` 去重才清爽。
- **`AnimationSelfTest` 里的假骨架不能省。** 真实资产上没法构造
  "L1 ≈ L2 且目标贴脸"（那是几何退化，不是动画），也没法让两根骨重合。
  假骨架 + 定值断言（`ik_bend_deg = 49.0`）才是余弦定理的正确性证据。

### 16.12 已知局限 / 下一步

- **只支持两骨链。** 脊柱那种 5~7 根的链、手指那种 4 段链都不行。多骨
  要么 FABRIK（放弃逐位确定性），要么逐段两骨迭代（外推，误差累积）。
- **`weight < 1` 时末端不在目标上**（§16.5）。软 IK（插值目标点）是另一
  种语义，没做。
- **不支持"目标在大腿上"的自碰撞规避。** 两骨解只保证"落在球面上"，
  不保证"不穿模"。
- **极向量只从动画反推，没有"极向量跟踪目标"（pole target object）** ——
  那是 DCC 里的另一个物体引用，需要先有实体引用字段。
- **挂点只跟一根骨，没有"两骨之间插值"**（比如挂在膝盖和大腿中点）。
- **非均匀缩放的骨架不支持**（§16.5）。DCC 导出的骨架都是均匀缩放，
  这条链上没有良定义，所以不假装支持。
- **下一刀：⑥ 表情 / 面部 SDF。** 之后再回头做 ③ 的扩展（多骨链 /
  软 IK / pole target）。
