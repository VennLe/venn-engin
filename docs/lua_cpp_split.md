# C++ + Lua 双语言：各管哪一半

> 定稿 2026-11-03。回答一个问题：**同一台引擎里有 C++ 也有 Lua，边界画在哪。**
>
> 前置：`code_env_2026-11-03.md`（现状与三种语言的选择成本）。
> 本文不重复"要不要换"，只谈"换完之后怎么分工"。
>
> ⚠ 数字口径：本机源码 grep + 实测构建。改动前重跑。

---

## 0 · 一句话判据

> **Lua 只做「决策」，C++ 只做「执行」。**
>
> Lua 决定**往哪走、打谁、什么时候开门、血少于 30 % 播什么**；
> C++ 负责**怎么走、伤害怎么算、门怎么转、骨骼怎么动**。

这条判据的好处是**可判定**——任何一个功能，问一句"它是在做决定还是在做计算"，
答案就出来了。比"C++ 快 Lua 慢"好用得多（后者永远可以争论）。

三条推论，后面所有分工都从这里来：

| # | 推论 | 落地 |
|---|---|---|
| 1 | **乘法归 C++** | 每帧 × N 实体 × M 字段的开销，一律在 C++ |
| 2 | **决策归 Lua** | 频率低、变化快、需要"改一行立刻看"的，一律在 Lua |
| 3 | **对象归 C++，句柄归 Lua** | Lua 手里只有 `entity`（{id, generation}），没有指针、没有 `void*` |

## 1 · 五条划分准则

按重要性排。前两条能解决 80 % 的争论。

### 准则 1 · 看「每帧乘不乘 N」

```
每帧 × 1 次        → Lua 随便写（一个机关、一个门、一次对话推进）
每帧 × 10 次以内    → Lua 可以（但要数调用次数，见 §4）
每帧 × 上百次       → C++（一次跨语言调用 ≈ 100 ns，1000 次就是 0.1 ms，1 万次就是 1 ms）
每帧 × 每个顶点/粒子 → 只有 C++
```

### 准则 2 · 看「改一行要不要重编译」

| 内容 | 改动频率 | 结论 |
|---|---|---|
| 数值平衡（伤害系数、掉率、冷却） | 每天 | **Lua** |
| 关卡机关（顺序、条件、触发区） | 每天 | **Lua** |
| 剧情分支（C7 的 `conds` / `writes`） | 每天 | **Lua** |
| 渲染管线 Pass 顺序 | 一年几次 | C++ |
| 组件字段布局 | 一年几次 | C++ |

**改得越勤的越该进 Lua**——这是引入 Lua 的**唯一正当理由**。如果你的内容三个月不动一次，
它留在 C++ 更好（不增加跨语言复杂度）。

### 准则 3 · 看「崩了毁多少」

| 崩了会怎样 | 放哪 |
|---|---|
| 编辑器挂掉、未保存场景全丢 | **必须 C++**（且要被审查） |
| 整局游戏冻结、玩家进度全丢 | **必须 C++** |
| 一个 NPC 不动了、其他照常 | **Lua**（每个实例独立熔断） |
| 一段对话卡住、玩家能跳过 | **Lua** |

⚠ **这条决定了 Lua 必须保留"每实例熔断"**：现在 `.vks` 是死循环 3 帧内停、只停一个实例。
换成一个全局 `lua_State` 之后，`while true do end` 会冻住**整个 VM**——
所以 **Lua 必须配 `lua_sethook` 的指令预算**，否则这条纪律会丢（见 §3.3）。

### 准则 4 · 看「要不要存盘」

| 项 | 结论 |
|---|---|
| 存档 **schema**（字段名、版本号、迁移规则） | **C++**。格式必须稳定十年 |
| 存档里**存什么值** | Lua 可以决定（但通过 C++ 的 `setProp` 写进去，不直接写表） |
| Lua 的**表**直接序列化进存档 | **禁止**。表的键序不稳定、类型不可控、没有版本迁移 |

⚠ 这条最容易被违反：Lua 写起来太自由，很容易把整个状态搁在一张表里。
一旦这张表进了存档，**下次改脚本就会让老存档读不出来**。

现在的 `ScriptVarsComponent`（`attr/setAttr` 黑板）就是正确形态：
脚本私有状态存在**组件**里，序列化由 C++ 管——Lua 沿用这条，别另开一套。

### 准则 5 · 看「要不要确定性」

确定性是本引擎验收体系的地基（回归逐字符比日志）。三条硬约束：

| 项 | 谁必须管 |
|---|---|
| **随机数** | **C++**。`gameplay::GameRandom` 有种子、可复现；Lua 的 `math.random` 不许用 |
| **容器遍历顺序** | C++ 用 dense 数组（定序）；Lua 的 **`pairs` 禁用**，只给 `ipairs` 或 C++ 返回的有序数组 |
| **时间** | 只用 `dt` / `simTime`，不许 `os.clock()` / `os.time()`（这两个库索性不注册） |

## 2 · 逐模块分工

### 2.1 必须是 C++（12 个）

| 模块 | 行数量级 | 为什么不能是 Lua |
|---|---|---|
| `core/`（窗口 / 输入 / 时间 / 日志 / 内存） | — | 每帧、系统调用；脚本拿不到 `GLFWwindow*` 是**结构性安全** |
| `rhi/`（Vulkan） | — | 每帧、驱动交互；崩了没法恢复 |
| `render/`（Pass 序 / 管线 / 材质 / 分簇） | — | 每帧 × 每 draw call；**Pass 顺序错了画面就错**，不能让脚本碰 |
| `ecs/`（组件存储 / 场景图 / BVH） | — | 每帧、内存布局、deterministic 遍历 |
| `assets/`（导入 / 烘焙 / `.pak`） | — | 阻塞 IO、几十 MB 内存 |
| `physics/`（求解器 / 接触） | — | 每帧 × 每刚体 |
| `audio/`（混音 / 总线） | — | **实时线程**，绝不能进脚本 |
| `animation/`（骨骼 / 蒙皮 / 图求值） | — | 每帧 × 每骨骼 |
| `navigation/`（navmesh 生成 / A*） | — | 图算法、内存 |
| **`script/`（VM 宿主层）** | 8165 | 这是 Lua 的运行底座，自己不能是 Lua |
| `editor/` 的引擎接口 | 90233 | 编辑器不能跑在脚本里（编辑态不跑脚本是铁律） |
| 序列化 schema / 打包 | — | 见准则 4 |

**注意 `engine/gameplay/` 不在这个表里**（5410 行：`Stats` / `TurnQueue` / `CardZones` /
`GameRandom` / `DamageNumbers`）。它是**灰区**，见 §2.3。

### 2.2 适合 Lua（6 类）

| 内容 | 现在的样子 | 为什么该进 Lua |
|---|---|---|
| **关卡玩法脚本**（巡逻 / 门 / 机关 / 开关） | `enemy_patrol.vks` 40 行 | 改一行 = 0.5 s 看效果，这就是 Lua 换来的全部价值 |
| **对话 / 剧情流程** | C7 的 `conds` + `writes`（已有条件求值） | 分支条件本质是"决策"，写在数据里已经别扭，写 Lua 才顺 |
| **UI / HUD 行为**（血条何时闪、数字何时弹、提示何时出） | 现在是 `setHealth` / `popup` 窄动作 | 改得最勤的表现层逻辑 |
| **拾取 / 背包 / 合成 / 升级规则** | `pickup.vks` | 规则密集、数值常调 |
| **关卡胜负条件 / 波次生成** | `GameState` 是 C++ 状态机 | "什么时候进 GameOver"是决策，现在写死在 C++ 里 |
| **过场 / 演出的触发时机** | C1 时间轴是资产数据 | **时间轴数据留资产**，触发条件用 Lua |

⚠ 第 5 条值得单独说：`runtime/GameState.h` 现在是 C++ 的
`enum StateId { Boot, Loading, MainMenu, Playing, Paused, GameOver }` + 状态栈。
**状态栈本身**（`blocksUpdate` / `blocksRender` 两个布尔量）是**机制**，留 C++；
**"什么时候压栈/出栈"**（血尽 → GameOver、到达终点 → 下一关）是**决策**，该给 Lua。

### 2.3 灰区（5 个，各有判据）

灰区不是"随便"，是"按判据切"。

| 灰区 | 切法 | 判据 |
|---|---|---|
| **AI：行为 vs 寻路** | 行为树/状态机 → Lua；navmesh 求路 → C++ | "算一条路"是图算法；"选哪个目标"是决策。现在的 `navGoto` 已经是对的形态：**Lua 说去哪，C++ 算怎么去** |
| **动画状态机** | 图求值 → C++；**切换条件** → Lua | 每帧 × 每骨骼必须在 C++；"血量 < 30 % 播受伤"是 Lua。⚠ 现在的 `AnimatorComponent` 是 0 可写字段，要接投影表 |
| **物理交互** | 求解 → C++；"该不该推" → Lua | 力的大小是数值（可以 Lua 给），作用点与积分是 C++ |
| **回合制结算**（`gameplay/`） | 数值容器 + 结算原语 → C++；**结算顺序与触发条件** → Lua | 见下方 |
| **存档** | schema + IO → C++；"存什么" → Lua | 见准则 4 |

#### 灰区详解 · `engine/gameplay/` 怎么切

这 5410 行是全项目**最适合当接缝**的地方，因为它**没有渲染依赖、纯数据与算法**。

```
  Lua 侧（编排）                          C++ 侧（原语）
  ─────────────────                       ─────────────────
  谁先行动                                 TurnQueue::advance（行动条推进）
  用什么技能                                Stats::applyModifier（属性结算）
  打谁 / 打几个                             Stats::computeDamage（公式）
  什么时候结算                              CardZones::draw / play（抽牌/出牌）
  胜负判定                                  GameRandom::next（有种子，可复现）
```

**为什么数值公式留 C++**：它是**确定性**的来源（`GameRandom` 有种子），
而且一旦进了 Lua，同一份公式会在多个脚本里被复制粘贴出 N 个版本——
平衡调整就变成"改 N 处"。C++ 里只有一处。

**为什么编排给 Lua**：编排是"内容"，一天改三遍。放 C++ 里就是每次 67.8 s。

## 3 · 接缝：四个必须现在定的决策

这四条不是"以后再说"——它们决定了后面所有代码的形状。

### 3.1 一个 `lua_State`，还是每实体一个？

**推荐：一个全局 `lua_State` + 每实体一个 `_ENV` 表。**

| 方案 | 内存 | 跨实体通信 | 模块共享 | 熔断 |
|---|---|---|---|---|
| **每实体一个 VM** | 一个空 `lua_State` 约 20~30 KB → 1 千实体 = 20~30 MB ❌ | 要序列化 ❌ | `require` 各一份 ❌ | 天然隔离 ✅ |
| **一个 VM + `_ENV`** | 只有表，几百字节/实体 ✅ | 直接传 entity ✅ | `require` 共享 ✅ | **要靠 hook** ⚠ |

选后者的理由：**A 打 B 是玩法里最常见的事**。两个实体在两个 VM 里，
"把 A 的伤害算到 B 身上"就得跨 VM 序列化——这一条就足以否掉多 VM。

代价：**必须自己做指令预算**（§3.3），否则一个死循环冻住全场。

### 3.2 脚本挂载粒度：一个实体一个脚本，还是允许"管理器"？

现在 `.vks` 是 **一实体一脚本**（`ScriptComponent` 挂在实体上）。
Lua 应该放开这一条——否则"关卡管理器"（管波次、管胜负）只能挂在一个假实体上。

**建议**：`ScriptComponent` 认两种挂载：

| 挂载 | 生命周期 | 典型用途 |
|---|---|---|
| 实体绑定（现在这样） | 实体存在就 tick | 巡逻兵、门、拾取物 |
| **场景级**（无实体，场景一加载就跑） | 场景加载到卸载 | 关卡管理器、波次、胜负判定 |

⚠ 场景级脚本**不能有 Transform**，也不该出现在 BVH 里——现在 `GameStartComponent`
就踩过这个坑（"出生点没有网格 → 点选/落地要单独开口"）。

### 3.3 熔断：Lua 的 `while true do end` 会冻住整个 VM

这是换 Lua **最实在的代价**，必须现在就解决。

现在 `.vks` 的保护：每实例每帧的步数预算 + 总预算，超了置 `failed`，**本实例后续帧不再执行**
（`ScriptInstance::failed`），其他实例照常。

Lua 里同样的保护要靠 **`lua_sethook` 的 count hook**：

```cpp
// 伪代码：每 1000 条 VM 指令查一次预算，超了就 luaL_error（长跳回 C++）
lua_sethook(L, [](lua_State* L, lua_Debug*) {
    if (++budget > kStepsPerFrame) luaL_error(L, "script budget exceeded");
}, LUA_MASKCOUNT, 1000);
```

⚠ 两个坑：
1. **`lua_error` 是 `longjmp`**，不是 C++ 异常。它会**跳过 C++ 的析构函数**。
   所以绑定层里**绝不能有"注册了 `lua_error` 之后还持有需要析构的 C++ 对象"的代码**——
   所有 C++ 侧临时对象必须在调 `lua_*` 之前析构干净，或用 `lua_pcall` 包住。
2. **C++ 异常不能穿过 Lua**。引擎里 `loadFBX` 是会 `throw` 的（`fbx_asset_pipeline.md`
   记过这个坑）→ 绑定层**每个** C++ 函数都要 `try/catch(...)` 转成 `lua_error`，
   否则一个异常穿过 Lua 的 C 栈就是 UB（大概率崩在莫名其妙的地方）。

### 3.4 热重载：Lua 怎么"保状态"

现在 `.vks` 靠 `Stmt::id`（源码先序序号）对账：id 能对上 = 从原位置继续，对不上 = 整体重启。
Lua 没有这个概念，换 `_ENV` 方案后：

| 保留什么 | 怎么做 |
|---|---|
| **实例变量** | 就是 `_ENV` 表本身 —— 换 chunk 时**不换这张表**，`let` 沿用"存在才初始化" |
| **协程挂起位置** | Lua 的协程是**对象**，换 chunk 后旧协程的 `pc` 指向旧函数 → **只能重启那个协程**（不是整个实例） |
| **闭包捕获的 upvalue** | 旧闭包活在新 chunk 里 = 悬空 → 强制重建 |

⚠ 结论：**Lua 的热重载是"变量保留、协程重启"，比现在的"按语句 id 精确续跑"弱一档**。
这条要写进文档，别让人以为换了 Lua 热重载会更强。

## 4 · 性能预算（可执行的数字）

标准 Lua 5.4（**不是** LuaJIT）的量级：

| 操作 | 开销（量级估计） |
|---|---|
| Lua 调一个 C 函数（无参数转换） | ~50~100 ns |
| 带 vec3 / entity 参数转换 | ~150~250 ns |
| Lua 内部一条算术指令 | ~5~10 ns |
| Lua 相对 C 的纯计算 | 慢 **20~50 倍** |

**于是预算很清楚**：

```
  每帧 Lua→C++ 调用 ≤ 1 万次   →  ≈ 1~2 ms   （可接受）
  每帧 Lua→C++ 调用 ≈ 10 万次  →  ≈ 10~20 ms （掉帧）
```

对照现状：`enemy_patrol.vks` 每帧调 **4 次**（`pos` × 2、`dist`、`setPos`）。
**100 个敌人 = 400 次/帧**，连预算的 5 % 都不到——这个量级 Lua 完全够用。

⚠ **真正会踩的坑不是"Lua 慢"，是"在 Lua 里写 N²"**：

```lua
-- ❌ 1000 个实体 = 100 万次 C++ 调用 = 每帧 100~200 ms
for _, e in ipairs(allEntities()) do
    if dist(pos(e), pos(self())) < 5 then ... end
end
```

正确形态是现在的 `near(pos, r)`——**C++ 侧走 BVH，一次调用返回一个有序数组**。
这条已经是现有设计（`script_roadmap.md` S-D5 的"限界说明"），Lua 要沿用，别退化。

## 5 · 迁移路径（如果真要做）

顺序不可跳，前一步不做后一步就是白干。

| 步 | 做什么 | 为什么必须在前 |
|---|---|---|
| **0** | **补绑定（投影表）** 7 → 16 个组件 | 不补，Lua 侧也只能写 15 % 的东西，换语言等于白换 |
| **1** | 抽 `IScriptBackend`（编译 / 实例 / tick / 变量枚举 四个虚函数） | 现在 `ScriptRuntime` 直接持有 `ScriptProgram`，换后端 = 重写 605 行 |
| **2** | vendor Lua 5.4 + 绑定壳（103 个内建 → `engine` 表） | `ScriptHost` 的 `std::function` 原样复用，只换调用壳 |
| **3** | `.vks` 与 `.lua` **共存**，按 `ScriptComponent` 的扩展名分派 | 老脚本一个字不改，新玩法用 Lua |
| **4** | 补 §3.3 的 hook 预算 + §3.4 的热重载语义 | 不补会丢掉"坏脚本不冻住游戏"这条 |
| **5** | 把 `GameState` 的"何时压栈"、`gameplay/` 的"结算顺序"迁到 Lua | 这一步才是真正把"玩法"搬过去 |

⚠ 第 3 步之前不要动 `GameState` / `gameplay/`——**先证明 Lua 能跑通一条完整玩法**，
再迁基础设施。反过来做的话，Lua 侧一有问题，你分不清是"绑定错"还是"迁移错"。

## 6 · 反面清单：这些千万别放 Lua

| 别放 | 为什么 | 正确做法 |
|---|---|---|
| 每帧遍历全场景算距离 | N² 次跨语言调用 | C++ 提供 `near()`（已有，走 BVH） |
| 逐粒子 / 逐顶点的计算 | 每帧 × 上万 | 粒子系统 C++，Lua 只调 `playEffect` |
| 资源加载 | 阻塞 IO，卡一帧 | 预加载；Lua 只按名取已加载的 |
| 存档读写 | 同上 + 格式稳定性 | C++ 管 IO 与 schema |
| 随机数 | 破坏确定性 | `GameRandom`（C++，有种子） |
| `os.clock` / `os.time` | 破坏确定性 | 只用 `dt` / `simTime`，**这两个库索性不注册** |
| `pairs` 遍历 | 键序不稳定 → 回归无法逐字符比 | 只给 `ipairs` 或 C++ 返回的有序数组 |
| 渲染状态 / Pass 顺序 | 画面会错，且难查 | 配置在 C++ / 资产里 |
| 编辑器逻辑 | 编辑态不跑脚本是铁律 | 编辑器永远 C++ |

| # | 判据 | 落点 |
|---|---|---|
| 1 | 一条完整玩法（巡逻 + 拾取 + 开门 + 胜负）**纯 Lua 写完**，零 C++ 改动 | 这是"分工成立"的总判据 |

## 8 · 一页纸回答

- **C++ 管什么**：所有"每帧 × N"的东西 —— `core / rhi / render / ecs / assets / physics /
  audio / animation / navigation`，加上 **脚本宿主层本身**（VM、绑定、熔断、热重载）
  和**存档 schema**。一句话：**引擎与执行**。
- **Lua 管什么**：所有"改一行要重编译"的东西 —— 关卡玩法、剧情分支、HUD 行为、
  拾取规则、胜负条件、演出触发。一句话：**内容与决策**。
- **灰区怎么切**：`gameplay/`（5410 行）当接缝 —— **数值公式与随机留 C++，编排顺序给 Lua**；
  AI 是"行为 Lua / 寻路 C++"；动画是"图求值 C++ / 切换条件 Lua"。
- **四个现在就要定的**：① 一个 `lua_State` + 每实体 `_ENV`；② 允许场景级脚本；
  ③ `lua_sethook` 指令预算（否则死循环冻全场）；④ 热重载是"变量保留、协程重启"，
  **比 `.vks` 的精确续跑弱一档**。
- **顺序**：**补绑定 → 抽后端 → 接 Lua → 共存 → 补熔断/热重载 → 迁玩法**。
  第 0 步不做，后面全白干。
