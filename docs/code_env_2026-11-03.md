# 代码环境：现在是什么方案，C++ / Lua / C# 该选哪个

> 定稿 2026-11-03。回答三件事：① 现在的代码环境是什么；② 三个候选语言的**真实**成本；
> ③ 下一步该做什么。
>
> **数字口径**：`engine/script/` 源码 grep、`--selftest script`、本机 `make build` 实测。
> ⚠ 数字会漂，**改动前重跑，别拿这份当基准**。
>
> 姊妹文档：`script_language_assessment.md`（能力边界）· `script_roadmap.md` §2（为什么自研）
> · `script_api.md`（函数签名）。本文只补"**语言选型**"这一个角度，不重复它们。

---

## 0 · 结论先行

| 候选 | 判决 | 一句话 |
|---|---|---|
| **C++** | **已经在用；缺的是分层，不是语言** | 47/47 组件全可达，但改一行 `Components.h` 要重编 **75** 个 TU、**67.8 s** |
| **Lua** | **唯一值得换，但不是现在** | 净收益只有「调试器 + 函数/模块」，**不增加组件覆盖** |
| **C#** | **不建议** | 运行时依赖 + 绑定生成工具链 = 数月工程量，换「写得舒服一点」 |

**真正的结论**：

> 引擎**不缺代码环境**（两层都活着）。缺的是**脚本层的手**——绑定只覆盖 **7/47** 个组件；
> 和**脚本层的脸**——引擎里看不到 103 个函数、没有内联编辑、没有变量检视、没有断点。
>
> 这两件事**换任何语言都要做**。换语言只会让它们更贵，不会让它们变简单。

## 1 · 现状：代码环境是三层，只有两层是活的

```
  L0  C++（engine/ + editor/ + runtime/）   47/47 组件 · 全字段 · 改一行 = 15 s ~ 数分钟
       │
  L1  .vks（engine/script/，自研树遍历 VM）   7/47 组件 · 103 个内建 · 改一行 = 0.5 s 热重载
       │
  L2  可视化（蓝图 / 节点图）                ❌ 不存在
```

### 1.1 实测数字

| 项 | 实测值 | 口径 |
|---|---|---|
| 脚本引擎规模 | **8165 行**（`engine/script/` 6 个文件） | `wc -l` |
| 引擎总规模 | **约 24.8 万行**（engine 14.7 万 + editor 9.0 万 + runtime 8.5 千 + launcher 2.2 千） | `wc -l` |
| 脚本引擎占比 | **3.3 %** | 8165 / 248000 |
| 内建函数 | **103 个**（`kBuiltins[]` 表长，含 `vec3` / `atan2`） | 正则数表 |
| 语句种类 | **8 种**：`Assign` / `ExprStmt` / `If` / `While` / `Block` / `Let` / `Foreach` / `Wait` | `Stmt::Kind` |
| 表达式种类 | **8 种**：`Number` / `Str` / `Bool` / `Var` / `Unary` / `Binary` / `Call` / `Member` | `Expr::Kind` |
| **有没有函数定义** | **没有**（`Stmt::Kind` 里没有 `Function` / `Return`） | 同上 |
| ECS 组件 | **47 个** | `engine/ecs/Components.h` |
| **脚本能写字段的组件** | **7 个 = 15 %** | 见 §1.2 |
| 示例脚本 | 4 个 / **603 行**（含模板三份） | `find -name *.vks` |
| 热重载延迟 | **0.5 s**（轮询，成功才替换） | `ScriptAsset` |
| 调试器 | **没有**（断点 / 单步 / 调用栈 / 变量内容全无） | grep 零命中 |
| 全量编译 | **58 s**（Debug，文档旧记录） | 见 `usability_2026-11-03.md` |
| **改一个 3888 行的 .cpp** | **15.4 s**（含链接 4 个 exe） | 2026-11-03 实测 |
| **改一行 `Components.h`** | **67.8 s**，重编 **75 个 TU**（418 个 obj 中的 18 %） | 2026-11-03 实测 |

> ⚠ 这两个数字是**同一天同一台机器**测的，差距 **4.4 倍**，且差别不在"文件大小"，
> 在**扇出**：`ScriptEngine.cpp` 只被 6 个文件 include，`Components.h` 被 **75 个**。
> 这就是「加一个组件字段 = 去泡杯茶」的真实来源。

### 1.2 「手有多短」—— 逐组件清点

脚本能**写字段**的（7 个）：

| 组件 | 能做到 | 做不到 |
|---|---|---|
| `TransformComponent` | `pos/setPos` `rot/setRot/rotY` `scale` `move/rotate/scale` 及其 `By` 版 | — |
| `RigidBodyComponent` | `vel/setVel` `impulse` | 质量 / 阻尼 / 重力系数 / 睡眠 |
| `VisibilityComponent` | `visible/setVisible` | — |
| `PointLightComponent` | `setColor/setIntensity/setRange` | 阴影开关 / 衰减模型 |
| `SpotLightComponent` | 上面三个 + `setDirection` | 内外锥角 |
| `MaterialComponent` | **只有 `setEmissive`** | 全部 PBR 因子、贴图槽 |
| `ScriptVarsComponent` | `attr/setAttr`（脚本自己的黑板） | ——它本来就不是玩法数据 |

能**间接驱动**的（2 个）：`NavAgentComponent`（`navGoto` 四件）、`AnimatorComponent`（`playAnim`）。

只能**读**的（3 个）：`NameComponent`（`name`）、`HierarchyComponent`（隐式 self）、
`CharacterControllerComponent`（`grounded`）。

**其余 35 个组件，脚本一行代码都没有。** 最扎眼的三条：

- **`CameraComponent` —— 29 个字段，可达 0。**
  运镜体系（焦距 / 快门 / 景深 / 路径 / 手持）**一条脚本都改不了**。
  "被击中时推焦到 85 mm + 抖一下"只能回 C++。
- **`ParticleEmitterComponent` —— 0。** 脚本点不着特效（`playEffect` 是预制体，不是发射器参数）。
- **`DirectionalLightComponent` —— 0。** `setIntensity` 只认 point/spot；
  对只有主光的实体调用会**返回 0 不报错**——和"脚本没跑"长得一模一样。

## 2 · 与业界对照：脚本层是否好用，取决于「绑定是否自动化」

| 引擎 | 内核语言 | 脚本层 | 脚本层可达 | 热重载 | 调试器 |
|---|---|---|---|---|---|
| UE5 | C++ | Blueprint（编译成字节码） | 全部（UHT 反射） | 蓝图 VM 天然 | ✅ 蓝图调试器 |
| Unity | C++（不开放） | C#（Mono / CoreCLR） | 全部（反射） | ✅ domain reload | ✅ |
| Godot | C++ | GDScript（自研） | 全部（反射 + ClassDB） | ✅ | ✅ |
| Defold / LÖVE / 老 CryEngine | C++ | Lua | 全部（注册表） | ⚠ 靠 reload 惯例 | ✅ Lua 调试器 |
| **本引擎** | **C++** | **.vks（自研）** | **15 %（手写绑定）** | ✅ 0.5 s | ❌ |

三条规律，按重要性排：

1. **有反射的引擎，绑定是零成本的**（Unity 的 `GetComponent<T>()`、Godot 的 `ClassDB`、
   UE 的 `UHT`）。**本引擎没有反射表**（`script_roadmap.md` S-D5 明确不做）→ 每加一个可写字段
   都要人手写一处。
2. **用 Lua 的引擎，绑定靠注册表**——比手写 `std::function` 简单，但**表里有什么还是人写的**。
   所以「换 Lua 能加快绑定」这句话**只对了一半**：写调用壳更快，**决定暴露哪些字段**一样慢。
3. **所有主流引擎的脚本层都是「全可达」的**。Unity 的 C# 能碰每个组件，Godot 的 GDScript 也是。
   **没有一个主流引擎的脚本层只够得着 15 %。**

> 所以 15 % 这个数字不是「语言选错了」，是**绑定没做完**。
> 换语言改变的是第 2 条（写壳快慢），改变不了第 1 条（有没有反射）和第 3 条（覆盖多少）。

## 3 · 三个候选，逐条算账

### 3.1 C++ —— **已经在用，问题在分层不在语言**

**现状**：`engine/` 全部是 C++，47 个组件全字段可达。用户今天写玩法逻辑，写的就是 C++。

那为什么感觉「不可上手」？三个具体原因：

| 痛点 | 实测 | 换语言能解决吗 |
|---|---|---|
| 改一个组件字段要重编 75 个 TU，**67.8 s** | `Components.h` 扇出 75 / 实测 | ❌ 换语言反而更糟（要维护两套） |
| 玩法代码和引擎代码混在一个 `engine/` 里 | 没有 `game/` 目录 | ✅ 这是**分层**能解决的 |
| 写错就崩编辑器，状态全丢 | 进程内 | ⚠ 只有「独立进程」能解决，代价极高 |

**如果要做「C++ 游戏模块（DLL）」**，要付的成本：

- **ABI 纪律**（不是"加个 `dllexport`"这么简单）：
  同一个 MSVC 大版本 + 同一个 CRT + **不允许 STL 类型跨边界**（`std::string` / `std::vector`
  的布局是编译器实现细节）+ 异常不跨边界 + 内存必须用引擎的分配器分配、引擎的分配器释放。
- **热重载极脆**：`FreeLibrary` 在有静态对象 / 后台线程时**直接失败**，
  通行的绕法是「复制成临时名再 Load」——UE 的 Hot Reload 就这么干，业界口碑是"能用但会咬人"。
- **崩溃带走编辑器**：现在 `.vks` 死循环只停**一个实例**（3 帧内熔断），DLL 崩了要重启编辑器
  + 丢掉未保存场景。
- **失去确定性**：C++ 可以开线程、读系统时间、用随机数 → 回归**无法逐字符比日志**。
  这是本引擎验收体系的地基（`script_roadmap.md` S-D11）。

**判决：做「分层」，不做「热重载」。**

```
  ✅ 建议                            ❌ 不建议
  game/ 目录 + IGameModule 窄接口     C++ 模块热重载（Live Coding）
  玩法代码不碰 engine/                 （只在 Game.exe 里安全，
  编译时间从「改引擎」降到「改游戏」     编辑器里做就是拿稳定性换）
```

`IGameModule` 的形态（约 200 行接口 + 300 行加载器）：

```cpp
// game/IGameModule.h —— 只有三个入口，全是 POD 或引擎自己的类型
struct GameModuleDesc { const char* name; int apiVersion; };
extern "C" {
    GameModuleDesc venn_game_module();
    void venn_game_start(scene::Scene*);        // 只拿到场景，拿不到 VkDevice / AudioSystem
    void venn_game_tick(scene::Scene*, float dt);
    void venn_game_stop(scene::Scene*);
}
```

**为什么 `game/` 层值得做，而不是让用户改 `engine/`**：
① 编译面从 418 个 obj 缩到个位数；② `engine/` 的 147k 行不再被用户代码污染；
③ 将来真要换脚本后端，`game/` 和 `engine/` 的接缝不变。

### 3.2 Lua —— **唯一值得换，但现在不该换**

| 维度 | 评估 |
|---|---|
| **能买到** | ① **函数 / 表 / 模块**（现在 `Stmt::Kind` 里根本没有 `Function`，逻辑只能复制粘贴）② **成熟调试器**（lua-debug + VSCode，断点/单步/变量/调用栈全有）③ 协程天然（`coroutine` 比现在手写的 ip 帧栈简单） |
| **要付** | ① vendor 约 3 万行 C（**离线可接受**，与现有 ufbx / nlohmann 同量级）② 绑定壳 1.5~2.5k 行（`ScriptHost` 的 `std::function` 可原样复用，只换调用壳）③ **热重载要重做**——现在靠 `Stmt::id`（源码先序序号）对账，Lua 里没这个概念 |
| **会失去** | ① **确定性**：Lua 的 `pairs` 遍历顺序不保证 → 必须禁用或包装，且**每个新脚本都要 review** ② 安全边界从「**结构性**不可能」退化成「注册表白名单，**漏一个就是后门**」③ `kBuiltins` 编译期解析（拼错 = 编译失败）的**单点控制力** |
| **不会买到** | ⚠ **组件覆盖率一点都不会涨**（还是 7/47 —— 绑定表是人写的，跟语言无关） |

**`script_roadmap.md` §2 定的退出条件**（3 条里中 2 条就换）：

| # | 条件 | 现在 |
|---|---|---|
| 1 | 需要在脚本里定义**可复用的函数 / 结构体**，且已写满 3 个以上关卡 | ❌ 4 个示例脚本、0 个关卡 |
| 2 | 需要一个**真正的调试器** | ❌ 但正在靠近（见 `script_language_assessment.md` 缺口 2） |
| 3 | 需要**第三方生态**（对话树 / 行为树库） | ❌ |

**当前 0 / 3。不换。**

**但有一件事现在就该做**：把 `ScriptRuntime` 和 `ScriptProgram` 之间的耦合抽成
`IScriptBackend`（编译 / 实例 / tick / 变量枚举 四个虚函数）。现在 `ScriptRuntime` 直接持有
`ScriptProgram`，换后端 = 重写 `ScriptRuntime`（605 行）。抽完之后，换后端 = **新增一个实现**。

> 这条不是"提前设计"，是**给退出条件留门**。现在的代码是「换 = 重写」，抽完是「换 = 加一个文件」。

### 3.3 C# —— **不建议**

| 项 | 内容 |
|---|---|
| **运行时** | CoreCLR 自包含发布 **60 MB+** / Mono 十几 MB。与「离线构建 + 单 exe 出包」直接冲突：`dist/` 从 200 MB 起 |
| **宿主 API** | `hostfxr` / `mono embedding`，C API + 平台相关。MSVC 链接没问题，但**版本耦合**（换 .NET 主版本要重测全链路） |
| **绑定生成** | **这是杀手**。Unity 能做 C# 是因为它有完整反射 + IL 后处理 + 一个团队维护的绑定生成器。本引擎**没有反射表** → 47 组件 × 平均 10+ 字段 = **500+ 个属性**，要么手写几千行，要么**造一个 C++ 头文件解析器**（等于再造一条工具链，还要引入 libclang） |
| **GC 边界** | 托管对象 ↔ `ecs::Entity` 句柄 / `std::function` 回调，每次回调都跨托管/非托管边界，要 `GCHandle` 管理 |
| **热重载** | `AssemblyLoadContext` 可以卸载，但「旧状态」「委托还挂着」是坑 —— Unity 的 domain reload 被骂了十年 |
| **能买到** | 语言表达力（LINQ / 泛型 / 委托）、成熟 IDE（VS / Rider 补全 + 调试）、Unity 用户的熟悉感 |
| **判决** | **不做**。除非目标是「对外开放、给别人用的引擎产品」—— 那时 C# 是**获客成本**，不是技术选择 |

一句话对比成本量级：

```
  补绑定（投影表）        ≈ 1 个里程碑
  抽 game/ 层            ≈ 1 个里程碑
  接 Lua（含后端抽象）      ≈ 1 ~ 2 个里程碑
  接 C#（含绑定生成器）     ≈ 4 ~ 6 个里程碑 + 永久运行时依赖
```

## 4 · 推荐路径：三步，**与语言无关**

### 第 1 步 · 补齐绑定（投影表）—— 这是换任何语言都躲不掉的

按 `script_language_assessment.md` §4 的白名单字段投影层做：

```vks
setProp(cam, "camera.focal", 85)                  # 现在：完全够不着
setProp(self(), "directional.intensity", 2.0)     # 现在：静默失败
setProp(self(), "particle.rate", 60)              # 现在：够不着
```

- 一张 `PropField{name, type, offset, lo, hi}` 表描述一个组件的可写字段；
- 字段名**编译期**解析（走 `findBuiltin` 同一条路径）→ 拼错 = 编译失败，不是运行期静默；
- 目标：**7 → 16 个组件（34 %）**，玩法相关的基本齐了。

⚠ 硬约束两条：被投影的字段必须满足 `std::is_standard_layout_v`（`offsetof` 的前提）；
表里没有的字段**脚本根本写不出来**（这是它和"反射"的区别，也是它安全的原因）。

### 第 2 步 · 分出 `game/` 层

让用户的重逻辑有地方放，不用改 `engine/`。`IGameModule` 三个入口（见 §3.1）。
编译时间从「改引擎」降到「改游戏」，并且**给 C++ 一个正式的定位**——
它不是"脚本的替代品"，是"脚本写不动的那些东西的出口"（大规模遍历、自定义空间划分、
第三方库胶水）。

### 第 3 步 · 补编辑体验（比换语言便宜 10 倍，收益在本项目上更大）

| 补什么 | 现在 | 成本 |
|---|---|---|
| **面板内 API 参考** | 103 个函数在引擎里**看不到**，全靠手抄 `docs/script_api.md` | 小：从 `kBuiltins` 表直接生成，不手写 |
| **内联编辑器** | 改一行要切 VSCode 再切回来按 reload | 小：`InputTextMultiline` + 保存 + 自动 reload |
| **变量检视** | Instances 页签只显示**变量个数**，不显示内容 | 小：`vars` 已经是 `(键, 值)` 列表，画出来即可 |
| **编译失败要显眼** | 现在是「成功才替换」→ 旧版本还在跑，**你以为改了** | 小：面板红字 + 行号 |

这四件加起来**远小于**接一次 Lua，而它们正是「可上手性低」的直接来源。

## 5 · 什么时候该换（可判定的触发条件）

写下来是为了**将来不纠结**。命中任一条就动手，没命中就不动。

| 触发条件 | 换成 | 为什么 |
|---|---|---|
| 需要在脚本里定义**函数**，且已经写满 3 个关卡 | **Lua** | 复制粘贴的玩法代码会失控 |
| 需要**真正的断点 / 单步 / 调用栈** | **Lua** | 树遍历 VM + 单协程 + 无函数 → 「没有栈可看」，自己造调试器性价比为负 |
| 需要第三方生态（行为树 / 对话树 / 状态机库） | **Lua** | 生态是买不到的 |
| 玩法里出现「每帧遍历上万实体」的性能瓶颈 | **C++ `game/` 层** | 这是**下沉**，不是换语言 |
| 要把引擎交给别人用，且对方明确要求 C# | **C#** | 那是获客成本 |

⚠ **反过来的三条不算触发**（都会被误当成理由）：

- ❌ "Lua 更流行" —— 流行度不解决 7/47。
- ❌ "C# 写起来爽" —— 爽的是写的人，付运行时和工具链的是维护的人。
- ❌ "别人的引擎都有脚本语言" —— 本引擎**有**，而且 103 个内建、0.5 s 热重载、
  双宿主一致、逐位确定性，这四条比大多数自研脚本层都强。

## 6 · 判据（做完怎么证明）

| # | 判据 | 落点 |
|---|---|---|
| 1 | `prop` / `setProp` 覆盖 **≥ 16 个组件**，字段数 ≥ 120 | 表长 |
| 2 | 写不存在的字段名 → **编译期**失败（否定测试） | 投影表真的在拦 |
| 3 | `setProp(e,"transform.pos",v)` 与 `setPos(e,v)` **逐位相等** | 语义无漂移 |
| 4 | 脚本改 `camera.focal` → `CINE-STATE` 的 `fovEff` 跟着变 | 跨系统联动，不只字段变了 |
| 5 | 对没有该组件的实体 `setProp` → **报错**（不是返回 0） | 修掉静默失败 |
| 6 | 老脚本（4 个 `.vks`）逐位不变，`sceneHash` 不变 | 不破坏 |
| 7 | `game/` 层：改一行玩法代码 → 编译 **≤ 3 s** | 分层真的省了时间 |
| 8 | 面板内能搜到 103 个函数名，点一下插入 | 可发现性 |
| 9 | `IScriptBackend` 抽出后，`ScriptRuntime` 不认识 `ScriptProgram` | 换后端的门留好了 |

## 7 · 明确不做（写下来为了不反复讨论）

| 不做 | 原因 |
|---|---|
| 现在换 Lua | 退出条件 0/3；换了**不解决**组件覆盖（15 % 原地不动） |
| 接 C# | 运行时依赖 + 绑定生成工具链，4~6 个里程碑换"写得舒服" |
| C++ 模块热重载（编辑器内） | `FreeLibrary` 脆弱 + 崩溃带走编辑器，与熔断纪律正面冲突 |
| 反射式 `getComponent(e,"X")` | 破坏结构性封闭；投影表是它的**有白名单替代** |
| 可视化节点图 | 成本高于 S0~S6 总和；**只能在投影层之后**作为第二套前端 |
| 脚本里创建 / 销毁实体 | 生命周期与存档一致性（`spawn` 已有，销毁另议） |

## 8 · 一页纸回答

- **「现在是什么方案」** → **两层活的 + 一层没有**：L0 C++（47/47 可达）、
  L1 `.vks` 自研 VM（7/47 可达、103 个内建、0.5 s 热重载、无调试器）、L2 可视化（无）。
- **「能不能用 C++」** → **已经在用**。要修的不是语言，是**分层**：
  把玩法代码从 `engine/` 挪到 `game/`（`IGameModule` 三入口），
  编译面从 418 个 obj 缩到个位数（现在改一个组件字段 **67.8 s**，改一个 `.cpp` 才 15.4 s）。
  **不做 DLL 热重载**。
- **「能不能用 Lua」** → **能，而且是唯一性价比为正的换法**，但**现在不该换**：
  退出条件 0/3，且**换了不解决组件覆盖**。先抽 `IScriptBackend` 把门留好。
- **「能不能用 C#」** → **不建议**。没有反射表 → 500+ 个属性要手写或造绑定生成器；
  外加 60 MB+ 运行时依赖。这是拿一个数量级的工程量换"写得舒服一点"。
- **「那到底该做什么」** → 三件与语言无关的事：**补绑定（7→16 组件）**、
  **分 `game/` 层**、**补编辑体验（API 参考 / 内联编辑 / 变量检视）**。
