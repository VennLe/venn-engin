## 2 · E14 的四个真坑（都踩过、都留了取证）

### 2.1 浮层必须是**子窗口**，不能是独立顶层窗口
视口窗口本身是 ImGui 的焦点窗口，每帧都会把焦点窗口 `BringWindowToDisplayFront`
→ 独立顶层窗口会被推到列表前面、**被视口盖住**（第一版就是这么翻车的）。
子窗口的绘制永远在父窗口之后，天然压在 3D 画面之上。

### 2.2 浮层子窗口的高度必须用 `*WithSpacing()` 版本
`GetTextLineHeight()` / `GetFrameHeight()` 少算几像素 → 子窗口冒滚动条、
**最后两行被滚出可视区**（相机信息的第 9 个书签格就是这么丢的）。
统一改 `GetTextLineHeightWithSpacing()` / `GetFrameHeightWithSpacing()`，
并给所有浮层子窗口加 `NoScrollbar | NoScrollWithMouse`。

### 2.3 `VP-RECT` 日志**不能用来裁图**（本轮最大的排查）
`logRect` 是按 tag **去抖**的（同 tag 只在矩形变化 >4px 时才打一条）。
而视口首帧的布局用的是"启动那一刻的窗口尺寸"：先起小窗再 `SetWindowPos` 的话，
首帧会打一行小矩形，之后收敛到另一处 —— **日志里最后留下哪一条，取决于
resize 与首帧的先后**。实测同一份二进制能拿到
`(310,184)-(1238,776)` 和 `(310,184)-(1260,832)` 两种首值。

排查路径（可复用）：
1. 先用**整窗**逐像素比对证明"渲染其实没变"（两次抓图 0 差异）；
2. 再用相机差分（两次不同的 `MYVK_EDITOR_CAM`）定位视口真实边界；
3. 最后看**行方差**：视口底边之下那几行在 x=320..1200 上的 `std == 0`
   （纯面板背景）→ 真边界在 y≈776，不是 832。

教训：早期那张 `_venn_verify/e14/nohud_baseline.png`（950×648）就是按偏高的
首值裁的，多带了 56 行工具栏。现在一律：
- **整窗图比对**（`tools/vp_nohud_baseline.png` = 1578×844 全窗口）；
- 或视口内部那块稳定锚点 `VP_INNER=(330,200,1200,750)`。

### 2.4 `Shift+N` 切的是**模式索引 N-1**，不是"第 N 个按钮"
`Shift+2 → unlit(1)`、`Shift+5 → metallic(4)`、`Shift+6 → wireframe(5)`。
我第一版断言写"Shift+5 → wireframe"，脚本连按 4 次都失败 —— 不是注入丢键，
而是期望本身就错了。另外 `setViewMode(Wireframe)` 在设备不支持
`fillModeNonSolid` 时会**回退 Lit**，而且 `if (m == m_viewMode) return;`
会让日志完全不出现 —— 排查时别被"没有日志"骗了。

### 2.5 `logRect` 的"每帧都在打"是错的假设
`VP-RECT modebar/stats/cam` 这类矩形日志**不是逐帧刷的**。
想断言"这块还在不在画"，不能用"数矩形日志条数"，
于是新增了一行状态日志：

```
VP-OVERLAY master=1 modeBar=1 stats=1 camera=1 navGizmo=1
```
**只在状态变化时**打（`ViewportPanel::draw` 第 6 步，签名 `(m_showOverlay<<0)|(modeBar<<1)|…`）。
有了它，"点一下菜单 → 状态真翻了"与"读盘后生效了"才都是可断言的。

## 3 · E14 的四角分工与两层显隐（设计结论）

- 左上 = 视图模式条（8 格 + `view: xxx` 常驻名字）
- 右上 = 统计 HUD（10 行**逐项开关**）
- 左下 = 相机信息（pos/look/FOV/dist/Sensitivity/Grid/View… + **9 个书签** + 视口设置 popup）
- 右下 = 导航 gizmo（**从原左下角搬来** —— Blender 在左下、UE 在右下，两种都常见，按四角分工走）

两层显隐：
- **总闸** `m_showOverlay`（工具栏 HUD 勾选框，也是 `MYVK_EDITOR_NO_HUD` 的落点）；
- 总闸之上**四块各自一个开关**（`EditorContext::ViewportOverlay`），
  右键视口空白处 `Viewport Display` 菜单切换、随偏好落盘。

**这就是 NO_HUD 逐像素回归能成立的前提**：总闸一关，四块全灭，
3D 画面与改造前逐像素一致（整窗 0 差异，含面板边框）。

### 快捷键分层（数字键全被占满）
数字键本体已有两套：`1/3/7(+Ctrl)` = Blender 视图方向、`Alt+数字` = 面板显隐。
E14 三件事全挂 Shift 层：
- `Shift+1..8` 切视图模式
- `Ctrl+Shift+1..9` 存相机书签
- `Alt+Shift+1..9` 跳书签（**只恢复 yaw/pitch、保留当前注视点**——
  比连位置一起还原好用，"看一眼侧面再回来"不会把镜头甩走）

`handleViewShortcuts` 首行加 `if (io.KeyShift) return;`；
`handleOverlayShortcuts` 必须排在它**之前**调用。

### 浮层避让
`m_modeBarRight/Bottom` 每帧记录模式条边界；统计 HUD 顶边会撞上时自动下移。
模式条关闭时先把边界清零，否则统计 HUD 会永远留在下面回不到顶边。

## 9 · 全量 3 例红的定性：全是 harness 问题（不是回归）

全量 42 例跑出红的三例：`verify_bvh` / `verify_csm` / `verify_ibl`。
逐条查证后**全部是验证侧问题**，引擎/编辑器代码没动：

### 9.1 CSM / IBL —— 抓到了空白帧（`PrintWindow` flaky）

- 两例的**数值组断言全 PASS**（CSM：分割点逐项等于解析公式、级联裁剪矩阵、
  距离分级单调性；IBL：天空/辐照度/预过滤/BRDF 表回读），只有**像素组**红。
- 决定性证据：`csm_on.png`、`csm_cascades1.png`、`ibl_no_sky.png`、
  `ibl_redblue_sky.png`、`ibl_redblue_sphere.png` —— **全都恰好 4460 字节**，
  即 **1280×800 纯白整窗单色**。`csm_off.png` 是 285243 字节的正常图。
  空图 vs 正常图做差 → "差异铺满整窗（bbox=[0,0,1257,743]）/ 采样区全 255"，
  看起来特别像"阴影开关改变整幅画面"。
- 根因：`capture_nonempty` 只防 **0×0**，不防"尺寸正常但整幅纯白"
  （`PrintWindow(PW_RENDERFULLCONTENT)` 在 Vulkan 交换链上偶发返回未合成帧）；
  而 **csm/ibl 根本没走 `capture_nonempty`**，直接 `capture_client`。
- 修法：`capture_window.py` 新增 `_looks_blank()`（整窗下采样 32×20 后
  min/max 差 < 3 判空）+ `capture_stable()`（重试），`capture_nonempty` 转发；
  csm/ibl 改用 `capture_stable`。
- 验证：csm/ibl 单跑 **PASS**；另跑 7 支同样走 `capture_nonempty` 的用例
  （auto_exposure / color_lut / drs / hiz / light_modifiers / nav_gizmo /
  shader_variants）**7/7 PASS** → 加固无副作用。

### 9.2 BVH —— 右下角"空地"被 E14 的导航球吃掉了

- 首次跑的失败是注入 flaky（预热 10 次/21.8s 全没被收到）。加了"预热循环里
  每轮重抢前台"后，**拾取断言全 PASS**（`正中点击 -> Cube_0`、`same=1`），
  只剩"点空地要 miss"这条：`miss 日志 0 -> 0`。
- 真因：该用例点**视口右下角 94%,94%** 当"空地"。E14 四角布局把导航球从
  **左下搬到右下**（左上模式条/右上统计/左下相机信息/右下导航球），
  浮层是**子窗口**，会先吃掉落在自己身上的点击 → 视口 pick 不执行。
  用例里本来就有注释"**不能点左下角**——那里是导航小图标"，说明这坑早有，
  只是随导航球换了角。四个角现在全被浮层占了。
- 修法：该用例统一 `MYVK_EDITOR_NO_HUD=1` 启动（与 csm/ibl 同辙）。
  修后**PASS**，且预热点击从"10 次/21.8s 全落空"变成"**1 次/2.0s 收到**"
  —— 反向印证诊断。

### 12.1 head-line bug：`UBO 是记录期写、执行期读的内存`

**症状**：捕获出来的立方体**只有最后一个面有内容**，其余 5 面全是背景。
极易误诊成"cube-compatible 图像的逐面拷贝没生效"，或"面序搞反了"。

**真因**：`recordProbeCapture()` 原先在**循环外**取一次 `beginOneTime()`，
6 个面共用同一个相机 UBO 槽（`kProbeCaptureUboSlot = 8`）。UBO 是**记录期写、执行期读**
的内存 —— 一次 `vkQueueSubmit` 里，GPU 执行第 0 面时那块内存里**已经是第 5 面写进去的矩阵**。
于是 6 个面**全部**按第 5 面的相机渲染。而绘制列表是**记录期**按各面相机剔除的
（第 0 面的列表里只有 +X 那个物体），用"朝 -Z 的相机"去看它 → 落在 90° 视野外 → 该面只剩背景。

**修法**：
```cpp
static constexpr int kProbeFaceUboSlotBase = 64;   // 每面独占一个槽（base+0..5）
```
- **每面一个 UBO 槽**（不能 6 面共用一份）；
- **一个探针一次独立提交**（`beginOneTime()` 搬进探针循环）—— `rhi::CommandPool`
  的 cmd 缓冲**不能录两次/提交两次**，多探针必须各取各的；
- 基址 64 而非 0：离屏目标的槽 = `m_targets` 下标，留余量以免撞上。

**离屏目标早就踩过同一个坑**（`FrameResources::OffscreenUbo`）—— 这是第二次。
**通用教训**：**同一份 UBO 在同一个提交里给多个"视角/目标"复用，必然全用最后一份的值。**

**排查路径（可复用，值得记住）**：
1. 假设甲"cube-compatible 图像的拷贝必须 6 层一组" → **WebSearch 证伪**（标准立方体贴图
   加载器普遍逐层建 region，SaschaWillems 的 loader 亦然）；
2. 假设乙"缺内存屏障" → 加全量 `VK_PIPELINE_STAGE_ALL_COMMANDS_BIT` 屏障后**结果完全不变**
   → 不是同步问题；
3. **切分实验**：`MYVK_PROBE_SAMEFACE=1`（6 个面全用第 5 面的相机剔除 + 渲染）
   → **6 层全都有内容**（`PROBE-NZ` 六面各 4）→ 一击定案：**拷贝链路没问题，问题在渲染**。
   （临时钩子已完全移除，`grep -c "TEMP-DEBUG\|SAMEFACE"` = 0。）

**修复后取证**：`PROBE-MID` 六面中心色与摆放**逐面精确对应** ——
`+X=(3,0,0) -X=(0,3,0) +Y=(0,0,3) -Y=(3,3,0) +Z=(0.6,0.6,3) -Z=(3,1.2,0)`。
**面约定**（`vennCubeDir`）再次确认：`PX(+1,-uv.y,-uv.x) / NX(-1,-uv.y,uv.x) / PY(uv.x,+1,uv.y) /
NY(uv.x,-1,-uv.y) / PZ(uv.x,-uv.y,+1) / NZ(-uv.x,-uv.y,-1)`。

### 12.2 第二个真 bug：mip 链长必须与分辨率自洽

`MYVK_PROBE_PREFILTER_RES=8` + `_MIPS=5` → 2 条

（另把 `prefilterSize` 上夹 512、`prefilterMips` 上夹 8）。修后 `errs: 0`。

### 12.4 验收场地的因果闭环（设计要点）

## 14. ⚠⚠ 两个"不报错、但要命"的真 bug（本轮最值钱的两条）

### 14.1 计数管线漏声明 `VkPushConstantRange` → 一颗粒子都不画

- 症状：验证层每帧刷 `VUID-VkComputePipelineCreateInfo-layout-07987`。
- 后果（**比报错严重得多**）：`vkCmdPushConstants` 的落点**未定义**，而且
  `cfg.y`（总槽数）取到 0 → `count = min(counters, 0) = 0` →
  间接命令的 `instanceCount` **恒为 0** → 画面上一颗粒子都没有，
  而日志里除了那几行 VUID 什么都没说。
- 修：`VkPushConstantRange{VK_SHADER_STAGE_COMPUTE_BIT, 0, kCountPushBytes}`。
- **教训**：`VkPipelineLayoutCreateInfo` 里 push constant 的**范围**必须与着色器
  里 `layout(push_constant) uniform X` 那个块**逐字节一致**。`createPipelines()`
  里每个 compute 管线都要检查这一条，不能只给"要传参数的那个"声明。

### 14.2 有返回值的 lambda 缺 return → MSVC Debug 塞 trap → 整进程 SIGILL

- 症状：`MYVK_EDITOR_INSP_EXPAND="Particle Emitter"` 时 Editor.exe 以
  `exit=132`（`0xC000001D`，Illegal instruction）**瞬间**死掉，日志停在
  `INSP-EXPAND injected=...` 之后，**一个字都不多打**；不带 EXPAND 完全正常。
- 定位：① 逐个模块二分（fx/soft、fx/renderer、fx/noise、fx/rot 全崩）→
  ② 收窄到"只要展开组件就崩" → ③ 读回生成的 lambda，发现 `return false;` 与
  `ImGui::PopID()` **互换了位置**（把 `-> bool` 从签名去掉、把 `return opened;`
  换成 `if (opened) { ... body(); }`，却漏了那个 `return false;`）。
- 根因：`auto&& body` 版 lambda 的**返回类型是推导的**，被 `return false;` 推成
  `bool`，而函数末尾没有 return → **UB**；MSVC 在 Debug 下会在末尾塞一条
  **trap 指令**（`ud2`）。
- 修：`if (!moduleVisible(title, key)) return;`（**裸 `return;`**）。
- **教训（通用）**：写返回类型推导的 lambda 时，**任何一个 `return 值;` 都会把
  整条路径的返回类型定死**。要"提前退出"就用裸 `return;`，要么干脆显式写
  `-> void`。这一条值一整轮调试。

## 15. ⚠ 冻结帧的"确定性"到底是什么（**实测**，别凭直觉）

`MYVK_FX_FREEZE=N` 能保证的是**状态**逐位可复现，**不是像素**逐像素一致。
实测（FREEZE=120，各配置跑 3~4 次取最大两两差）：

| 配置 | alive | 像素平均差 |
|---|---|---|
| 1 颗、静止、无重力 | 1 | 0.0082 |
| 4 颗、静止、无重力 | 4 | 0.0029（n>18 = 0） |
| 4 颗、只受重力 | 4 | 0.0548 |
| 4 颗、初速 3.2 | 4 | 0.0462 |
| 4 颗、初速 32（10 倍） | 4 | 0.0289 |
| 364 颗羽流 + 软粒子 | 364 | 1.59 ~ 2.13 |
| 364 颗羽流 + 软粒子**关掉** | 364 | 0.058 |

`alive / draws / cap / maxAlive / simFrame / inst` 在**所有**配置的所有次运行里
**完全相同** —— 这才是"确定性"的验收面。

两条来源（都不是 bug、也都关不掉）：

1. **池按 frames-in-flight 分槽**（`m_frames[slot]`，各自有 framebuffer 和粒子状态）。
   每槽只在**自己**被派发的那一刻推进（`dtSlot = elapsedFrames * dt`），冻结之后
   各槽就停在**各自的最后一步**上、彼此差 1~2 步 → 恰好落在边界上的那颗粒子
   生或死不同 → 一整块粒子面积（≈250 px）变。
   **这条解释了为什么差异不随速度放大**（10 倍初速反而更小）——差的是**集合**，
   不是位移。**"一颗粒子也有 0.0082 的差"** 就是这条在单独起作用
   （软粒子开/关读数完全相同：0.008244 vs 0.008244）。
2. **紧凑表（alive list）的顺序来自 compute 里 `atomicAdd` 的完成顺序**，本来就不确定。
   加色混合数学上与顺序无关，但帧缓冲是 **8 位 UNORM**：每个片元的 `+=` 都要量化
   一次，顺序不同 → 舍入路径不同 → 差值随**重叠的部分覆盖率像素**增长。
   软粒子打开时 `fade` 是连续值（每个粒子到处都在贡献一点点），关掉退化成 0/1
   —— 这就是 364 颗那两行的 **27 倍差**。

⇒ 验收口径：**B1 状态逐位一致（精确，无阈值）+ B7 像素差有界（≤ 4.0）**。
`Renderer.cpp` 里原先写着"the image is now fully determined"的日志和
"验证脚本据此断言逐像素一致"的注释**都已改准**。

## 16. ⚠ 验证脚本这一轮的五条教训

1. **`结果: PASS` 是硬约定，我又踩了一次。** 脚本一开始打 `PASS: 全部通过`，
   而 `run_regression.py` 的 `OK_RE` 只认 `RESULT: PASS` / `全部断言 PASS` /

3. **新加一条 `FX-EMITTER` 诊断（`MYVK_FX_DBG=2`）**，把交给 GPU 的发射器数据用
   `%.9g`（float32 十进制往返精度）逐值打出来。序列化等价于是退化成一次

   ⚠ `%g` 默认 6 位会**把不同的值打成一样**，"相等"的结论就没意义了。

   脚本跑十几次里出现过一次 **0.261**。处置：`capture_pair()` **失败时重抓**

5. **测试期望值本身写错了三处**（都是"实现是对的、期望是错的"）：
   - E1a 注入 `fx/playback` 是**空操作**（playback 本来就默认展开），
     期望 `["playback"]` 必然失败；实得默认的 4 个。
   - D5 只展开组件、不展开模块：`modules=` 只登记**展开**的模块，被搜索命中的
     `noise` 默认折叠 ⇒ 再对也是 `(none)`。**必须先把 12 个模块全展开再搜。**
   - D5d 用 `"particle"` 测"只命中组件级关键词"的兜底 —— 它是

   过滤等于没生效。
   **通用教训：兜底条件必须与放行条件同源（同源判据），否则两者会互相打架。**
