## C++ / Lua 分工（新增 `docs/lua_cpp_split.md`）

用户已决定走 **C++ + Lua 双语言**，问「各自适合管什么」。给出判据 + 分工表。

**总判据：Lua 做决策，C++ 做执行**（可判定，比"C++ 快 Lua 慢"好用）。

- **C++ 管**（12 项）：core / rhi / render / ecs / assets / physics / audio / animation /
  navigation + **脚本宿主层本身** + **存档 schema** + 编辑器接口
- **Lua 管**（6 类）：关卡玩法 · 剧情分支 · HUD 行为 · 拾取规则 · 胜负判定 · 演出触发
- **灰区**：`engine/gameplay/`（5410 行）当接缝 —— **数值公式与 `GameRandom` 留 C++**
  （确定性来源，且避免公式在 N 个脚本里复制成 N 版），**编排顺序给 Lua**；
  AI = 行为树 Lua / 寻路 C++；动画 = 图求值 C++ / 切换条件 Lua

**四个必须现在定的决策**
1. **一个 `lua_State` + 每实体 `_ENV`**（每实体一个 VM：20~30 KB × 千实体 + 跨实体要序列化）
2. 允许**场景级脚本**（无实体，管波次/胜负）—— 现在是一实体一脚本，管理器只能挂假实体
3. **`lua_sethook` 指令预算**：否则 `while true do end` 冻整个 VM，现有的"3 帧熔断只停一个实例"会丢
4. 热重载语义变弱：**变量保留、协程重启**（Lua 协程 pc 指向旧函数），
   不如 `.vks` 的 `Stmt::id` 精确续跑

**性能预算**：Lua→C++ 一次 ≈ 100~250 ns → **每帧 ≤ 1 万次**（≈1~2 ms）。
现有巡逻兵每帧 4 次调用，100 个敌人 = 400 次，远在预算内。
⚠ 真正的坑不是"Lua 慢"，是**在 Lua 里写 N²**（`for e in allEntities()` 算距离）
→ 必须沿用 `near()` 这种 C++ 走 BVH 的形态。

**迁移顺序**：补绑定 → 抽 `IScriptBackend` → 接 Lua → `.vks`/`.lua` 共存 → 补熔断/热重载
→ 最后才迁 `GameState` 与 `gameplay/`。⚠ 第 0 步不做，后面全白干。

### ⚠⚠⚠ 本轮最贵的坑：`lua_resume` 第 4 个参数不能传 `nullptr`

Lua 5.4 把 `lua_resume` 从 3 参数改成 4 参数（多 `int* nresults`）。
`ldo.c:863` **无条件**解引用：`*nresults = (status == LUA_YIELD) ? ... : ...;`
→ 传 `nullptr` 就是往**地址 0** 写一个 `int` → `0xC0000005`。

**为什么极难查**（症状全部指向错误方向）：
- 崩在 `lua_resume` 内部，调用栈完整、协程栈内容正常（`fn` + `41` 都在）
- `lua_pcall` 跑同一段 chunk **完全正常** → 看着像"协程机制坏了"
- 独立小程序跑同一段协程代码 **也正常** → 看着像"引擎链接/编译方式坏了"

**走过的弯路（记下来避免重犯）**：
1. 先怀疑 Debug 运行时检查 → 给 `lua_static` 加 `/RTC- /GS-`
   —— ⚠ **`/RTC-` 不是合法选项**，cl 只报 `warning D9002` 然后**忽略**，
   等于什么都没改。MSVC 只有 `/RTC1 /RTCc /RTCs /RTCu`，**没有负形式**；
   要关掉 Debug 默认的 `/RTC1` 只能把它从 `CMAKE_C_FLAGS_DEBUG` 删掉。
2. 再试 `/O2` → `error D8016`（与 `/RTC1` 不兼容），库直接编不出来。
3. 用独立探针把「同源码 / 同开关 / 同 `lua_static.lib`」三种组合全跑一遍
   —— **全部正常**，才把"库/开关/语言/链接"整片排除。
4. 最后给 `Game.pdb` 挂 `dbghelp`（`SymFromAddr` + `StackWalk64`），
   崩溃栈直接打出 `lua_resume+0x201 (ldo.c:863)` —— 一眼定位。

**方法论**：「同一个库、A 程序崩 / B 程序不崩」时，**先怀疑两份调用代码本身
有差异**，再怀疑环境。探针当时写的是 `int nres; lua_resume(..., &nres)`，
而引擎里写的是 `nullptr` —— 差异就在那一行，却因为"探针能过"而被误读成
"环境和探针不同"。

**已内置的护栏**：`crashFilter` 现在是**符号化**的（`dbghelp` + `Game.pdb`，
`SymInitialize(proc, nullptr, TRUE)` 自己找 pdb），崩了直接给 函数+行号+20 帧
调用栈。以后再崩，第一轮就能看到位置，不用重建排查链。

### 顺手修掉
- `ScriptBackend.h` 前向声明 `class ScriptHost` → `struct`（`C4099` 是
  `LNK2019` 的前兆，见 MEMORY 纪律）。

## 收尾复查：C++ API 阶段留下的六处静默失效（已修 + J 组 7 条判据）

做完 C+ 组件覆盖之后又逐函数复查了一遍（问"跑三个月会怎么坏"），查出六处
**不报错不崩溃、只在特定时序下错**的问题 —— 106 条全覆盖的 G 组一条都没抓到。

1. **实体句柄被 `int` 截断**（最严重）：`engine.valid` / `world.setParent` /
   `game.joint` 用 `aInt()` 取参数 → `(gen<<32)|id` 的 generation 整段被截掉。
   只有"销毁过、槽位被复用"之后才错（valid 恒假、setParent 报 not alive、
   joint 挂到旧句柄）。修：`aHandle()`（`luaL_checkinteger`→`uint64_t`）。
2. **空句柄与"0 号实体"撞车**：打包 `(gen<<32)|id` 在 id=0,gen=0 时是 0，
   而文档一路写"空句柄=0" → `setParent(kid, 0)` 静默挂到 0 号实体（常常是玩家）。
   修：打包改 `((gen<<32)|id)+1`，0 = 唯一空句柄；`unpack(0)` → `Entity{}`。
   ⚠ 这条是 I1 断言先红才发现的。
3. **`ApiTable` 的 minArgs/maxArgs 从来没人查**（§8 那句"注册时按表校验"是假的）。
   修：绑定统一挂 `dispatch`，upvalue 带 `Impl*`+`ApiEntry*`，先核个数再进实现。
4. **顶层 chunk / `waitUntil` 条件函数不受熔断**（钩子只在 `doResume` 里装）→
   顶层写 `while true` 冻住进程。修：钩子提到文件级 `luaBudgetHook`，
   三处都装。⚠ 不能用 RAII（`luaL_error` 是 longjmp，析构跑不到，钩子会留在 state 上）。
5. **`camera.fov` 在定焦镜头下静默无效**：`focal>0` 时视场角由焦距算并覆盖 fov
   （`poseFromEntity`/`apply`/`applyCameraEntityTo` 三处）。修：写 fov 清 focal（打
   `LUA-CAMERA`）、读返回**实际生效**的 `focalToFovY`。
6. **`World::setName` 缺 `NameComponent` 时不补** → `Scene::find` 找不到。修：补组件
   （只在显式改名时补，`create()` 不补，否则存档/sceneHash 变）。
   顺带：`world.despawn` 现在先摘父节点 `children` 再销毁（否则 id 复用会删掉别人的登记）。

判据：**J 组 J0~J6**（`--selftest lua` 35 → **42** 条，全绿）。`J1` 是夹具前提
（销毁后重建必须复用同一 id 且 gen+1，否则测不到）。
顺带确认既有 flaky：`.vks` 的 `C8b 熔断后帧时间 <500ms` 在构建负载下会红
（508ms vs 空闲 421ms），与本次无关。

文档：`script_framework.md` §2.1 补 +1 编码/空句柄、新增 **§9.4**；
`script_api.md` §4/§6/§8 `world`/`camera`/§13；`script_api_reference.md` 已重生成。

# M5-c 收口：游戏 C++ 模块 = 一个**独立的 VS 工程**（用户新需求）

`<工程>/code/` = 一个能双击打开的 VS 工程：

```
MyGameGame.sln / .vcxproj / .vcxproj.filters   ← ★ 直写，不经过 cmake
CMakeLists.txt                                 ← 等价描述（CI / 非 VS）
include/venn/VennAbi.h                         ← ABI 快照（只读）
src/GameModule.cpp / src/Gameplay.cpp
bin/MyGameGame.dll                             ← 引擎从这里加载
```

创建流程：`3d` 段只写文件 → `commit` rename → `4c` 段把 `slnPath` 换成**最终**路径 →
launcher `openInVisualStudio()`。**生成物里一个绝对路径都没有**（`$(ProjectDir)` 编译期才展开），
所以 rename 不会让 `.sln` 失效。

## 这一轮最大的一个坑：`CreateProcessW` 的 87

现象：`cmake` 配置永远 `exit 1`，日志里只有 `GAMECODE CreateProcess failed error=87`。

排查链（错了两步才对）：
1. 先怀疑"`CREATE_NO_WINDOW` 把输出丢了" → 加日志重定向 ✅（但这只解决"没线索"）。
2. 从日志里看到真因之一：**MSBuild 用大小写敏感字典装环境变量**，本机同时有 `HTTP_PROXY` /
   `http_proxy` / `HTTPS_PROXY` / `https_proxy` 四条 → `Hashtable.Insert` 抛异常 →
   报成**误导性的 `MSB6001: CL.exe 的命令行开关无效`**。修法：传子进程前忽略大小写去重。
3. 去重后变成 `error=87`。先归因"环境块 27370 字符超 32K 上限"——**这是错的**。
4. 用 ctypes 直接调 `CreateProcessW` 做对比实验才定住：

| 场景 | 结果 |
|---|---|
| 48 字符小块，不带 flag | **87** |
| 48 字符小块，带 flag | 成功 |
| 27370 字符真实环境，不带 flag | 87 |
| 27370 字符真实环境，带 flag | **成功** |

**根因是漏了 `CREATE_UNICODE_ENVIRONMENT`**，与块大小无关。教训：**"看起来像是 A，其实是 B"
的时候，写一个最小复现比继续读代码猜快十倍。**

## 从"调 cmake"改成"直写 sln/vcxproj"的决定

不是被 87 逼的（修好 flag 后 cmake 也能跑），而是三条独立的理由：
1. 用户机器上可能**根本没装 cmake**；cmake 只是生成器，真正编译的还是 MSBuild。
2. cmake 会把 `<tmp>` 的**绝对路径**写进 `.vcxproj` / `CMakeCache.txt` → 整个 `code/` 目录
   拷走就废；直写的文件可以随便搬。
3. 纯文本写入 = 不起进程、不联网、瞬间完成。

代价：源文件列表在 `.vcxproj` / `.filters` / `CMakeLists.txt` 三处各一份 → 加自检
`D6_vs_sources_match` 盯着（`ClCompile` 计数必须 == `CMakeLists` 里 `.cpp` 计数 == 2）。

**探测代替写死**（本机实测：VS 装在 **D 盘** `D:\Microsoft Visual Studio\2022\Professional`，
按 `%ProgramFiles%` 猜必失败）：
- `devenv.exe` / `MSBuild.exe` / 工具集 → `vswhere -latest -products *`
- `PlatformToolset` → 扫 `VC\Tools\MSVC\14.44.35207` → `v143`（写死 v143 在 VS2019 上报 MSB8020）
- `WindowsTargetPlatformVersion` → **不写**，用最新已装 SDK（写死会在没装那个 SDK 的机器上炸）
- `OutDir` → **必须**显式 `$(ProjectDir)bin\`（VS 默认落 `$(Configuration)\`，引擎按
  `code/bin/<M>.dll` 找 —— 对不上就是"编成功、游戏里没反应"，两边都不报错）

## 判据（都真跑过）

```
GC-TOTAL  pass=48 fail=0 skip=0        （--selftest project 的 GC 组 A~E）
CREATE-TEST SUMMARY pass=54 fail=0     （含新增 K26b~K26g：slnPath 必须是 rename 后的路径）
GAME-TOTAL pass=12 fail=0              （--selftest game，含 A9~A12 真加载）
```

**E1 是真编出来的**：`E1_msbuild_build ... Demo_third_personGame.dll (36352 bytes)`。
**A9~A12 是真加载的**：

```
GAME-MODULE loaded name=Demo_third_person version=1.0.0 abi=1 functions=2
GAME-T pass A11_functions_registered n=2 first=demo_third_persongame.ping
GAME-MODULE unload name=Demo_third_person
```

即"生成 → 编译 → 加载 → 卸载"四段全是实测，不是推断。`--selftest game` 默认 8 条，
设 `MYVK_GAME_DLL=<dll>` 才多跑 A9~A12（不设就 SKIP，避免"某个工程的坏 DLL 让无关自检变红"）。

## 顺带发现的一个 flaky（**没修，留给用户定**）

`--selftest script` 的 `C8b 熔断后帧时间仍在预算内` 是**墙钟断言**（< 500 ms），
Debug 下实测 **469 / 501 / 535 / 688 ms** 四个值 → 4 次里只绿 1 次。

判断：这是**期望写错了**，不是实现坏了。理由是同一测试的 `C8 quotaHit` 已经能区分
"配额没生效"（脚本会平静跑完 30000 次、`failed=false`）—— C8b 那 500 ms 只是在测
"这台机器 Debug 下快不快"。要修的话应该改成相对基线（先量一个标定循环，再断言 N 倍内），
或者把墙钟降级成"没挂死"的宽松烟雾线。**没有擅自改另一个子系统的断言。**
