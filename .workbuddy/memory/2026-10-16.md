## 3 · 表驱动：加页签 = 表里加一行

```cpp
struct TabDesc { const char* id; const char* label; const char* tip;
                 void (*icon)(ImDrawList*, ImVec2, float, ImU32); };
const TabDesc kTabs[] = { {"object","Object","变换 / 可见性 / 网格几何",iconObject}, ... };
```

两处 `static_assert` 把"表"与"枚举"钉死：

- `kTabCount == static_cast<int>(InspTab::Count)`
- `static_cast<int>(InspTab::All) == kTabCount - 1`

**顺序 = 枚举整数值 = 图标栏自上而下的顺序**，一处定义三处生效（表 / 派发 switch /
落盘 id）。`tabId(i)` 是**唯一**的 id ↔ 下标桥，所以落盘永远写 id 不写下标 ——
以后在中间插一个页签也不会把用户的布局读歪。

## 4 · 导航条的实现细节

- **尺寸全部从 `GetFrameHeight()` 派生**：`btn = GetFrameHeight()`（本机实测 **28px**）、
  `colW = btn + WindowPadding.x * 2`。不写死像素 → 换字体/换 DPI 不会错位。
- 每项画 `InvisibleButton("##tab", {btn,btn})` + **自绘**圆角高亮（`Header` /
  `HeaderHovered` 两个主题色），选中项左侧加 2px 竖指示条。
- 图标 `inset = btn * 0.165f`（**先写 0.20 偏小、视觉发闷，调大图标后改回 0.165**）。
- `All` 之前插 `Dummy(4) + Separator() + Dummy(2)` 做**语义分隔**（它是"特殊项"，
  不是第 11 个分类）。验收脚本专门断言了这个空隙存在。
- 容器是 `BeginChild("##insp_nav", {colW,0}, Borders, NoScrollbar)`，
  `PushStyleColor(ChildBg, (0.09,0.095,0.105,1))` 压深一档。
- 每项打 `logRect("INS-NAV <id>")` → 自动化能拿到每个按钮的真实屏幕矩形。

**内容区一个子窗口**：`SameLine()` + `BeginChild("##insp_content")` + `drawTabContent(e)`
+ `drawNoMatchHint()` + `EndChild()`。

## 5 · ⚠ 本轮最重要的决定：自动化下默认页签 = `All`

**问题**：项目里已有 **9 个**验证脚本靠 `INS-MESH-HEADER` / `INS-COLLISION-HEADER` /
`INS-PROBE-HEADER` / `INS-FX-EXPAND-ALL` 这些矩形锚点断言"那个分区画出来了"。
分区一旦按页签分散，不指定页签就只看得到 Object 页 → **那 9 个脚本会整批误报**。

**决定**：`draw()` 的一次性初始化解成三段优先级 ——

1. 显式 `MYVK_EDITOR_INSP_TAB=<id|下标>` 优先（给单页测试用）；
2. 否则**自动化运行**（`editorLayoutAutomationRun()`）→ 默认 `All`；
3. 交互运行 → 默认 `Object`（用户看到的仍是精简的首页）。

这样"改 UI 不动旧验收"和"用户拿到新体验"两件事同时成立。**代价**：`All` 这一页
必须把旧的绘制顺序**一字不改**地保住（`drawTransform / drawVisibility /
drawMeshAndMaterial / drawLights / drawScript / drawAddRemove`）—— 它不是一个
"新页面"，是**兼容层**。这条要写进 roadmap，别以后有人觉得它多余就删了。

## 6 · 收尾时发现的两笔回归映射表欠账（**本轮新增，原计划外**）

### 6.1 `verify_inspector_tabs` 进了 `DEFAULT` 却没进 `TRIGGERS`

`DEFAULT` 有（放在 `verify_sss` 之后，注释说明"它逐个页签启动 16 次编辑器，是本套件里
最慢的一个；但它同时看守着其它脚本的默认页签，失败信息应尽量早出现"），
`TRIGGERS` 里**一条都没有** → 改 `InspectorPanel.cpp` 时它不参与关联集。

**补法**（严格按文件顶部铁律 2「不要登记横切文件」）：

```python
"verify_inspector_tabs": ["editor/InspectorPanel.*", "editor/InspectorIcons.h"],
```

**故意不登记两个**，理由写进了注释：

- `editor/EditorLayoutIO.*` —— 页签选择落盘确实在这里，但它同时是**全编辑器共用的
  落盘守卫**（布局 / 偏好 / 通知历史都走它）。只挂在本例名下 → `verify_viewport` /
  `verify_notifications` 在它变更时被判成"不受影响" = **假跳过**。
- `editor/EditorApp.cpp` —— 宿主接线，同一文件里还有几十处别的面板接线。
  项目既有约定就是"未登记 → 全量"，与 E18/E19/E21 的写法一致。

### 6.2 ⚠ 一条**写错的注释**掩盖了一个真实的覆盖缺口

`verify_particles` 的 TRIGGERS 上方原本写着：

> "面板在 InspectorPanel.* —— **那是横切文件**，所以面板那一组（D/E）实际上是无条件重跑"

**这句是错的。** `GLOBAL_GLOBS` 里根本没有 `editor/**`（横切清单是
`CMakeLists.txt` / `engine/core|rhi|**` / `engine/render/RenderTypes.h|ShaderKeywords.*|
Renderer.*|FeatureRegistry.*` / `engine/scene/Scene.*` / `engine/ecs/**` / `engine/ui/**` /
`engine/assets/**` / `engine/physics/**` / `common.glsl` / `pbr.*`…）。

`InspectorPanel.*` 只是被 `verify_inspector` / `verify_mesh_params` 登记过 →
**改它不会触发全量** → 粒子面板那 12 个 Shuriken 模块的 D/E 两组断言
**在"改面板"时被静默跳过**。

**修法**：给 `verify_particles` 显式补 `"editor/InspectorPanel.*"`，并把注释改成
纠正记录 + 教训：

> 判断"某文件是不是横切"**只能去 `GLOBAL_GLOBS` 里查，别凭印象**。

### 6.3 连带：`check_regression_map.py` 的 fixture 先红了（它在正常工作）

`[A]` 组有一条硬编码期望：

```python
run("editor/InspectorPanel.cpp → mesh_params", OLD, with_change("editor/InspectorPanel.cpp"),
    want={"verify_mesh_params", "verify_inspector"})
```

改完 TRIGGERS 后它报 `FAIL`，并**把多出来的两个用例名打了出来**：

```
editor/InspectorPanel.cpp → mesh_params  FAIL
     want=['verify_inspector','verify_mesh_params']
     got =['verify_inspector','verify_inspector_tabs','verify_mesh_params','verify_particles']
```

这正是它该有的行为（自检工具发现了映射表与期望脱钩）。同步 fixture 后
`结果: PASS`。**结论：改 `TRIGGERS` 一定连带改这个 fixture，两步是原子操作。**

## 8 · 两个靠"截图放大"才发现、日志里看不出来的视觉缺陷

`logRect` 能告诉你"矩形在不在、尺寸对不对"，**但矩形里面画的是什么糊不糊，日志一个字都不说**。
这轮我写了个一次性探针（`tools/_probe_nav.py`，**用完已删**）把导航条放大截图肉眼过一遍，
抓到两个缺陷：

1. **「物理」图标**：原方案是"原子"（一条椭圆 + 两条倾斜轨道交叉）→ 在 **24px** 下
   两条轨道交叉成一个**蝴蝶结**。改成"**小球 + 向下重力箭头**"。
2. **「动画」图标**：原方案"一颗菱形 + 横轴"→ 糊成**加号**；改"两颗菱形 + 轴线"→
   又成**哑铃**；最终定稿"**坐标轴 + 缓动曲线**"。

两条都写进了 `InspectorIcons.h` 的注释，说明**为什么不是看起来更贴切的方案** ——
避免以后有人"顺手改回原子"。

顺带修掉：

3. 图标 `inset` 0.20 偏小 → 0.165。
4. **「输出」页的 `BulletText` 不换行，长句被右边缘裁掉** → 新增 `bulletWrapped()`
   （`Bullet()` + `SameLine()` + `TextWrapped()`）。

**探针本身踩的坑**：`capture_client()` 返回的是 `(PIL.Image, ok)` **元组**，不是

`np.array(img)` 才切得动。取矩形不要自己从截图里认，直接用 `LogTap.last_rect(tag)`。

## 9 · 锚点语义造成的**假红**（验证脚本这一轮最值钱的一条）

`verify_inspector_tabs.py` 的 D 组一开始有一条红：**"搜 `rough` 时 Mesh 段被过滤掉"**失败。

查下来是**我的断言口径错了，不是功能坏了**：

`INS-MESH-HEADER` / `INS-COLLISION-HEADER` / `INS-PROBE-HEADER` 这几个锚点被我刻意记在
`sectionHeader()` **之后**、`if (!open) return;` **之前** —— 目的是让脚本**能点到折叠着
的分区标题把它展开**。代价是：

> **记在提前返回之前的锚点，只能证明"这个函数被调用了"，不能证明"这个分区可见"。**

搜索把 Mesh 段过滤掉时，函数照跑、锚点照打 → 拿它做"锚点应当消失"的负向断言必然假红。

**修法 = 换锚点**：改用记在提前返回**之后**的 `INS-MATERIAL-HEADER` 做正/负对照
（没搜 → 在；搜了滤掉 → 消失）。这条已经写进脚本注释 + `docs/editor_roadmap.md`。

**可复用规则**：

> 一个 `logRect` 锚点能证明什么，取决于它**记在提前返回的哪一侧**。
> "看得见"只能用返回之后的锚点断言；"函数跑过"用返回之前的。

## 15 · 定点复跑抓出一个**与 E11.1 无关的 P0**：R6-1 粒子系统开不起来

这是本轮最有价值的意外收获 —— 由 §6.2 那次 TRIGGERS 补漏间接引出来的。

### 15.1 症状与第一层误诊

`verify_particles` 挂在 A2/A3（抓图）上，日志里只有：

```
[dbg] 抓图失败：client=(0,0) 进程存活=False 标题可见=False
```

`进程存活=False` 看着像"编辑器莫名提前退出"。**差点误诊成 harness flaky**（这个症状在
`capture_nonempty` 的 docstring 里被明确记成"kill_stale_editors 无差别杀进程"的表现）。
但：
- `run_once()` **不设 `MYVK_FRAMES`**（它会等 `SHADER-VARIANTS` 再 settle 3s 抓图）→ 不是"跑太快"；
- **单跑复现**（两次都挂）→ 不是偶发；
- 我**直接**用该用例的环境启动编辑器，`timeout 40` 返回 **124（还活着）** → 编辑器本身不崩。

于是写了一个一次性探针（`%TEMP%\probe_cap.py`，**仓库外，用完已删**）复刻 `run_once` 并在失败时
打印**子进程的遗言**，一击命中：

```
[VK_CHECK] Vulkan error -1000069000 at engine\rhi/DescriptorSet.inl:61
[ERROR] Fatal: Vulkan call failed
```

**教训**：`进程存活=False` 不等于"进程被杀了" —— **它可能早就 `Fatal` 退出了**。
"打印子进程最后 N 行"这一步花了我 5 分钟，却省掉了几小时的方向性错误。

### 15.2 根因：粒子描述符池**按类型给少了**（一行 too small）

`-1000069000` = **`VK_ERROR_OUT_OF_POOL_MEMORY`**，落在 `vkAllocateDescriptorSets`。

`ParticleSystem::createDescriptors()` 原本：

```cpp
//   SSBO  —— 模拟 4 + 计数 2 + 绘制 2 = 8 个/帧          ← 注释数错了
m_descriptors = std::make_unique<rhi::DescriptorAllocator>(
    m_device, m_framesInFlight * 3, m_framesInFlight, m_framesInFlight,
    m_framesInFlight * 8, 0);
```

但 `createFrame()` 实际写的是：

| set | STORAGE_BUFFER 个数 |
| --- | --- |
| 模拟 `simSet` | 4（emitters / particles / alive / counters） |
| 计数 `countSet` | **6**（bindings 0..5，含 `aliveSorted`） |
| 绘制 `drawSet` | **4**（bindings 0/1/4/5） |
| **合计** | **14 / 帧** |

⚠ **池是按 set layout 的"全部 binding"计费的** —— `vkAllocateDescriptorSets` 那一刻就把整个
layout 的每种描述符从池里扣掉，**不是"实际写了几条"**。所以预算 8/帧 < 需求 14/帧 →
**第二帧一开始就爆**。

**修法（已改）**：`m_framesInFlight * 8` → `* 16`（留 2 个余量，以后给某个 set 加一个 binding
不会再炸），并把上面那段注释改成**逐 set 数一遍**的正确版本。

验证：

```
MX   FX=1 空场景 30 帧 : 无 Fatal，FX-POOL allocated 4096 slots，正常退出
     FX=1          120 帧 : VUID/ERROR 行数 = 0
     FX=0                  : 逐像素/行为基线不变（A1a-c 全 PASS）
```

### 15.3 修完后 `verify_particles` 从"崩"变成"34 项里 3 项红"

之前 A2/A3 一挂、脚本立刻在 A4 抛 `UnboundLocalError` 死掉 —— **B/C/D/E/F/G 七组从来没跑到过**。
所以这 3 项**不是新引入的回归，而是被前面的崩溃一直遮着**：

| 断言 | 实测 | 判读 |
| --- | --- | --- |
| `B1` 冻结帧两次运行 → 状态逐位一致 | `alive:368!=369, draws:368!=369, maxAlive:374!=371, instAdd:368!=369` | 差**恰好 1 个粒子** —— 与 §"冻结帧的确定性"里记的**固有不确实性①（池按 frames-in-flight 分槽，各槽停在自己的最后一步）** 完全吻合。属于**口径**问题：要么断言该按"集合差有界"来写，要么冻结逻辑要保证各槽同步到同一步。 |
| `F2` `dispatches=182 > simFrame=182` | 182 == 182 | 要求**严格大于**。正常语义下"一帧一次 dispatch"应当相等 → **期望写成 `>` 很可能是错的**（先怀疑期望）。 |
| `G1b` 排序只改顺序不改数量 | `alive 369 == 368` | 又是差 1：两次运行各一次抓取，取的是**不同帧**的计数。典型的"拿两次独立运行的瞬时计数比相等"。 |

**共同特征 = 差 1**，三条都是"跨两次运行比较瞬时计数"的口径问题，而不是粒子逻辑算错。
按项目纪律「**FAIL 了先怀疑「期望」再怀疑「实现」**」「**flaky 先查度量口径**」，
这三条应当先改**断言口径**（对齐到同一 simFrame 再比 / 把"严格大于"改对 / 冻结语义补齐），
而不是去改粒子代码。**本轮没有动它们**（超出用户请求范围，且需要先定"冻结帧到底承诺什么"）。

### 15.4 顺带发现的一处脚本缺陷（已修）

`verify_particles.py` 的 A4 无条件拼 `err_a2 + err_a3 + err_on`，而 `err_a2/err_a3` 只在
"A2 抓图成功"的 else 分支里赋值 → 抓图失败时抛
`UnboundLocalError: cannot access local variable 'err_a2'`，
**脚本带 traceback 死掉、永远走不到结尾的 `结果:` 行** → 回归里只看到 rc=1 + 一个 Python 堆栈，
**看不出是哪条断言红了**。已改成先 `err_a2, err_a3 = [], []` 初始化 ——
"抓图失败"是**已知会发生**的情形，那条路径必须是"判 FAIL + 报清楚"，不能是崩溃。

### 16.4.4 ⚠⚠ 新发现：**首帧布局竞态**（V2c 从 PASS 翻红的原因）

`verify_viewport.py` 第一次重跑时 V2c（三浮层全关 == NO_HUD，视口内部逐像素）是 **0 差 PASS**，
第二次却变成 **130564px 差异 FAIL**。定性：

- 连起 **6 次**同一份二进制：**5 次**收敛到 `VP-RECT=(310,184,1238,776)` / 骨架 `[304,1246,1572]`，
  **1 次**变成 `VP-RECT=(305,184,1241,776)` / 骨架 `[300,1249,1568,1575]`（左栏窄 4px）。
- 根因：**分栏根节点 `ratio = 0.0` = 按窗口自适应**（`SplitLayout.h` 里"工作区预设里 ratio 写 0
  的那些节点"），而 harness 是"**先起窗、再 `SetWindowPos`**" → 首帧布局用的是**启动那一刻**的
  尺寸，偶尔就停在没有收敛的那一支上。
- 危害：逐像素比对变成拿**两块不同几何**的图去比，差异全来自那 4px 位移 → **真实回归被淹掉**。
- **对策**：新增 `launch_converged()`，等到 `VP-RECT == CONVERGED_VP` 才抓图（最多重试 4 次，
  最后一次没收敛也照常返回、让断言如实报红，**不在这里吞掉**）。用在 V1/V2/V3 这三条逐像素用例上。

⚠ **这条是编辑器侧的隐性缺陷**（布局在 resize 后没有重新按比例收敛），本轮只在 harness 侧绕开，
**没有去改 SplitLayout**。将来若有人把 `ratio=0` 的自适应改成"每次布局都按当前客户区重算"，
`launch_converged` 就可以退休了。

### 16.4.5 ⚠⚠ 第二个竞态：**Win32 会把新窗口级联摆放** → 同一个屏幕坐标落在不同控件上

修完 §16.4.4 后再跑，V2c 绿了，**V1b 却翻红**：两次 NO_HUD 差 **348px / 最大 17**。

**定性过程（一次典型的"先怀疑期望、再查度量口径"）**：

1. 差异只有 **348 个像素，全挤在 `x 601..628 / y 106..133` 的一个 28×28 方块里**，
   差异形状是**一个标准圆环**（ASCII 差异图能看出环形）。
2. 放大看图 → 那是**视口工具栏上 `World / Local` 那对单选钮**。圆环 = 单选钮的外圈；
   内圈蓝点两边**完全一样**（`(112,192,248)` 逐位相同），只有**外圈亮了一档**
   （实测外圈内缘 `(131,134,139)` → `(117,119,122)`）。
3. 第一反应是 **hover 高亮**（鼠标"正好停在那个钮上"）。**但负向测试打脸**：
   故意 `SetCursorPos` 到该钮上再抓图，差异 = 0。→ 说明"光标在这一帧是否压着控件"
   **不是**全部原因（而且我新加的"抓图前把光标挪走"把负向测试本身给抵消了，这也是个教训：
   **加了 pin 之后再想复现原症状，得先把 pin 关掉**）。
4. 回到"为什么会变"这个更基本的问题：**窗口在哪**？旧代码用的是
   `SetWindowPos(hwnd, 0, 0, 0, W, H, SWP_NOMOVE | SWP_NOZORDER)` —— **SWP_NOMOVE**，
   也就是**只改大小、不动位置**，位置留给 GLFW/Win32 决定。
5. **决定性实验**：按旧写法连起 3 次，打印 `GetWindowRect` →

   | 第几次 | 窗口屏幕位置 |
   | --- | --- |
   | 1 | `(114,114)-(1714,1014)` |
   | 2 | `(152,152)-(1752,1052)` |
   | 3 | `(190,190)-(1790,1090)` |

   **每次往右下挪 38px —— 这就是 Win32 经典的"新窗口级联摆放"（CW_USEDEFAULT 行为）。**
   → **同一个屏幕坐标，在三次启动里落在客户区的不同控件上** → 被 hover 的控件不同 →
   V1b 的两次抓图（相隔约 12s、两次独立启动）自然对不上。**374px 的环，根因在窗口位置。**

**对策（两件一起做，缺一不可）**：

- `launch()` 把窗口**显式摆到 (0,0)**（去掉 `SWP_NOMOVE`）→ 窗口位置变成确定值；
- 新增 `park_cursor()`：把光标 `SetCursorPos` 到**屏幕右下角**（一定在 1600×900 之外），
  在**摆好窗口之后**与**抓图之前**各调一次（后者是给"点了菜单/控件"的会话用的 ——
  那些动作会把光标留在刚点过的东西上）。

与 `pinned_env`（布局/偏好）、`MYVK_NO_HUD`、`MYVK_GRID=0` 属于同一类：**把环境钉死，
让像素只反映被测代码**。教训一句话：**"两次抓图不一致"先问"两次是不是在同一个窗口位置上抓的"。**

## 17.7 四条教训

1. **像素/颜色类断言的扫描区间必须夹在"被测控件自己的矩形"里** —— 同一屏幕行上的邻居
   （Inspector）会污染横跨整窗的统计量。这是同类第 4 次踩（见 §16.4 `verify_viewport` 三根因）。
2. **比"两个来源的数字"先问"两侧采样窗口一样吗"** —— 周期性采样（每 30 帧）与"启动瞬间也来

## 18.1 E1b 复挂的真因：`force_foreground` 的**返回值被忽略**

§17.4 的结论是"抢不到前台时真实鼠标事件被系统丢掉"，于是加了个 `click_for`：抢前台 + 点 + 验状态，
重试 3 次。**但最后一轮单跑 E1b 又挂了（点 3 次全未送达）。** 复盘后找到真正的漏洞：

```python
for k in range(tries):
    force_foreground(hwnd)   # ← 返回值直接丢掉
    click_client(hwnd, x, y)
```

`force_foreground` 是**明确设计了返回 False** 的（`verify_asset_drag.py:117`，文档写着"两条都失败
就返回 False —— 调用方应该把失败**当成失败**处理（重试或报错），别继续往下发事件"）。
它返回 False 时编辑器窗口还被终端压着，于是 `mouse_event` 那几发**真实的**点击全落到了**压在上面
的窗口**上 —— 不是"被系统丢掉"，是**送错了窗口**。重试多少次都一样。

**修法**：加一条**与前台/遮挡无关**的注入路径 `click_client_post`（`tools/verify_bvh.py:116`）：
`mouse_set_client`（`PostMessage(WM_MOUSEMOVE)` 送位移，ImGui 的 GLFW 后端在光标进入窗口后
只吃光标回调）+ `user32.PostMessageW(WM_LBUTTONDOWN/UP, lParam=客户端坐标)`。消息直投目标窗口
的消息队列，**不经 DefWindowProc 的激活路径**，所以既不怕被压住，也不怕"第一次点击被激活吃掉"。

`click_for` 改成两路轮换：k==0 且抢到前台 → 真实事件（最接近用户操作）；否则 → 直投。

**验证（两条路各证一次，不靠"多跑几次碰运气"）**：

| 场景 | 结果 |
|---|---|
| 真实路径（正常前台）| `E1a/E1b/E2b` 全 PASS，各 **1 次**点击到位（`/real`） |
| **强制直投**（把 `verify_asset_drag.force_foreground` 打成 `lambda hwnd: False`）| `E1a/E1b/E2b` 全 PASS，各 **1 次**点击到位（`/post`） |

E1b/E2b 的输出现在带路径与次数（`点了 1 次/real`），下次再出问题一眼能看出走的是哪条路。

## 18.3 剩下 3 项"差 1"：先量出分布，再定口径

§15.3 记过 B1/B3/F2/G1b 是"差 1 的口径问题"，但没定"冻结帧到底承诺什么"。这次先**实测**
（`_probe_b1.py`，FREEZE=120 连跑 5 次）：

```
run 0: alive=369 draws=369 maxAlive=371 simFrame=120
run 1: alive=365 draws=365 maxAlive=372 simFrame=120
run 2: alive=365 draws=365 maxAlive=372 simFrame=120
run 3: alive=365 draws=365 maxAlive=372 simFrame=121   ← B3 "正好 ==120" 其实随机红
run 4: alive=366 draws=366 maxAlive=371 simFrame=120

极差：alive/draws/instAdd = 4 · maxAlive = 1 · simFrame = 1
     cap / emitters / frozen / instAlpha = 0（这几个是真确定的）
```

两条机制（都关不掉）：
- **① 池按 frames-in-flight 分槽**，每槽只在自己被派发时推进（`dtSlot = elapsedFrames × dt`）。
  冻结后各槽停在**各自的最后一步**，而"哪一槽是最后被派发的"由**墙钟帧号**决定 ⇒ 两次运行截到的
  槽不同 ⇒ 边界处那几颗粒子生/死不同。本场景 rate=260/s、simHz=60 ⇒ 一步 ≈ 4.3 颗。
- **② 累加器允许一帧补多步**（`kMaxSimStepsPerFrame = 8`）⇒ 越过 FREEZE 的那一帧可能从 119
  直接跳到 12x ⇒ `simFrame ∈ [120, 127]`。

⇒ **断言口径**：
- `B1`：`EXACT_KEYS`（`frozen`/`cap`/`emitters`/`instAlpha`）**精确**比；`BOUND_KEYS`
  （`alive`/`draws`/`instAdd` ≤8、`maxAlive` ≤2、`simFrame` ≤7 = 一帧上限−1）比**有界**。
  容差只给机制的 2 倍余量 —— 确定性真坏了（哈希改了、步长失控）差值会是几十上百，照样抓得住。
- `B3`：`120 <= simFrame <= 127`（原来是 `== 120`）。
- **`B3b`（新增，反而更严）**：**"冻结之后真的停住了"是精确可验的** —— 同一趟里冻结后的**所有**
  FX-DUMP 样本，状态字段必须逐个相同（实测冻结后还有 10 条样本）。跨趟只能有界，但"停住"不必有界。
  ⚠ 比的是**状态字段子集**，不能拿整条字典比 —— `slot`（帧号）冻结后仍在涨。
- `G1b`：`abs(dg.Alive - d1.Alive) <= 8`（原来是 `==`，而两者来自**两次独立运行**的瞬时计数）。
- `F2`：见 §18.4。

## 18.4 F2"派发远多于步数"：**必须把 simHz 压到远低于帧率**，否则恒不成立

F2 原来是 `dispatches > simFrame`，实测 `182 > 183`（§15.3 记的是 `182 == 182`）。查语义
（`Renderer.cpp` 的 FX-DUMP 注释）：

```
dispatches = 模拟 compute 派发了几次 ≈ 渲染帧数（每帧一次）
simFrame   = 模拟推进了几个固定步 = 模拟时刻 × simHz
```

编辑器 **vsync 锁 60fps**，而 **simHz 默认也是 60** ⇒ 两者本来就 1:1，这条断言在这台机器上
**永远不成立** —— 不是功能坏了，是**这个配置根本不区分**。特性存在的场景恰恰是"帧率远高于模拟
频率"，所以给 F 组加 `MYVK_FX_HZ=8`：

| | dispatches | simFrame |
|---|---|---|
| 改前（hz=60）| 182 | 183 |
| 改后（hz=8）| **182** | **25** |

断言改成 `dispatches >= 2 * simFrame`（留余量：帧率掉到 16fps 也成立）。
**判别力**：旧行为（每帧一步、不看墙钟）下 `simFrame == dispatches` → 必红。这条断言这才真的
在验"速度与帧率解耦"。
