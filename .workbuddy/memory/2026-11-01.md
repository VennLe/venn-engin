## #152 B6 表情预设 + 眨眼/口型驱动（第一档最后一项，做完）

`docs/remaining_work_2026-10-27.md` §6.1 第 6 位。原判词："数据链早通到 GPU，只缺资产层与 UI"。
实际做下来，缺的是**三层**：按名字组合权重的资产、跨角色复用的语义、以及"没人推滑条时脸也要动"
的驱动器。

### 一、为什么不能把 `ExpressionComponent` 并进 `MorphComponent`

`MorphComponent::weights` 是"脸此刻长什么样"，**谁写都行**；驱动器的语义是"这些数怎么算出来的"。
合成一个组件后，"驱动每帧写满"与"用户推滑条"变成同一块内存上的两种写入，谁后写谁赢 ——
症状是**推滑条没反应**，且只在"引擎没在驱动"的时刻偶然正常，极难复现。分开之后边界很清楚：

- 驱动器**只写自己拥有的通道**：①当前预设列出的 ②眨眼通道 ③口型通道；其余原样不动。
- 上一帧拥有、这一帧不再拥有的通道**显式写 0**（换预设时旧表情必须归零）——
  但 `ownedChannels` **只存本帧活跃的**，补 0 的不进。否则清空预设后每帧都写 0，滑条永远推不上。

### 二、眨眼：确定性抖动，不是 `rand()`

`blinkWeight(phase, close, hold, open)` 三段（`smoothstep01` 进、1 保持、`1-smoothstep01` 出）。
抖动用 **LCG**（`seed = seed*1664525+1013904223`，种子取自实体 id）：
`rand()` 会让自检只能写"10 次里至少 1 次"这种等于没测的断言；确定性抖动可以钉
"第 N 次间隔落在 [0.85,1.15]×interval"（自检 A4 还顺手钉住了"是 smoothstep 不是线性"：
`blinkWeight(0.025) == 0.15625`，线性会得 0.25）。首帧 `blinkTimer = -1` 按 id 抽相位，
避免全场景角色同时眨。

### 三、口型：输入是 **Voice 总线** 的 RMS

- 全局 RMS 里混着 BGM 与音效 → 一句轻声台词配响 BGM 会一直张嘴；
- `voicePlaying()` 带一个 block 的宽限期 → 嘴先张、声后到；
- 所以新增 `MixStats::busRms[kBusCount]` + `Mixer::busLevel(bus)` + `AudioSystem::voiceLevel()`
  （**不带宽限期**）。累加器用 `double`（float 丢尾音）；`frames==0` 不更新（除 0 → inf → NaN 的脸）。
  平滑是**指数**（攻 0.02 / 放 0.09）：线性逼近会让 60 fps 与 144 fps 的韵律不同。

## #153 P1 Release 基线（`remaining_work` §6.1 第 3 位，做完）

### 一、`build/` 不能换成 RelWithDebInfo

`build/` 是**回归用的 Debug**（`/RTC1` + 全断言 + 不内联），160 多个 `verify_*.py`

新增 `make perf-build` → `build-rel/`（`PERF_BUILD_DIR`/`PERF_BUILD_TYPE` 可覆盖）。
⚠ 顺带发现的老坑：Makefile 的 msvc 分支里 `MSVC_BUILD` 那条命令**根本不传
`BUILD_DIR`/`BUILD_TYPE`** —— `make BUILD_DIR=build-rel ...` 会静默地去 configure
`build/`（实测日志 `dir=build type=Debug`）。新目标按 `ship` 的写法用
**target-specific export**（不是 `cmake -E env` 包一层：Git Bash 会把 `/c` 改写成

### 三、实测结论（表 → `docs/perf_baseline.md`）

```
Game.exe   anime_demo  1280x720 12.1ms / 1600x900 16.4ms / 1920x1080 24.3ms
           sandbox     1280x720 10.7ms / 1600x900 14.8ms / 1920x1080 19.7ms
分段 1080p: forward=12.57  depth=5.17  post=2.71  shadows=2.05  local_sh=0.78  cluster=0.07
```

1. **`forward` 占 50%，且随分辨率线性涨**（5.2→12.6 = ×2.4 ≈ 像素比 ×2.25）→
   是**填充率**，不是几何/提交；`depth` 同样线性（×2.0）= 带宽。
2. **`shadows` 不随分辨率动**（2.04/2.05/2.05）→ 它跟光源数与级联图尺寸走，
   降分辨率救不了阴影。
3. ⚠⚠ **反直觉的那条**：同配置 Debug 26.2 ms vs Rel 24.3 ms，**只差 8%**；
   编辑器侧甚至互有胜负。→ **这两份场景当前不是 CPU 受限**，所以
   "(a) 换 Release 能快一倍" 是错的；"(b) 以前拿 Debug 数字判性能退步" 也不可信；
   "(c) P2/P3 这类只动 CPU 的项在这两份场景上不会体现在帧率里"。
