### 关键设计决策（值得复用）
1. **用 compute 而不是 6 次 render pass 生成立方体**：面号→方向是纯函数
   （`vennCubeDir(face, uv)`），一趟 dispatch 的 z 维 = 6 就能写满，
   不需要 6 个 framebuffer / 6 个 render pass。
2. **`imageStore` 不能指定 mip 层级** → 预过滤每个 mip 各建一个
   `VIEW_TYPE_2D_ARRAY` 视图（`baseMipLevel = m`），逐级写入。
3. **天空立方体用 `R32G32B32A32_SFLOAT`、BRDF LUT 用 `R32G32_SFLOAT`** ——
   不是为了精度，是为了 **CPU 回读时能直接当 float 数组读**，免掉半精度转换代码，
   也让数值自检直接读 float。
4. **天空 pass 排在前向 Pass 最前**（`depthTest/depthWrite` 全关）。排到最后会
   盖掉地平面栅格 —— 栅格也不写深度，像素深度停在 1.0，正好落进"天空该画"的判据里。
5. **天空/栅格管线的 set 布局与推常量范围必须与主前向管线逐字段一致**，
   否则后半段所有 draw 报 `VUID-...-08600`。
6. **Vulkan 只保证 4 个 set 可同时绑定**，set 1..6 已被六张贴图占满 →
   环境资源必须挤进 set 0。
7. 保留旧的程序化近似路径，用 `FrameUBO.envParams.x` 开关切换。这**不是备用方案**，
   而是"两条路径必须给出不同画面"的对照实验手段（`MYVK_IBL=0`）。

## 本轮踩的坑

### 1. glslc 的 `#include` 只认 `-I` 给的目录
- 放 `#version` 之前 → `'#version' : must occur first`（`#version` 必须是编译单元第一行）。
- 放同目录 → `Cannot find or open include file`（**不认源文件所在目录**）。
- 修复：`CMakeLists.txt` 里 `COMMAND ${GLSLC} -I${SHADER_SRC_DIR} ${SRC} -o ${OUT}`，
  并 `file(GLOB SHADER_INCLUDES ... *.glsl)` 加进 `DEPENDS` —— 否则改共享头不触发重编译。
- compute 着色器里 `#include` 要放在 `layout(local_size_*)` **之后**（local_size 必须在其它声明之前）。

### 2. `rhi::Device& / rhi::CommandPool&` 是引用，不是 `unique_ptr`
`*m_device` 编译不过（`no match for 'operator*'`）。对象本身用 `m_device.get()`；
取地址用 `m_device`。同时把 `(readback ? USAGE_A : 0u)` 的三元改成
`VkImageUsageFlags usage = ...; if (readback) usage |= ...;` 消 `-Wextra` 的枚举混用警告。

### 3. 测试脚本踩的两个坑（都是**测试**的问题，不是渲染的问题）
- **坑 A：`region_diff` 的 stride 采样放大了局部噪声。**
  `region_diff` 按 `range(x0,x1,2)` 抽样。`tl` 全区域平均差只有 1.11，用 stride 却算出
  4.48 —— 说明里面有少数像素差得很大。
- **坑 B（真正的元凶）：视口左上角有 ImGui 统计叠加层。**
  `ViewportPanel::drawOverlay` 在视口左上角画 `1317 FPS  0.76 ms` / `entities N` 等文字，
  **FPS 和帧时间每次运行都不同**。同配置跑两次，`tl` 区 region_diff = 2.72，
  而 `tr` / `bl` / `center` 精确为 0.00 —— 这就是全部"IBL 开关影响背景"假象的来源。
  （右上角那块 `Viewport navigation` 浮层反而稳定，所以 `tr` 当时是 0.00。）
- 修复：新增 `MYVK_EDITOR_NO_HUD=1` → `ViewportPanel::setHudVisible(false)`
  （同时关掉统计文字、导航 HUD、左下角导航球、手柄）。只影响 ImGui 覆盖层，
  不动 3D 场景。
- **教训：做视口像素断言前，先把 FPS/帧时间这类浮动 HUD 关掉。**
  另外"同配置跑两次背景必须逐像素相同"应该成为这类脚本的前置自检。

### 4. 我自己的断言在几何上就不成立
第 4 组原来断言"把天顶染红后画面上方偏红"。实测左上角 `(189,54,201)` —— **蓝仍占优**。
原因：45° FOV、画面宽高比 1.24 → 画面上**边缘**的仰角只有 22.5°，
`t = 0.5 + dir.z*0.5` 里 `dir.z ≈ 0.35~0.38` → `t² ≈ 0.45 < 0.5`，
mix(地面蓝, 天顶红, 0.45) 本来就是蓝略多。**断言写错了，不是代码错了。**
- 改成：无球场景 + 竖直中线上三条采样带，断言 `r/b` **单调递减**。
- 且不能再用固定倍数阈值：色调映射把高光段压平了，线性空间 2.1× 的 r/b 差
  到了画面上只剩 1.24×。改判**逐级落差 > 0.02**（实测 Δ=0.111 / 0.070）。
  这反而是更强的判据：若梯度错落到 `dir.y`（水平方向），竖直线上的三条采样带
  会拿到**完全相同**的 `dir.y` → 落差直接是 0。

# 第二块：阴影 —— 级联方向光（CSM）+ 阴影距离分级

用户原话的第二半：「阴影：只有方向光一张 2048² 图；无级联（CSM）、无点光/聚光灯阴影、
无阴影距离分级」。本轮做完 **CSM + 距离分级**；**点光/聚光灯阴影尚未开始**。

## 设计：为什么是"视锥切片包围球 + 纹素量化"
- **用包围球而不是包围盒**：球的半径**与光方向无关**。盒的半径会随光方向变，
  光一转阴影边缘就"呼吸"。这是 CSM 的第一条稳定化措施。
- **球心在光空间量化到纹素网格**，再把差量补回视图矩阵平移列
  (`view[3][0] += floor(cLS.x/texel)*texel - cLS.x`)：相机连续平移时球心连续移动，
  采样点相对纹素滑动 → 整片边缘闪烁；量化后只在纹素边界跳变。第二条稳定化措施。
- **包围球由"视锥切片的 8 个角点"求出**（由 `invViewProj` 反投影），
  **不再是**旧的"投影物体的世界 AABB"。MEMORY.md 里那条"正交范围用投影物体的
  世界 AABB"已经**作废**（那条是为单张图写的，级联下每级只覆盖一个切片）。
- 正交投影用 `glm::orthoRH_ZO(-r, r, -r, r, 0.0f, 2*(r + kDepthPadding))`：
  近平面取 **0**（深度线性，牺牲的那点精度可忽略），换来"光源到切片之间的所有
  遮挡体都进深度图"。`kDepthPadding = 25m` 的外扩就是为此。
- **分割点 = PSSM practical scheme**：`splits[i] = λ·near·(D/near)^(i/N)
  + (1-λ)·(near + (D-near)·i/N)`，其中 **`D = min(相机远平面, 距离上限)`**。
  λ=0.6 略偏均匀。D=90、near=0.1 时 → `9.36 / 19.82 / 36.87 / 90.00`。
  ⚠ 这里的 near/far **必须与 `camera().projMatrix()` 用的是同一组值**：
  原来代码里写死 `kNear = 0.1f / kFar = 200.0f`，与 `Camera` 的默认值重复，
  场景一改就悄悄错位 → 改成 `scene.camera().nearPlane() / farPlane()`。
  级联分割点、切片角点的 NDC 换算、分簇的对数切片三处都依赖它。

## 实现要点
- `FrameUBO.lightSpace` 从 `mat4` 变成 `mat4 lightSpace[4]`（+192B），并新增
  `shadowParams`(576) / `cascadeSplits`(592) / `shadowBias`(608) → **共 624 字节**。
  矩阵**只有这一个副本**：`ShadowPass::updateCascades` 算完写进去，渲染时从同一个
  数组取（靠推常量里的级联索引选），采样侧 `pbr.frag` 读的也是它 ——
  **不可能出现"渲染与采样用了不同矩阵"**。
- `ShadowPass` 的深度图是 `VIEW_TYPE_2D_ARRAY`（4 层），采样侧 `sampler2DArrayShadow`。
  但**渲染时每层单独建一个 `VIEW_TYPE_2D` 视图 + framebuffer** ——
  framebuffer/imageStore 不能挂 array 视图做单层渲染（那就变成 layered rendering，
  需要 multiview / gl_Layer）。
- **每级一次独立的 depth-only render pass**，在自己 Pass 内**自行绑定 set 0**。
  这一点是 `ShadowPushConstants`（96B）能存在的**唯一理由**：`PushConstants` 恰好
  用满 Vulkan 保证的 128B 下限，塞不下级联索引，所以阴影 Pass 用自己独立的
  96B 推常量。绑定时与绘制时是同一个管线布局对象，不可能不兼容。
  ⚠ **绝不能把这个 Pass 的绘制搬进前向 Pass 的 render pass**，否则立刻 VUID-08600。
- 每级剔除在**裁剪空间**做：正交投影 w 恒为 1 → 裁剪空间直接是 NDC → 退化成 6 次
  区间比较（`visibleInCascade`）。不做的话提交量 = 全场景 × 级联数。
- **级联盒边缘刻意不淡出**：只在"视深度 > 最大距离"处淡出
  （`fade = 1 - smoothstep(maxDist*fadeStart, maxDist, viewDepth)`）。
  若在盒边界也淡出，级联交界处会出现假暗带。
- 顺手修掉一个**既有缺陷**：老 `ShadowPass::render` 只推 `push.model`，
  **没推 `push.skin`** → 蒙皮角色的投影是**绑定姿势**而不是当前姿势（角色一动影子散架）。
  现已从 `&m_skinJointBase` 查表填入，与主前向路径同源。
- 环境变量：`MYVK_SHADOW` / `MYVK_SHADOW_CASCADES` / `MYVK_SHADOW_DIST` /
  `MYVK_SHADOW_LAMBDA` / `MYVK_SHADOW_RES`。

## 一个测试脚本的小坑
`SHADOW-DBG` 的正则有 12 个捕获组，`enabled` 是**第 12 组**（前面 4 个 splits +
4 个 bias 分量）。我第一次写成 `group(11)` 拿到的是 `bias.w = 0.55`，

### 结构
所有需要投影的局部光源**共用一张 1024² × 12 层的 2D array 深度图**：
- 聚光灯 **1 层**（沿锥轴一次 `perspectiveRH_ZO`，`fovY = 2·atan(tan(外锥半角)·1.02)`）；
- 点光 **6 层**（立方体 6 面各一次 90° 透视投影，面序与 `vennCubeDir` 逐条对应）。

`shadow.vert` **两套阴影共用**：靠 `push.which.y` 选矩阵来源
（0 → `FrameUBO.lightSpace[x]`，1 → binding11 的 `lightShadow.records[x].matrix`）。
`ShadowPushConstants.cascade` 因此改名成 `which`。

层分配（`Renderer::prepareLocalShadows`）：灯按到相机的**距离平方**由近到远排，
贪心分配连续层段（点光要 6 层、聚光 1 层），预算不够就**整体停在那一盏之前**
（不是"跳过它继续找下一盏"——那样会让"哪盏灯有影子"随相机移动乱跳）。
分配结果写回 `LightInstance::cosOuterType.z`（基准层号），随 `uploadLights`
一起进 set0/binding2。

set 0 扩到 **13 个 binding**：11 = `lightShadows` SSBO（逐层 `LightShadowRecord`，
VERTEX|FRAGMENT 两阶段读）、12 = `localShadowMap`（`sampler2DArrayShadow`）。

### 四个硬约定（踩过的坑都在这）

1. **未使用的层每帧也要走一次空的 depth-only pass（只清深度）**。
   那张 array 是**整张**被采样器绑定的，留一层停在 UNDEFINED 会让验证层
   直接报 IMAGE_LAYOUT。空清是"快清"，代价远小于按需重建 image 或维护
   per-frame 布局状态机。实测 12 层全清 + 8 层真画，零 VUID。

2. **近平面必须按 range 取（`clamp(range/20, 0.1, 2.0)`），不能拍一个 0.05**。
   透视投影的 NDC 深度是**双曲**的，`far/near` 越大，远平面附近两个只差
   几米的表面在 NDC 上就几乎贴在一起。实测 range=32 用 near=0.05 时，
   离灯 15m 的遮挡体和 20m 的地面 **NDC 只差 7.5e-4** —— 任何合理的深度
   偏移都会把阴影整个推没。改 range/20 后同一个场景涨到 **2.8e-2**。

3. **深度偏移参数必须以「米」为单位给，片元里按参考深度换算回 NDC**。
   这是本次最贵的一个坑：一开始照抄 CSM 的 NDC 常数 `0.0016`，
   而在 range=32 / near=0.05 那组参数下，0.0016 的 NDC 偏移 = **10 米世界深度**
   → 聚光灯的阴影**一片都不剩**（`MYVK_LOCAL_SHADOW_LIGHTS=1` 时与关阴影
   逐像素完全相同，5956 → 0 像素差异）。修法：
   - `LightShadowRecord.params = (near, far, 所属光源下标, 有效位)`
   - `pbr.frag::ndcBiasFromWorld(refZ, near, far, worldBias)`：
     `dz/dd = (f − z·(f−n))² / (n·f·(f−n))`
   - 默认 `(0.030, 0.150, 1.2)` = 常数 3cm / 斜率 15cm / PCF 1.2 纹素。
   **教训：给"双曲分布的深度"配一个 NDC 常数偏移，等于在不同的距离上
   配了完全不同的世界偏移 —— 参数在物理上不可调。**

4. **光栅化阶段的 `depthBias` 对浮点深度几乎是 0**。
   `r` 对 `D32_SFLOAT` 约 `2⁻²³`，`depthBiasConstant=1.4` 等于 1.7e-7 NDC。
   CSM 那边一直靠片元侧的 bias 在干活，光栅化那两个常数基本是装饰。
   局部阴影已把常数降到 1.0/1.5，主要偏移交给片元。

## Shader 变体 / 关键字系统

补掉渲染分类里的又一项缺口：着色器一直是**离线 glslc 预编译的固定管线**，
材质特性（双面 / 透明 / 有无法线图）只能靠手写 N 条管线来开关 —— 已经攒到
四条（不透明 / 双面 / 透明 / 透明双面）外加三处 `if` 阶梯，再加一个特性就是 8 条。
而且"有无法线图"这件事**根本没得开关**：`pbr.frag` 无条件采样法线贴图并跑一遍
cotangent frame，哪怕材质压根没挂图（只是绑了张内置平坦法线）。

### 一条规则，三处逐字对齐

关键字是**位集合**（掩码 0..7），位序在三个地方各写一遍，**必须逐字对齐**：

| 位 | 宏名 | 名字 | 改名代码？ | 改固定状态？ |
|----|------|------|-----------|-------------|
| bit0 | `VENN_DOUBLE_SIDED` | `double-sided` | 是（按 `gl_FrontFacing` 翻法线） | 是（`cullMode`） |
| bit1 | `VENN_ALPHA_BLEND`  | `alpha-blend`  | 是（输出真 alpha） | 是（混合 + 不写深度） |
| bit2 | `VENN_NORMAL_MAP`   | `normal-map`   | 是（采样 + TBN） | **否**（只少一段代码） |

三处 = `render/ShaderKeywords.cpp` 的 `kKeywords[]`、`CMakeLists.txt` 的
`SHADER_KEYWORDS` / `VARIANT_DEFINES_0..7`、`assets/shaders/pbr.frag` 的 `#if`。
`ShaderKeywords.h` 是唯一事实来源（位序 + 宏名 + 文件名规则 + `keywordsOf`）。

变体 .spv 命名：`pbr.frag` + 掩码 n → **`pbr.k<n>.frag.spv`**（2³ = 8 份，k0..k7）。
实测 8 份字节数**全不同**：k0=39644 / k1=39848 / k2=39740 / k3=39944 /
k4=42856 / k5=43060 / k6=42952 / k7=43156 —— k4 多出 3.2 KB 正是被编进来的
法线采样 + TBN，这就是"关键字真的改了代码"的物证。

### 掩码同时推导两件事（这是设计的核心）

`buildDrawLists` 里 `it.keywords = effectiveKeywords(*mat)`，然后：
* **编哪份 .spv** —— `VariantPipelines::get(mask)` 拼 `variantShaderFile()`
* **管线固定状态** —— `applyKeywordState(mask, stateMask, desc)`

于是**结构上**杜绝了"编译期是双面、栅格化还在剔背面"这种半成品。
`stateMask` 用来过滤：深度预通道只关心 DOUBLE_SIDED（它不输出颜色），
所以它 `stateMask = kKeywordDoubleSided` + `SingleSpv` → 日志里
`depth_created=2` 而不是 8。

**队列分类也跟着掩码走**：`if (hasKeyword(it.keywords, kKeywordAlphaBlend))`
判透明，不再看 `mat->alphaMode` —— "半透明"从此只有一处定义。

### ⚠ 踩到的真 bug：`layout()` 顺手把 k0 建了出来

第一版 `VariantPipelines::layout()` 写成 `return get(kKeywordNone).layout();`
——`recordFrame` 要在第一个 draw 之前绑 set 0，那时还不知道用哪个变体，
作者（我）就"借基线那份用"。

副作用是**每次取布局都会把一个 k0 变体建出来**，直接违背"只建用到的变体"。
只是恰好 `FORCE_MASK=0` 时 k0 就是要用的那份，所以漏过去了；
`FORCE_MASK=4` / `=1` 时日志报 `fwd_created=2`（该是 1）才暴露。

修法（顺带是个 API 改进）：给 `rhi::PipelineDesc` 加 `sharedLayout`
（非空则直接用它、**不拥有不销毁**），并把布局创建抽成
`rhi::createPipelineLayout(device, desc)`。`VariantPipelines::init()` 里
**只建一份**布局，全体变体通过 `sharedLayout` 复用 —— "兄弟管线 layout 不同"
这件事在结构上就不可能发生，不再依赖"从同一份 baseDesc 派生"这种约定。
`layout()` 变成 `const` + 零开销。

**变体之间共用一份 VkPipelineLayout 不是优化、是正确性要求**：set 0 是整个
Pass 一次性绑定的，中途绑一条 layout 不兼容的管线会被 Vulkan 认为 set 0 被
"打断"，后面所有 draw 报 `VUID-...-08600`。

### 两条硬约定（写进注释了）

1. **绑定缓存的"什么都没绑"哨兵不能用 0** —— 0 是合法掩码
   （不透明、非双面、没法线图）。用 0 会让第一个全关材质被跳过绑定。
   用 `constexpr KeywordMask kBindsNothing = 0xFFFFFFFFu;`。
   栅格管线（`m_gridPipeline`）刚刚把管线绑定改掉之后**必须重置**缓存，
   否则第一个透明物体若掩码恰好等于"栅格之前绑的那个"就会跳过重绑、
   直接拿栅格管线画几何（栅格没有顶点缓冲 → 一堆乱画的三角形）。
2. **`SHADER-VARIANTS` 自检日志必须打在前向 Pass 之后**。它要读
   `m_stats.variantSwitches`，而那个值是前向 Pass 的循环里累加的；
   `buildDrawLists` 跑在 Pass **之前**，在那儿读永远是刚清零的 0。
   第一版就放在 `buildDrawLists` 里，日志恒为 `switches=0`。

### `NORMAL_MAP` 等价性怎么证（不需要任何贴图文件）

关键事实：没挂法线图时绑的是**内置平坦法线 (128,128,255, 线性)**，
`*2-1` 得 `(0.00392, 0.00392, 1.0)` —— 注意 **128/255 ≈ 0.50196，不是精确的
0.5**。于是 `normalize(TBN * nSample)` 与 `TBN 第三列 = N` 只差一个极小的
水平扰动。

所以断言 `MYVK_SHADER_FORCE_MASK=0`（编掉法线段）vs `=4`（走采样路径）
**逐像素最大差 ≤ 1 个 LSB**：
实测 `>18 的像素 = 0`、`最大差 = 1`、`逐像素均值 = 0.1012`、`bbox = None`。
（我第一版断言写 `均值 < 0.05`，被 0.1012 打回 —— 差异像素多、每个差 1，
均值天然是这个量级。第二版改成 `max ≤ 1 且 均值 < 0.5`，并把"不是精确 0.5"
这条原因写进注释。）

**第 4 组是配对断言**（防止"两边都错"的假通过）：挂一张非平坦棋盘法线图
（colorA `(128,128,255)` / colorB `(220,128,255)`，x 向扰动最大 0.7255），
`FORCE_MASK=0 vs 4` 实测 **5808 像素、最大差 30**。
判读阈值卡 **max > 20**（不是 40）：太阳压到 0.45 避免过曝后，法线 ±0.7 的扰动
在漫反射上只换来约 30/255 的亮度变化。与第 2 组的 max=1 相比仍有 20 倍余量。

## ⚠ 回归偶发的真根因：**注入的第一次左键点击会被窗口激活吃掉**

一直把 `verify_bvh` / `verify_mesh_params` / `verify_collider_gizmo` 的偶发失败
归到"套件内前台焦点干扰"，靠"单跑就过"糊过去。这轮 `verify_bvh` 变成了
**可复现**失败，才真正查下去。

**现象**：第 2 组报 `正中点击 -> None`、`PICK-DBG : None`。
`PICK-DBG` 是 `PickingSystem::pick` 里的自检日志，找不到它只有两种可能 ——
射线没打中，或者 `pick()` 压根没被调用。

**第一步（顺手修掉一个真缺陷）**：`PickingSystem.cpp` 里
`if (!hit.hit) return best;` **排在自检日志之前** → 没打中时一条日志都不出，
于是"射线没打中"和"自检没跑到"完全无法区分。把自检块提到早退之前
（顺手补了 `hit=%d` 字段）。⚠ 顺序还要注意：得先把 `hit` 写进 `best` 再自检，
否则 `same` 恒为 0。

**第二步**：改完仍然 `PICK-DBG : None` → `pick()` 真没被调用。
看 `ViewportPanel.cpp` 的条件：
```cpp
if (m_ctx.isEditing() && hovered && !gizmoConsumed && !navGesture &&
    !m_gizmo.dragging() && ImGui::IsMouseClicked(ImGuiMouseButton_Left))
```
注意 **`ImGui::IsMouseClicked`**（按下的那一帧）。而 `mouse_set_client` 是
`PostMessage(WM_MOUSEMOVE)` + `SetCursorPos`，之后隔 0.35s 才
`mouse_event(LEFTDOWN)`。

**结论**：Windows 会拿"窗口激活后的第一次左键按下"去激活窗口，ImGui 收不到
它。于是**全程第一次点击静默丢失**。这完美解释了失败的样子：
* 正中那一下是全程第一次点击 → 丢了 → 什么都不打、一行日志都没有；
* 右下角那一下是第二次 → 正常出 `pick: nothing hit`
  （而这条断言只看"日志里有没有 `pick: nothing hit`"，于是**恒真地**通过，
  给了一个虚假的"至少空地那条是对的"的信号）。

**修法**：在第 2 组开头加一次**预热点击**（右下角空地，本身也是合法对照），
断言它确实产生了 pick 日志；并把"点空地"那条改成**计数增量**判据
（`miss_count()` 前后对比）—— 否则预热那条日志会把恒真判据喂饱。

改完 `verify_bvh` 单跑 **PASS rc=0 20.2s**（此前连续 3 次同一处 FAIL）。

**同类影响面**：`verify_mesh_params` 的拖拽、`verify_collider_gizmo` 的第一次
拖拽同样是"全程第一次鼠标输入"。`verify_mesh_params` 单跑 PASS（它的
`drag_h` 里已有 `force_foreground`，且拖拽前还有一次成功的面板点击），
暂不改；`verify_collider_gizmo` 本轮已 PASS，**刻意不动**（加预热点击会改变
它的选中 / collider 编辑态，反而可能弄坏）。

**教训**：验证脚本里凡是"注入鼠标操作然后断言结果"，第一次操作要么丢弃、
要么显式预热并断言预热本身生效 —— 否则第一次操作失败时会以"很合理"的
面貌出现（点不中物体、拖不动滑块），把人引向引擎逻辑去查。

## 本轮踩的坑（重要的都在这）

1. **`vkGetPhysicalDeviceFeatures2` 在 1.0 实例上是无效调用**（验证层报 ERROR、
   结果全 0）→ `separateDepthStencilLayouts` 误判不支持 → Device throw。
   修：Instance 的 apiVersion 升到 1.2（`vkEnumerateInstanceVersion` 查 loader
   取 min(1.2, supported)）；Device 用 `VkPhysicalDeviceFeatures2`+pNext 链
   查询并启用 Vulkan12Features.separateDepthStencilLayouts（此时
   `pEnabledFeatures` 必须为 NULL，samplerAnisotropy 走 feats2.features）。

2. **DEPTH_READ_ONLY_OPTIMAL 独立布局需要 separateDepthStencilLayouts 特性**
   （未启用时 6 条 VUID）。共享深度方案是硬需求 → Device 创建时显式启用，
   不支持直接 throw（本方案在这类设备上无法工作）。

3. **着色器 set/binding 与 C++ 描述符布局错位**（一次修三处）：
   ssao_blur.frag / fg_ssgi / fg_ssr / fg_godrays.frag 都把"源图+深度"声明在
   **同一 set（set0 binding0/binding1）**，而 C++ 侧是**两个独立 set**

   VkPipelineLayout` + 运行期 vkCmdDraw 报 binding 缺失。**教训：写这类着色器
   前先看 buildDescriptorSets 的 set 划分。**

4. **DescriptorAllocator 的 maxUBOs=0 会把 descriptorCount=0 的条目带进池**

5. **ping-pong 保守屏障 oldLayout 不能写 SHADER_READ_ONLY**：k=1 工作图在单

6. **验证层的 VUID 报错不致命但会毁回归**：`零 VUID` 判据让所有用例 FAIL，

   是缓冲没刷）。判崩溃要看 errs 里有没有 Fatal / 窗口是否存在。

7. **场景 JSON 的 mesh size 只吃标量**：`"size":[2,2,12]` 数组直接让加载崩

# 第二轮：纹理能力（mipmap / 各向异性 / BC / 纹理流）

## 摸底结论
- **各向异性其实早已接通**（Device 查 maxSamplerAnisotropy≤8 →
  TextureContext → sampler anisotropyEnable）——缺的只是 MYVK_ANISO
  覆盖钩子与验证。
- mipmap 缺失（mipLevels=1、maxLod=1）；BC/纹理流完全缺失（stb→RGBA8
  一次性同步上传）。

## 实现（engine/assets/Texture.h/.cpp 重构）
- **mipmap**：MYVK_MIPMAP=1 时 RGBA8 路径 blit 链生成 mip（每层源层
  blit 前转 TRANSFER_SRC、blit 后就地转 SHADER_READ；**初始 barrier 必须
  全层 UNDEFINED→TRANSFER_DST**——只转 level0 会让 blit 目的层撞 09600）。
  默认关 = mipLevels 1 + maxLod 1，基线逐像素不变。
- **BC 压缩**：Texture::fromDDS 解析 DDS 头（fourCC DXT1/3/5、ATI1/2、
  DX10 扩展 DXGI 71/74/77/80/83/95/98）→ vkCmdCopyBufferToImage 逐层
  直传（不解码）；`.dds` 扩展名在 fromFile 自动分派。
- **纹理流 lite**：MYVK_TEXSTREAM=1 且 DDS 时先只传 mip0，未传层也转
  SHADER_READ（内容未定义但布局合法，验证层按描述符视图**全层**查布局；
  maxLod=1 挡住逻辑采样）；AssetManager::tickTextureStreaming() 由
  Application 主循环每帧驱动，每帧补一层（SHADER_READ→TRANSFER_DST→
  copy→SHADER_READ），完成后重建 sampler 放开 LOD + 刷描述符。
- **流完整性黄金判据**：TEXSTREAM=1 最终帧与 TEXSTREAM=0 逐像素一致
  （n=0 PASS）。
- AssetPath/CMake：assets/textures 加入 POST_BUILD 拷贝。

## 工具链（tools/make_bc_dds.py）
- Pillow 只能读 BC 不能写 → numpy 手写 BC1/BC3 编码器（per-channel
  min/max 端点 + 565 量化 + 4 色调色板最近索引）+ 手写 DDS 头。
- **三个坑**（都踩了）：
  1. DDS 头 struct 格式 `8s` 装 32 字节 ddspf 会被截断 → `32s`；
  2. same 端点进位段必须只作用于 same 块（全图数组无脑 +1 会把非
     same 块的调色板与已编码 v0 撑错位 → PSNR 8dB）；
  3. decode 侧 (Bh,Bw,16,3) 直接 reshape 成图像会把块列与 texel 维
     错位拼接 → 必须 reshape(Bh,Bw,4,4,3).transpose(0,2,1,3,4)。
  修复后 roundtrip PSNR 42.3dB。
- 内置 BC1 解码器做自检（Pillow 不支持 BC 回读）。
