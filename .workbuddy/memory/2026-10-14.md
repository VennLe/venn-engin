### 关键坑（**全部是 MSVC 独有，MinGW 没这些**）
1. **代理变量大小写重复 → MSBuild 直接崩**
   `https_proxy` 与 `HTTPS_PROXY` 同时存在时，MSBuild 内部用 .NET Framework
   的 `Hashtable` 存环境变量，**这张表大小写不敏感** → 抛 `ArgumentException`
   → 报成 `MSB6001: "CL.exe" 的命令行开关无效`。同样的坑也咬了 PowerShell 的
   `Enter-VsDevShell`（`Path` vs `PATH`）。
   **修法：调 vcvars/msbuild 之前清掉小写版**（`vcvars.cmd` / `msvc-build.cmd`
   开头都做了）。诊断线索藏在 `build/CMakeFiles/CMakeConfigureLog.yaml` 里。
2. **源文件 UTF-8 无 BOM + 中文注释 → C2001「常量中有换行符」**
   MSVC 默认按系统 ANSI 代码页（本机 936/GBK）解析源文件，中文字符串的
   UTF-8 字节在 GBK 下被切成"半个字符"，编译器以为字符串没闭合，
   报 C2001 + 一串 C2143/C2059 语法错误（`Lod.cpp:19`、`Light.h:67/97`、
   `MdiDraw.h:64`…）。**修法：给 cl 传 `/utf-8`**（= `/source-charset:utf-8
   /execution-charset:utf-8`），已在 `CMakeLists.txt` 里为所有 target 钉死
   （venn / glfw / imgui / ufbx 各一次 + 全局一次）。
3. **`.cmd` / `.bat` 必须纯 ASCII** —— 老坑重现。给 `vcvars.cmd` 写中文注释，
   cmd 按 GBK 读取变乱码，被当命令执行，日志里一片
   `'xxx' 不是内部或外部命令`。**已把 `make.cmd` / `vcvars.cmd` /
   `msvc-build.cmd` 全部改成纯 ASCII。**
4. **GNU Make 在 Windows 上可能用 sh 执行配方**（PATH 里有 PortableGit 的
   sh.exe 时）。后果：
   - `echo` 里的 `(` `)` `|` 会让 sh 语法错误 → 已移除
     （`MSVC (cl.exe via ...)` → `MSVC cl.exe via ...`）。
   - cmd 的 `if exist` 不能放进 `$(shell ...)`。
   - `$(wildcard)` 探测**含空格的路径必须用反斜杠转义**：
     `$(wildcard D:/Microsoft Visual Studio/...)` → **空**（探测永远失败，
     静默退回 mingw）；`D:/Microsoft\ Visual\ Studio/...` → 命中。
     ⚠ GNU Make **没有** `exists()` 函数（试过，返回空）。
5. **MSVC 模式下不要把 `$(PARALLEL)` 拼进 `msvc-build.cmd build`** ——
   会被脚本当成 target 名，报 `CMake Error: Invalid value used with --target`。
   并行度由脚本自己从 `NUMBER_OF_PROCESSORS` 取。

## R4-1 AlphaMode::Mask（alpha 裁切）+ 抖动裁切 ✅ 完成

路线图 `docs/render_roadmap.md:567` 的任务（原标"S，性价比极高，建议提前"）。
交付：`Material::AlphaMode` 从 2 值（Opaque/Blend）扩到 3 值（+**Mask**）。

### 交付
- **第三种 alpha 模式 `Mask`**：写深度、不混合（管线固定状态与 Opaque 相同），
  片元 `alpha < cutoff` 时 `discard` → 镂空处背面透光。
- **抖动裁切 `ditherAlpha`**：4×4 Bayer 有序抖动代替固定阈值（配合 TAA 累积出
  柔和边缘，且**照样写深度**，不像 Blend 会排序崩）。
- 关键字系统加 **bit3 `VENN_ALPHA_MASK`** → 变体 **8 → 16**。
- `ShaderKeywords.{h,cpp}` / `CMakeLists.txt`（`SHADER_KEYWORDS`）/
  `pbr.frag` 的 `#if VENN_*` 三处同步（2³→2⁴ 的位序表）。
- MSAA 下管线开 **alpha-to-coverage**（`VariantPipelines::applyKeywordState`
  + `Pipeline::multisample.alphaToCoverageEnable`），配 alpha 预映射
  `alpha' = clamp((alpha-cutoff)*2+0.5)` 让 cutoff 滑条在 1x / MSAA 下表现一致。
- 组件/Inspector：材质面板 Alpha Mode 下拉加 `Mask`；Mask 模式显示
  `Alpha Cutoff` 滑条 + `Dither Alpha` 勾选框。序列化存
  `alphaMode`（字符串）/`alphaCutoff`/`ditherAlpha`，并保留旧 `alphaBlend`
  布尔向后兼容。
- `tools/verify_alpha_mask.py`（5 组全 PASS），进回归 `DEFAULT`。

### 关键判断
- **cutoff 载体 = `push.skin.w`**（最后一个空闲位，偏移 124）。push 常量被硬件
  卡死 128 字节，不能再加字段。**符号位当抖动开关**（负 = 抖动，绝对值仍
  cutoff）。
- **Mask 跳深度预通道**：预通道不采样材质，无从判断镂空位置。
  `Renderer::buildDrawLists` 置 `DrawItem::skipDepthPrepass`，
  `recordOpaqueDepthGeometry` 两种（instanced / 逐项）都跳过。
- **Mask 走不透明队列**（唯一判据仍是 `kKeywordAlphaBlend` 位）。
- **非 Mask 材质推 +0.5**（旧默认值），它们在编译单元里读不到该值 ——
  保证 Opaque/Blend 逐像素不变。

### 踩坑（重要）
1. **CMake 生成式 `-D` 表会因空串被丢弃而错位**（最隐蔽的 bug）：
   `list(APPEND VARIANT_DEFINES_ALL "${DEFS}")` 在 `DEFS` 为空时**该项被整个
   丢掉**，导致后面所有变体的位序整体前移 —— `k8` 编译时传的是
   `-DVENN_NORMAL_MAP=1`（bit2）而非 `-DVENN_ALPHA_MASK=1`（bit3），
   **`pbr.k8.frag.spv` 里根本没有 `OpKill`**。
   修法：空项存哨兵 `"_"`，非空用 `list(JOIN DEFS " " DEFS_STR)` 拍平，
   最后 `list(TRANSFORM ... REPLACE "^_$" "")` 还原。
   **验证手段**：`spirv-dis build/shaders/pbr.k8.frag.spv | grep -c OpKill`。
2. **多关键字组合必须 `separate_arguments`**：`${DEFS_STR}` 是带空格的
   单个字符串（`"-DVENN_DOUBLE_SIDED=1 -DVENN_ALPHA_BLEND=1"`），
   不拆会被当成**一个**畸形 `-D` 参数 → glslc 报
   `'#if' : unexpected tokens following directive`。
   `separate_arguments(DEFS NATIVE_COMMAND "${DEFS_STR}")` 后再用。
3. **alpha-to-coverage 只允许 samples != 1**：Vulkan 硬编码 0.5 阈值，
   1x 下开 `alphaToCoverageEnable` 会让 `vkCreateGraphicsPipelines` 报错 →
   必须 `hasKeyword(...) && desc.samples != VK_SAMPLE_COUNT_1_BIT`。
4. **验证脚本采样区选错 → 假 FAIL（耗时最久的坑）**：
   相机 (0,-26,9) 俯角 8° 时视口**上半是天空盒**，测试板在裁剪区纵向
   ~72%~96%。首版 `center_mean` 取"视口正中"→ 只采到天空 → cutoff 变化测不出，
   一度误判成"shader 没生效"。改用 `panel_mean_diff`（锚定裁剪区 72%~92% ×
   30%~70%）后 5 组一次通过。
   **教训**：任何"片元/画面级"验证，先拿哨兵（shader 里 `w>1.5` → 输出灰度）
   确认真实数据流与采样区可见性，再下"功能没生效"的结论。
   （已加 `MYVK_CUTOFF_DBG=1` 打 `CUTOFF-DBG mat=.. cutoff=.. lane=..`。）

# R4-4 延迟贴花（DBuffer）✅

## 结构（先落地，再看为什么看不见）

一条贴花 = **一个盒体**。渲染器自建单位立方体 × 贴花世界矩阵，片元**不采盒体自己的表面**，
而是按 `gl_FragCoord` 从场景深度 `texelFetch` 重建**场景表面**的世界坐标 P（与 SSAO/SSR 同一套
重建），`P → worldToLocal` 投到贴花局部空间：

```
|local|/halfSize 的最大值 m > 1  → discard
否则按局部 Z 平面投影取 uv = vec2(local.x*side, local.y)/size.xy + 0.5（side = sign(nL.z)）
结果写三张 DBuffer（反照率 / 世界法线 / 粗糙度-金属度），第四通道统一 coverage
```

**盒内测试同时替代了深度测试** —— 盒体在表面后面的像素，重建点必然落在盒外。所以这个 pass
**不要深度附件**：引擎场景深度是 MSAA 的（跟 HdrTarget 走，实测 4x），DBuffer 是单采样，
采样数不同没法共用同一个 RenderPass 的深度附件；盒体自己也不吃深度测试（管线
`depthTest/depthWrite` 全关），画**正面**（凸体正面投影 == 整个盒体投影）。

三张图同分辨率 `R8G8B8A8_UNORM`（**线性**，做 sRGB 解码会把法线/粗糙度整体扳偏）。
混合语义（`PipelineDesc` 只支持一套）：`rgb = src·src.a + dst·(1-src.a)`、
`alpha = src + dst·(1-src.a)` → 清屏 `alpha=0` 时前向 Pass 直接跳过整段，这就是
"关 = 基线逐像素不变"的实现依据。

接线：`DecalRecord`（std430 **192 B**）走 **SSBO** 而非 push（两个 mat4 就吃满 push 的 128 B
下限）→ push 只剩 4 B 记录下标。`DecalBuffer` 自有 set0 = `{FrameUBO, 深度图, 记录 SSBO}`，
set1 = 逐贴花 `{albedo, normal}`。`FrameUBO` 720 → 736 → **752 B**（`decalParams`），
全局开关走 `decalParams.x`（**不是**关键字位 —— 贴花开关可随时切，关键字位留给材质属性）。
set0 binding 20/21/22（`kGlobalSetBindings` 20 → **23**）。`GpuTimer::kSectionCount` 9 → **10**。
`MYVK_DECALS` 默认**关**；`kMaxDecals = 64`/帧。

## 症状：贴花完全不可见

一切接线都写完、编译通过、日志正常（`DECALS: on`、`CULL-STATS decal=1`），但
**`diff on vs base: >18=0`** —— 贴花一个像素都没画上去。

## 排查：5 轮，前 4 轮的方法本身是错的

1. **第 1 轮（错误）**：把重建出的 P 编码成颜色输出，想用数值反推它偏在哪。
   读数全部贴在 0 或 1 附近，什么也看不出。
   **原因**：调试写 `coverage=1`，前向用 albedo × ~2.3 曝光再 tone-map（`x/(x+1)`）
   → 输出**饱和**，任何数值编码都被压平。**这一轮的所有推断作废。**
   → 改用**饱和原色做分类编码**（黑/蓝/黄/品红/绿），直接看截图区分"走了哪条分支"。
2. **第 2 轮**：分类编码显示 **蓝色（`m > 1`）106,634 px = 35.65%**，深度有效、coverage 正常
   → 盒内测试**恒判定失败**，且覆盖率正好等于盒体屏幕投影占比（说明几何没问题）。
3. **第 3 轮**：左右两半探针 → 深度落在 0.5..0.99、`local.z` 恒 ≥ 0。看不出所以然。
4. **第 4 轮**：怀疑分辨率 / MSAA / sampler。都排掉了 ——
   临时 `DECAL-DBG` 日志实测 `screenExtent=608x492 hdrExtent=608x492`（与
   `ppmScene` 一致，608×492 是画布、不是交换链）、`MSAA 4x`、深度格式正常。
   还顺手自查了 `invViewProj`（把近平面点反投影，到 `camPos` 的距离 < 1 m，矩阵是对的）。
5. **第 5 轮（一击定位）：窄带身份测试**。
   地面在 9..16.5 m，相机 `0,-9,7`、near=0.1、far=200、fovY=45° → 深度**只可能**落在两个
   候选区间之一：
   * 若深度附件存 `(ndc+1)/2` → `[0.9908, 0.9942]`
   * 若存 `ndc_z` 本身 → `[0.9817, 0.9883]`
   探针读三档：`d≈0.9817 / 0.9850 / 0.9883` —— **落在后者**。

## 根因：深度附件里存的是 NDC z，不是 `(ndc+1)/2`

本引擎的投影由 `glm::perspective` 生成且**没有** `GLM_FORCE_DEPTH_ZERO_TO_ONE`
→ GLM 的 NDC z ∈ [-1, 1]；而 Vulkan 的深度范围**恒为 [0, 1]**
（`VkViewport::minDepth=0 / maxDepth=1` → `z_f = ndc_z`）。两者叠起来的后果是
**深度附件里存的就是 `ndc_z` 本身**。

`decal.frag` 里的重建照抄了 `space.glsl::vennViewPosFromDepth` 的 `depth*2-1`
→ 对 `ndc_z` 做**二次映射**成 0.9634..0.9766 → 重建点被**拉近 ~1.7 倍**
（地面上的点全部飞到场地上空 2~3 m）→ 盒内测试全数失败 → 一张贴花都看不见。

修复（`assets/shaders/decal.frag::worldPosFromDepth`）：直接用 `depth`，不乘 2 不加减 1。
⚠ 这个约定与 SSAO/SSR 那套**不一样**，在那两个 pass 里 `depth*2-1` 是对的（它们读的是
另一份深度？不 —— 这是同一个附件，但那两个 pass 的输出本来就是"相对参考"的自洽量，
错了也不显形）。**这里是最能显形的地方**，所以注释写了一大段钉在函数头上。

## 一并修掉的另外两个空间错误

* **`worldToLocal` 必须是"米空间"的逆**：`it.world = base * glm::scale(size)` 含尺寸缩放，
  原来顺手写 `worldToLocal = glm::inverse(it.world)` → `local` 被反成**单位立方体坐标**
  （`[-0.5,0.5]³`），而片元里"盒内测试"（`|local|` vs `size/2`）和"uv 投影"
  （`local.xy/size.xy`）两处都按**米**写 → 三套空间混用。
  → `DecalDrawItem` 加 `worldToLocal` 字段，`collectDecals` 里写
  `it.worldToLocal = glm::inverse(scene.worldMatrix(e))`（**不含** size 缩放）。
* **法线的矩阵要用转置**：局部 → 世界改成 `transpose(mat3(rec.worldToLocal))`
  （刚体逆的转置 = 旋转本身）；原先用法线的 `mat3(rec.world)` 里带非均匀 size 缩放 → 扭歪。

## 品质修正

两处 `dFdx/dFdy`（重建法线的 `dFdx(P)/dFdy(P)`、贴图 uv 的 `dFdx(duv)/dFdy(duv)`）
**移到所有 `discard` 之前**无条件算完 —— 被 `discard` 掉的辅助调用，导数是垃圾。
贴图采样相应从 `texture()` / `textureLod(...,0)` 改成 **`textureGrad(tex, duv, ddxUv, ddyUv)`**。
（行为中性：程序化贴图是单层、无 mip，但接口这对。）

# 回归提速：变更影响分析（"只跑关联用例"）

## 旧机制的问题

原来的增量是**两层指纹**：① `build/bin` 全量算一个"产物指纹"（一变 → 全清）；② 每个用例
自己一个指纹（脚本 + 递归 import 的本地 tools 模块）。

第 ② 层很好用，但第 ① 层是**全有或全无**：只要有**任何一次重链接**，`Editor.exe` 就变了 →
39 例全跑 30+ 分钟。而这是最日常的情况：加个特性、改一行着色器、修个布局，全都要付这个价。

## 新设计：两道闸 + 三张表

把"产物指纹"换成**源码变更影响分析**。

**闸 ①（用例脚本）**：该脚本 + 它递归 import 的本地 tools 模块没变 → 判定逻辑没变。
（与原实现一致，保留。）

**闸 ②（变更影响分析）**：把**构建输入**（`WATCH_ROOTS` = `engine/` `editor/`
`assets/shaders|models|textures` `CMakeLists.txt` `Makefile` `make.cmd`）拍一份
`(相对路径 → (大小, mtime_ns))` 快照存进缓存；下次运行时 diff 出"自上次回归以来改过
哪些文件"（新增 / 修改 / 删除都算），再按三张表归类：

    ┌─ 变更文件 ─┬─ 命中 GLOBAL_GLOBS ──→ 全量重跑（横切，安全兜底）
    │            ├─ 命中 TRIGGERS      ──→ 只重跑它登记的那些用例
    │            ├─ 命中 IGNORE        ──→ 无视（文档/记忆/编译辅助脚本）
    │            └─ 谁都没命中          ──→ ⚠ 全量重跑 + 点名（提示补表）

**三条铁律**（决定这套东西安不安全）：

1. **没登记 = 全量 + 点名，绝不静默跳过。** 映射表的价值是"把已经确认过归属的文件从全量
   里摘出来"，不是"猜哪些不重要"。所以它能增量补：补得越多越快，**没补的部分退化成今天
   的行为，不会漏**。
2. **不要把横切文件写进 `TRIGGERS`。** 命中 `GLOBAL_GLOBS` 的永远**先**按全量处理，
   写进 `TRIGGERS` 是死代码；更糟的是 `--narrow` 下它会变成一条"看着有归属、其实没覆盖"
   的**假映射**，把该跑的用例静默跳过。我第一版就把 `ShaderKeywords.*` / `VariantPipelines.*`
   / `engine/assets/Material.h` / `engine/physics/**` 写进去了，被自检抓出来。
3. **判定顺序 = 先横切 → 再忽略 → 最后映射。** 见下面第 ① 个坑。

**横切文件（`GLOBAL_GLOBS`）** = `CMakeLists.txt` / `Makefile` / `cmake/**` /
`engine/core/**` / `engine/rhi/**` / `engine/render/RenderTypes.h`（FrameUBO + set0 契约）/
`ShaderKeywords.*`（变体位序三处对齐）/ `ShaderPath.*` / `VariantPipelines.*` /
`FrameGraph.*` / `FrameResources.h` / `Renderer.cpp|h`（所有 pass 的接线中枢）/
`engine/scene/Scene.h|Scene.cpp|Transform.h` / `engine/ecs/**` / `engine/ui/**` /
`engine/assets/**` / `engine/physics/**` / `assets/shaders/common.glsl` / `space.glsl` /
`pbr.frag` / `pbr.vert` / `fullscreen.vert` / `depth_only.frag`。

⚠ `assets/models/**` 与 `assets/textures/**` **故意不在**横切清单里 —— 它们只被个别用例读，
放进横切会把所有图形用例一起拖下水；留在"未登记"状态效果一样安全（全量 + 点名），
还多一层提示（看到名字就知道该往 `TRIGGERS` 里补哪条）。

## 实测收益

| 改动内容 | 跑几例 | 耗时 |
|---|---|---|
| 只改 `assets/shaders/decal.frag` | **1** | ~100 秒 |
| 改 `decal.frag` + `DecalBuffer.cpp` | **1** | ~100 秒 |
| 改 `fg_taa.frag` | **1** | ~90 秒 |
| 改 `editor/InspectorPanel.cpp` | 1 | ~35 秒 |
| 改 `Renderer.cpp`（横切） | 39 | 30+ 分钟 |
| 改 `Renderer.cpp` + `--narrow` | 6（那 6 例是"没登记"的） | ~4 分钟 |

**核心收益是着色器内循环**：C++ 接线改完、构建一次之后，往往要反复调 `decal.frag` 十几次 ——
每次从 30+ 分钟降到 ~100 秒。这是实际开发里最值钱的那条路径。

`Renderer.cpp` 是全量的天花板：**文件粒度看不出"改的是哪一段"**。想在"确认只动了一个特性"
时跳过它，用 `--narrow`（作者显式断言其它特性不受影响），再把该特性用例**显式点名**
（点名的用例永远跑）。

## 顺带加的两件事

1. **`--explain` 干跑**：只打印影响分析、不跑。改完先看一眼"会跑哪些、为什么"，
   比跑完了才发现跑错东西便宜得多。
2. **`tools/check_regression_map.py` 映射表自检**（秒级、不跑 GUI）。这是必需的 ——
   映射表天生会腐化，而它的腐化方式**恰好是静默的**。查 5 类问题：
   A. 影响分析的 13 个行为分支（合成快照，不碰仓库文件）
   B. 快照覆盖范围（该进的进：`decal.frag`/`CMakeLists.txt`；不该进的不进：
      `assets/scenes/**` 是编辑器运行时自己会写的目录，进快照就每轮都"变了"）
   C. 映射覆盖率（哪些用例没登记 → 会无条件重跑）
   D. **死映射**：`TRIGGERS` 里写了不存在、又不带通配的路径
   E. **全横切登记**：某用例的 globs 全落在 `GLOBAL_GLOBS` 里 → 等于没登记，
      应移出 `TRIGGERS` 转成"无条件重跑"，否则 `--narrow` 下会假跳过

## 本轮踩的 3 个坑

① **`.txt` 后缀的忽略规则把 `CMakeLists.txt` 吞了**（自检分支 J 抓出来的）。
   `IGNORE_SUFFIXES` 里放了 `.txt`（本意是忽略随手放的说明文件），于是
   `CMakeLists.txt` 被判成"文档 → 忽略" —— **改了构建配置却什么都不跑**，
   这是最危险的一类 bug（静默漏测）。修法：**先判横切、再判忽略**（顺序即语义），
   并且把 `.txt` 从后缀表里删掉。教训：**通配规则和"名字长得像文档的构建文件"会撞车**，
   凡是"忽略"类规则都要把"必须生效"的东西先判掉。

② **死映射**：`verify_decals` 里登记了 `assets/shaders/decal.msaa.frag`，但那个文件
   **不存在** —— MSAA 变体是 CMake 从 `decal.frag` 加 `-DVENN_MSAA_DEPTH=1` 派生的
   （`CMakeLists.txt` 里 `decal.frag` 同时出现在变体列表里）。自检的 D 项抓出来的。

③ **我自己的测试脚手架先写错了两次**：`snap()` 辅助函数用 `__` → `/` 做键名转换，
   结果单下划线（`decal_frag`）没被转换，导致"改一个文件"实际变成"新增一个键 + 删除一个键"，
   测试报告假失败。**测试脚手架本身也会腐化** —— 第二次改成显式传路径列表才干净。
   写测试时别用"聪明"的字符串变换。

# 新机制第一轮就抓到 R4-4 的真 bug：20 个 Vulkan 对象泄漏

## 现象

R4-4 首次全量回归 **36/39**，失败 3 例：`verify_collision_play` / `verify_drop_to_floor` /
`verify_drs`。

其中 `verify_collision_play` 特别值得看：**17 项功能断言全 PASS**，唯一失败的是
"日志无 ERROR / 校验层报错"。那条 ERROR 是：

```
[ERROR] [validation] vkDestroyDevice(): VkDevice 0x... has 20 leaked objects
```

—— **关闭期**泄漏。**单独复跑一次，可靠复现**（不是 flaky）。

## 根因

`~DecalBuffer()` 里写的是 `m_frames.clear();`。

`DecalFrame` 是个装裸句柄的 struct（`VkImage` / `VkImageView` / `VkDeviceMemory` /
`VkFramebuffer`），`std::vector::clear()` **只析构元素**，而这些成员是 POD 句柄、析构
什么都不做 → 没有一个 `vkDestroy*` 被调用。

账刚好对上：3 张 DBuffer × 2 帧 = **6 image + 6 view + 6 memory + 2 framebuffer = 20 个**。

而 `DecalBuffer` 是**无条件构造**的（`Renderer.cpp` 里 `if (!m_decals) m_decals =
make_unique<DecalBuffer>(...)`，不在 `MYVK_DECALS` 的判断里）→ 这个泄漏与"贴花开不开"
无关，**每次运行**都会在设备销毁时被点名。

对照写法：`VolumetricFog::~VolumetricFog()` 与 `SSAOPass::~SSAOPass()` 都规规矩矩调了
`destroyFrames()`。`DecalBuffer` 是唯一的异类。

**修法**：`m_frames.clear()` → `destroyFrames()`。

## 为什么只有它发现了（这条最重要）

全套 39 例里**只有 `verify_collision_play` 会让编辑器优雅退出**。其余脚本都是强杀进程
（或者只 tap 到测试结束就断开），`vkDestroyDevice()` 根本没机会跑 → 泄漏报告**根本不产生**。

我拿 8 个用例的日志验证过：`grep -c "Application shutdown"` 全是 **0**，只有
`verify_collision_play` 是 1。

所以它事实上是本项目的**资源泄漏门**。做了两件事把它固化下来：

1. **把它挂上整个渲染层**：`TRIGGERS["verify_collision_play"] = ["editor/EditorScene.*"]
   + RENDER_MODULES`。任何 render 模块少一个 `vkDestroy*`，它都会跑。
2. **回归脚本加一道"搭车式"兜底**：扫本轮**真跑过**的每个用例日志，命中
   `leaked objects that have not been destroyed` 就报 `== 横切检查 ==` 并把退出码置 1。
   为什么是"搭车"而不是全局扫描 —— 因为强杀的用例日志里压根没有这条，扫了也没意义；
   而"有源变更 → 至少有一个用例会跑"这个前提是新机制自己保证的。

⚠ **这条门是"只跑关联用例"的必要配套**：跳过的用例不再贡献覆盖率，**横切不变量必须
有人专门负责**。我差点在优化里制造出"泄漏再也测不出来"的真空。

## 本轮的又一个自造坑：整片 glob 会吃掉兜底

我第一版把泄漏门写成 `engine/render/**`。自检立刻报红：

> 新增**未登记**的 render 文件 → 全量 + 点名 ... FAIL got=['verify_collision_play']

因为 `engine/render/**` 会把"**新增的、还没人认识的** render 文件"也判成**已登记**
→ 它就不再触发"未登记 → 全量"的兜底，只跑了一个用例。**这是把"保守"改成"激进"**，
方向完全反了。

改成 `RENDER_MODULES`（把 `engine/render/` 下非横切的模块**逐个列出来**）：
新加模块仍然是"未登记" → 全量（安全）。并且给自检加了 [F] 项：
**"engine/render 下的每个文件要么在 GLOBAL_GLOBS、要么在 RENDER_MODULES"** ——
以后加新 render 模块，自检会提醒我补进泄漏门。

教训：**通配 glob 的"范围"就是它的语义**。写"整片目录"之前先想清楚：
它会不会把那些**本该落到兜底分支**的东西也一起认领了。

## 另外两例失败（判定为既有 flaky，待复跑确认）

- `verify_drop_to_floor`：B 组 "视口左键没点中 FloatingCube（pick 日志缺失）" ——
  典型的**注入点击被吞**（Windows 拿第一次左键去激活窗口）。与坑 #66 同源。
- `verify_drs`：D 组 `边缘感知升采样的高频能量 > 纯双线性` → 2.290 vs 2.428（差 5.7%）。
  这是一个**边缘很窄的锐度指标断言**（R1-4 的），场景/AA 状态的微小差异就能翻。
  两者都与 R4-4 无关（R4-4 不碰物理、不碰 DRS）。

## 一次性成本：缓存格式迁移

新的 `load_cache()` 不认旧的 `bin` 指纹格式 → 迁移脚本把 `src` 快照补上
（36 例 passed + 36 条 tests 原样保留），之后定向复跑 `verify_decals` +
`verify_collision_play`（这两个受析构修复影响）+ 上面两个可疑 flaky。
**4 例 3m55s**（`verify_decals` 115.9s / `verify_collision_play` 10.0s / `verify_drs` 70.7s /
`verify_drop_to_floor` 30.8s）→ **4/4 PASS**，而不是全量 39 例 34 分钟 —— 这正是新机制要的效果。

⚠ 诚实记账：其余 36 例的结论来自**修复前的二进制**。析构修复只影响"关闭期是否销毁资源"，
不改变任何功能路径，所以不重跑是合理的；要一份权威全绿随时 `--all`。

**泄漏修复的独立验证**（不信"日志里没看到就等于没有"）：
直接跑 `MYVK_FRAMES=60 MYVK_HIDE_UI=1 ./Editor.exe` → 输出
`Application shutdown. Total frames: 60`、退出码 0、**无 leaked objects 行**。
修复前每一次优雅退出都必然出现那一行，所以"没有"是有意义的证据。

## 收尾：完全没变更时一例都不跑

原来的 `no_trigger` 用例（没登记 TRIGGERS 的那 6 个）**无条件重跑**。但"快照与上次完全一致"
时它们也不可能受影响 —— **"没变 ⇒ 结果不变"**。所以改成只在**本轮确实有源码变更**时才
无条件重跑。效果：无变更时 `run_regression.py` 一例不跑（零 GUI 启动）就报 `39/39 通过`
（39 例全部 SKIP）。这是"刚才那轮被打断了，再跑一遍确认"的常见用法。

同时把"没登记 TRIGGERS"的警告收敛成一行，且只在有变更时才打 —— 否则每轮都刷 6 行噪声。

## 最终状态

- `tools/run_regression.py`：两道闸（用例脚本 + 变更影响分析）、`--explain` / `--narrow` /
  `--all`、横切泄漏兜底扫描。
- `tools/check_regression_map.py`（新）：映射表自检 A~F，**全绿**。
- `engine/render/DecalBuffer.cpp`：析构改调 `destroyFrames()`。
- 缓存：39/39 PASS，源码快照 225 条（新格式）。

## 遗留（影响分析的边界）

`engine/render/Renderer.cpp` 是**文件粒度**的死结：它是所有 pass 的接线中枢，一改就全量。
真要细分，只能做到"按改动行所在的 **banner 段落**（`// ==== 延迟贴花（R4-4）的收集 ====`
这类）反查特性"——但那需要一个可靠的"上次回归时**文件内容**"基准（git 只能给
"工作区 vs HEAD"，而回归常常在未提交状态下跑），成本与脆弱度都不划算。
`--narrow` 是性价比更高的替代。

另一条边界：**"未登记 → 全量"的兜底依赖"新增文件没人认领"**。所以任何写进表的
**整片 glob** 都会削弱兜底（见上面 `engine/render/**` 的自造坑）。
往表里加 glob 时，宁可"精确到文件"，别图省事写目录。

### 根因（三条，都是结构性的）

1. **两套平行控制世界**：env（`Renderer` 构造时读，**给自动化测试**）+ UI（面板直改**同一个**

   字段加了、env 加了、面板忘了 = "只有测试能用、人用不了"的功能。
2. **没有"特性登记"这一步**：缺了没人提醒，**静默**。
3. **面板是 500 行手写长函数**（`drawEnginePanel`），不是声明式清单 → 参数一多必然漏。

### 交付物

1. **`docs/editor_architecture.md`**（架构全文，12 节 + 3 附录）：
   * 六层：L0 特性注册表(SSOT) → L1 设置层级(偏好/项目/场景/对象/相机) →

     **"每个功能都有 UI"成为系统的性质，而不是人的记性**。
   * 七条原则：SSOT / 声明式优先 / 分级暴露 / 双向可测 / 全链路可序列化 /

   * 与现有代码**增量衔接**：4 个设置结构体只加元数据、**不动布局**（`offsetof` + 类型分派），

### 三个自己踩的坑（都写进工具注释了）

1. **计数必须用集合差**。第一版用 `len(reg)+len(allow)` 相减 → 算出 **-1**
   （同一变量既被登记又命中白名单前缀 `_DBG`）。改成三个两两不相交的集合。
2. **工具必须排除自己再扫仓库**。登记表里写了一堆 env 名字，扫进去会让
   "每个 env 都出现在仓库里"，**G 组（陈旧登记）永远无法报红**。
3. **通配符写法会污染统计**。注释里的 `MYVK_VFOG_*` 被正则抓成变量名 `MYVK_VFOG_`，
   误报成"裸 env 漏网"。过滤"以下划线结尾"的名字。
   同类误报：`gpu_timing` 我一开始拿日志标签 `GPU-TIMING` 当 UI 证据，实际
   Stats 面板显示的是 `GPU: %.2f ms/frame` —— **token 要取 UI 上真实存在的字面量**。

## 自测抓出来的两个真缺陷（都不是回归报的）

1. **折叠状态读盘后丢失**：`collapsed` 只是工具提示/菜单标签的标志位，真正的折叠是靠把 `ratio`
   设成 0/1 实现的；而 `ratio == 0` 在读盘时又被当成"自适应"哨兵（`setAutoRatio()` →
   `beginFrame` 下一帧重算）→ 折叠一读回来就没了，而 `collapsed` 还是 true，自相矛盾。
   修法：折叠中的节点存的时候写真实比例、读的时候走**独立分支**（`setRatio` 顺带把
   `autoRatio` 置 false）。
   取证：`collapsed:true, ratio:0` → `SPLIT-2` 贴到 x=480（右区左边缘）；对照
   `collapsed:false` → 回到 x=1270（重算成自适应）。对照组证明原行为确实会丢折叠。
2. **两条分隔条叠在同一点时一次双击被吃两次**：某节点被完全折到 0/1 时，它的分隔条正好压在
   父节点那条线上；`hovered` 是每个节点各算一遍的，于是同一次双击"折一条 + 展一条"同时发生。
   修法：加"悬停独占"（子树先于父节点处理，先到先得）。

### 确定性修复（定稿后追加）

`Workspace.h` 承诺两条 ——「切到别的工作区再切回来 → 回到该工作区的**出厂预设**」与
「没在 open/close 里点名的面板 → 保持它自己的 `defaultOpen`」—— **都要求确定性**，
但 `applyWorkspace` 是**增量套用**的：没点名的面板保持**当前状态**，于是同一套工作区
从不同起点切进来长得不一样，直接违反承诺。修法：进入时先 `resetPanelStateToDefaults()`。

取证（`MYVK_EDITOR_WORKSPACE_SEQ="10:debug 25:animation"`）：
`debug` 把 stats 打开 → 切到 `animation`（其清单里既没开也没关 stats）后
**`stats=closed`**（回到 defaultOpen），不再从 debug 泄漏。修复前会是 `stats=open`。

顺带把 `editor/EditorApp.cpp` 里 `applyWorkspace` 的注释与 `Workspace.h` 的那条承诺
对齐（写明"这条成立的前提是先复位"）。
