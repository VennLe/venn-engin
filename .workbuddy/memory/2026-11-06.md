### UE 源码 → 本工程的对照表（判据，别再自己发明）

| UE | 这里 |
|---|---|
| `ACharacter::GetActorEyesViewPoint` → `GetMesh()->GetSocketLocation("head")` | 眼位 = **head 骨**的世界变换（走蒙皮公式 `jointMat·(invBind⁻¹·0)` 再乘 `push.model`），不是"脚 + 常数" |
| socket 的相对变换（美术在骨架里摆的那 4~5 cm） | `PlayerComponent::eyeOffset` / `GameStartComponent::eyeOffset`（**作者数据**，米、玩家局部轴） |

| `bOwnerNoSee` | 第一人称藏自己的网格（改 `VisibilityComponent`，不动 `MeshComponent`，所以影子里是当前帧姿势） |

## 动画按 UE 源码标准化（idle / walk / run / jump）

用户原话：「请把引擎中关于角色的第一和第三人称的初始化模型本身还有动画
（包括 idle,walk,run,jump）都按照 ue 源码中的标准去实现。」

### 1 · 地面三态 = 混合空间，不是硬切

新增 `engine/animation/BlendSpace.{h,cpp}`（唯一一份 1D 混合空间，等价
`UBlendSpace1D` / `BS_Locomotion`）。**差别不在"有没有过渡"，而在过渡期腿在
干什么**：硬切是两个完整姿势整身平均（两条腿各走各的相位 = 腿打结），混合
空间是"3/4 步 + 1/4 步"（仍是一个连续步态）。

三个关键决定：

- **样本位置按"移动速度"放，不按动画自然步速放**。UE 的 Walk@200 是因为它
  `MaxWalkSpeed=500`；本工程走路满速 4.5、冲刺 9，Walk clip 自然步速只有
  1.929 —— 按自然步速放会让 4.5 m/s 整段落到 Run 上（"一按 W 就在跑"）。
  步幅匹配 `strideMatch` 负责速率，两件事分工。
- **Sync Group 用归一化相位**换算（`phaseOf(mainTime,mainDur)*otherDur`），
  不能对齐秒数（Walk 1.03 s / Run 0.63 s，永远差一圈）。idle 不参与同步。
- **两端钳制，不外插**。外插把另一段权重算成负数 → "反相姿势"，比不混合更糟。
- 混合开关有**迟滞（进入 3% / 退出 0.5%）**：速度正好落在样本点上时实测抖动
  1~3%，会让 `blending()` 隔几帧翻转、采样路径跟着切 → `verify_frame_pacing`
  尖刺从 0 顶到 50/129 帧。

`BlendSample.slot` 只给"当前主段"命名（`kSlotIdle/Walk/Run`），不参与插值 ——
这样 `EDIT-ANIM state=walk clip=Walk` 这些**已有日志锚点逐字不变**，老脚本不用改。

### 2 · 空中三态（UE ABP 口径）

`Jump`（`!onGround && v.z > 0`）/ `Fall`（`<= 0`）/ `Land`（落地后
`landRecoverSec`，默认 0.12 s），**三段都不循环**。判据只能用竖直速度的
**方向** —— 起跳瞬间速度最大但在上升，抛物线顶点速度为零却在下降。

### 3 · 朝向：UE 两条互斥路线

| | 第三人称 | 第一人称 |
|---|---|---|
| 角色 yaw | 跟**移动方向**（`bOrientRotationToMovement`，`RotationRate=500°/s` 匀速、帧率无关） | 跟**控制器**（`bUseControllerRotationYaw`） |

第一人称不是手感偏好，是**几何后果**：头骨侧偏约 9 cm，身体若跟着移动方向
转，侧步时头骨绕中线横移 9 cm，配 80° 视场就是画面平移一下 —— 那才是
"第一人称发晃"的真实来源，跟镜头阻尼无关。`ViewRig::setViewMode` 会**覆盖**
`orientToMovement`。

## 帧节奏第二章：交换链图像数（同一个症状，不同根因）

### 现象与误判

加完混合空间后 `verify_frame_pacing` 的 A3/A4/A5 红，读数很怪：**均值 16.75 ms
（59.7 fps，完全正确）而中位数只有 9.6 ms**。当时先后怀疑并排除了：日志
I/O（`ANIM-BLEND begin` 每帧一条）、混合开关抖动（加迟滞）、
`MYVK_NO_LOCO=1`（整个状态机跳过，仍红）。

### 定位手法（可复用）

把 `CpuProfiler` 的上一帧分段读数追加进 `FRAME-DT`（现已常驻）：

```
dt=24.6 cpu rend=21.80 rw=15.99 rec=5.00 pres=0.05 logic=0.83
dt= 8.9 cpu rend= 6.09 rw= 0.05 rec=5.34 pres=0.04 logic=0.81
```

长帧的 16 ms 全在 `rw`（`vkWaitForFences`），`rec` 没变 → **是节拍问题不是
工作量问题**。`pres` 恒 0.04 → present 从不阻塞，阻塞被推到下一帧的 fence wait，
形成极限环 `8.6 / 24.9` 交替（和 = 2 个刷新间隔）。

### 根因与修法

交换链 `imageCount = minImageCount + 1`（= 3）允许 **2 个 present 排队**，
CPU 能跑到显示器前面一帧。改成**按呈现模式取**：

- 锁帧（FIFO）→ `minImageCount`（2），present 队列只压一帧，CPU 被 vblank 咬住；
- 不锁帧（MAILBOX/IMMEDIATE）→ 仍 `min + 1`，多余图像正是为了不让 CPU 排显示器。

实测：dt 从 `8.6/24.9 交替` → `16.7 ± 0.3 全程均匀`；A3 的 p90/中位 2.64 → **1.04**；
A4 尖刺 55/129 → **0/127**；A5 静止 50 / 移动 55 → **0 / 0**。

### 两条方法论教训（比修复本身重要）

1. **判据不可复现时，先怀疑被测系统有多个稳定态**。上一轮"基线绿、改动红"
   的真相是：这个交替节拍**双稳态** —— 同一份代码、同一台机器，有时锁得干
   干净净，有时落进交替。我这次在基线上加探针一测，基线**一样交替**。
2. **绝对阈值会随机器漂移**。`C1 不锁时 > 200 fps` 在本机永远红：编辑器整帧
   实测 103 fps（9.7 ms），而 surface **是**给 MAILBOX 的。9.7 ms 是工作量、
   不是锁。改成相对判据「≥ 锁帧组的 1.5×」（实测 1.70×），换机器不用改。

## #351 · 8 方向移动集（`Anims/Unarmed/{Walk,Jog}` 那一层）

**做了什么**：`assetio/ProcAnim` 从"一段前向步态"扩成"一段步态 × 8 个方向"，
`--procanim` 出 20 段（4 基础 + `Walk_*` 8 + `Run_*` 8），后缀逐字照抄 UE
（`_Fwd/_Fwd_Left/_Left/_Bwd_Left/_Bwd/_Bwd_Right/_Right/_Fwd_Right`）。
运行时**还没消费**（`BS_Idle_Walk_Run` 升二维是下一刀，见 docs §8.5）。

**踩到的最关键一条（值钱）**：腿是 `Hips` 的子节点，而摆动轴按"静止局部系"
给 —— 髋转了 `hipsYaw = 0.30×deg` 之后整条腿连同轴一起被带走，于是"轴按
`deg` 给"的结果是脚实际沿 `1.3×deg` 飞。实测：90° 侧移量出 **+121°**、
180° 倒退量出 **-112°**（倒退直接跑到侧后方去了，肉眼像"斜着退"）。
修法：`swing` 用 `deg - hipsYaw` 预补偿。补偿后 8 个方向全在 ±10° 内。

**其它三条**
1. `deg == 0` 必须走"原样复用 `Frame` 基向量"的分支，不能过 `angleAxis/normalize`
   —— 老 `Walk`/`Run` 两段要和改动前逐位相同（既有脚本与已烤资产按这个基线）。
2. 判据要用**摆动相脚掌速度方向**（`atan2(横向, 前向)`），不能用"前向位移范围"：
   后者是对称量，方向反了范围一模一样。这和 F34 抓"月球漫步"是同一条道理。
3. 光验"方向对"还不够，得同时验"45° 落在 0° 与 90° 中间"（A16）—— 否则退化成
   四档硬切也能全绿，因为硬切时 `Fwd_Left` 就等于 `Fwd` 或 `Left`。
